# 175 マージリクエスト本文に作業の一覧とコミットを載せる

<!-- sdd-cur:form -->

対象は [Issue #175](https://github.com/paterapatera/sdd-cur/issues/175)。課題ランナーが `createPullRequest` に渡す本文に、設計の作業の一覧をチェックボックス付きで載せ、各作業に対応する `Sdd-Cur-Task` コミットの短いハッシュを付ける。並びは、課題の URL、作業の一覧、印 `sdd-cur: 受け入れ手順`、受け入れ手順である。

手を入れる対象は、`src/runner.ts`（`pullRequestBody`、`runImplementation`）、`src/git.ts`、`skills/sdd-cur/conventions.md`（「マージリクエストの本文」）、`docs/canonical/runner.md`、`docs/canonical/conventions.md` である。`src/cli.ts` の `cmdTasks` は、作業の一覧の取り出しをランナーと共有する。

重なる課題は #173（作業ごとのコミットと `Sdd-Cur-Task`）、#29（マージリクエストの本文と知らせる課題コメント）、#56（quick の終わりと実装の終わりが同じ本文）、#6（課題ランナー）である。

## 範囲外

- 印 `sdd-cur: 受け入れ手順` の文字列を変えること
- 印の行より後ろを現在の手順として取る規則を変えること
- 作業の一覧を、印の行より後ろに書くこと
- マージリクエストを知らせる課題コメントに、URL 以外を書くこと
- 課題コメントに受け入れ手順を書くこと
- 確認と回答の課題コメントを変えること
- `[ ]` の行が残ることだけを理由に、マージリクエストを作らないこと
- #173 の `Sdd-Cur-Task` の行の形を変えること
- `task-done` のコミットメッセージを変えること
- 不具合修正のコミットメッセージ `fix: 課題 <番号> の不具合を修正する` を変えること
- 受け入れ手順の payload の空白を削ること
- 短いハッシュを 7 桁より長くすること
- 同じ作業番号の `Sdd-Cur-Task` を持つコミットが複数あるときに、最も新しい一件以外のハッシュを書くこと
- 同じ作業番号の `Sdd-Cur-Task` を持つコミットが複数あるときに、コミッター日時で SHA を選ぶこと
- 作業の一覧または対応するコミットを読み出せないときに、作業の一覧を書かず課題の URL、印、受け入れ手順だけでマージリクエストを作ること
- 作業の一覧または対応するコミットを読み出せないときの失敗の理由を、この失敗専用の日本語一行に統一すること
- 不具合修正のあとに、既存のマージリクエストの本文を更新すること
- `acceptanceComment` の拒否理由と、成功時の戻り値の形を変えること
- `createPullRequest` の引数の形と、戻り値の `number` と `url` を変えること

## 決定

| 項目 | 内容 |
|---|---|
| 本文の並び | 課題の URL、作業の一覧（各行が一行）、印 `sdd-cur: 受け入れ手順`、受け入れ手順の payload である。課題の URL と作業の一覧と印のあいだに、空行も見出しも説明も入れない |
| 作業の一覧の元 | 対象課題の `docs/issues/<番号>/design.md` を読み、`collectTasks` が成功したときの配列である。`collectTasks` は、今 `src/cli.ts` にある実装を `src/runner.ts` へ移し export する。`src/cli.ts` の `cmdTasks` はその export を呼ぶ |
| 作業の本文 | 各要素の `line` から先頭の `- ` を除いた残りである。`[番号]` も含む |
| チェックボックス行 | 対応するコミットが branch-only の範囲に一つ以上あるときは `- [x] `、無いときは `- [ ] ` のあとに作業の本文を続ける。`[x]` の行だけ、末尾に空白一つ、`(`、短いハッシュ、`)` を付ける |
| コミットの範囲 | `tasks` の `done` と同じ。`remoteName`、`defaultBranchFromSymref`、`branchOnlyCommitShas` を使う。マージリクエスト本文を組み立てるときのデフォルトブランチ名は、`deps.github.getDefaultBranch()` ではなく `defaultBranchFromSymref` である |
| 作業と SHA の対応 | `branchOnlyCommitShas` が返す SHA を、配列の順に見る。各 SHA のコミットメッセージに、行全体が `Sdd-Cur-Task: <作業番号>` と一致する行がある最初の SHA を、その作業に使う。二つ以上あるときも、この最初の SHA だけを使う |
| 短いハッシュ | 全文 SHA の先頭 7 文字を十六進の小文字で書く。`git rev-parse --short` の伸びる省略は使わない |
| 失敗 | 作業の一覧またはコミットの読み出しに失敗したときは、マージリクエストを作らず、読み出しが既に返す `Error` のメッセージをそのまま失敗理由にする。作業一覧だけ省略して本文を作ることはしない |
| 失敗の定数 | `NO_WORK_LIST_SECTION` は `設計に作業の一覧がありません`、`NO_WORK_LIST_ITEMS` は `作業の一覧に作業がありません` である。`src/runner.ts` から export し、`src/cli.ts` も同じ文字列を使う |
| `pullRequestBody` | 同期の純関数のまま残す。第三引数 `workListLines` は、作業の一覧の各行（チェックボックス付き）の文字列配列である。戻り値は `` `${issueUrl}\n${workListLines.join("\n")}\n${acceptanceComment(payload)}` `` である。`workListLines` が空配列のときは呼び出し側が拒否する。`acceptanceComment` の拒否は今どおり先に行う |
| 読み出しの入口 | `resolveWorkListLinesForPullRequest(designMarkdown, git, cwd)` を `src/runner.ts` に export する。成功時は `workListLines`、失敗時は `throw` する |
| 実装の終わり | `continueImplementationOnBranch` は、手順ファイルを読む前に `readSpecPair` で設計を読み、`resolveWorkListLinesForPullRequest` を呼ぶ。失敗したときは手順ファイルを消し、`createPullRequest` も `addComment` も完了ラベルも呼ばない。成功したあと `pullRequestBody(issue.url, payload, workListLines)` を呼ぶ |
| 三つの経路 | `runImplementation`、quick の実装の終わり、起動時のやり直しは、いずれも `continueImplementationOnBranch` を通るため、同じ本文組み立てである |
| 不具合修正のあと | マージリクエストの本文は書き直さない。会話コメントだけである。#29 と #28 のままである |
| `acceptanceProcedure` | 変えない。印の行は受け入れ手順の先頭の非空行のままである。作業の一覧は印より前なので、戻り値に含まれない |
| `defaultBranchFromSymref` | `src/cli.ts` から `src/git.ts` へ移し export する。`defaultBranchFromSymref(remote, cwd, gitRunner)` の形である。`cmdTasks` と `resolveWorkListLinesForPullRequest` が同じ関数を使う |

`formatWorkListLine(taskBody, shaOrNull)` は `src/runner.ts` に export する純関数である。`shaOrNull` が文字列のときは `- [x] ${taskBody} (${shortCommitHash(sha)})` である。`null` のときは `- [ ] ${taskBody}` である。`shortCommitHash` は `src/git.ts` に export する。

### 追加 runner REQ-955

もとになった課題は #175 である。

作業の一覧または対応するコミットを読み出せないときは、マージリクエストを作らず失敗する。理由は、設計に作業の一覧が無いとき `設計に作業の一覧がありません`、作業が無いとき `作業の一覧に作業がありません`、リモートを特定できないとき `リモートを特定できません`、デフォルトブランチを特定できないとき `デフォルトブランチを特定できません`、git の終了コードが 0 でないとき `failReason` の一行、git を起動できないとき `git を実行できません`、デフォルトブランチ先端の `ls-remote` が SHA を返さないとき `git が失敗しました` である。作業の一覧を省略して URL と印と手順だけでマージリクエストを作ることはしない。

- シナリオ: 条件: 設計に作業の一覧が無い 主体: 課題ランナー 結果: `createPullRequest` を呼ばず `設計に作業の一覧がありません` で止まる
