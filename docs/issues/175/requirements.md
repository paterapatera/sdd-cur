# 175 マージリクエスト本文に作業の一覧とコミットを載せる

<!-- sdd-cur:form -->

対象は [Issue #175](https://github.com/paterapatera/sdd-cur/issues/175)。課題ランナーが作るマージリクエストの本文は、課題の URL、印 `sdd-cur: 受け入れ手順`、受け入れ手順の順である。マージリクエストを見る人は、設計の作業の一覧のどれが、どのコミットで入ったかが分からない。

本文の並びを、課題の URL、作業の一覧、印 `sdd-cur: 受け入れ手順`、受け入れ手順の順にする。印の行より後ろが現在の手順である規則は、この課題では変えない。課題の URL と、作業の一覧と、印のあいだに、空行も見出しも説明の行も入れない。

作業の一覧は、`sdd-cur tasks <番号>` が成功したときの `tasks` の各要素を、その配列の順に一行ずつ書く。作業の本文は、その要素の `line` から先頭の `- ` を除いた残りである。`line` に含まれる `[<番号>]` も、その残りに含まれる。対応するコミットが一つある行は、`- [x] ` のあとに作業の本文を続け、末尾に空白一つ、`(`、そのコミットの短いハッシュ、`)` をこの順で付ける。対応するコミットが無い行は、`- [ ] ` のあとに作業の本文を続け、作業の本文より後ろに文字を付けない。コミットは、#173 の `Sdd-Cur-Task` のトレーラーで、`done` を真にするのと同じ範囲から探す。マージリクエストを作る時点では、すべての作業に対応するコミットがあることが想定である。`[ ]` の行が残っても、マージリクエストは作る。その作業が残っていることは、その行で見て分かる。

短いハッシュは、そのコミットの全文のハッシュの先頭 7 文字を、十六進の小文字で書いたものである。桁は常に 7 である。同じ作業番号の `Sdd-Cur-Task` を持つコミットが、その範囲に二つ以上あるときは、最も新しい一件のハッシュだけを書く。最も新しい一件は、`branchOnlyCommitShas` が返す SHA の並びで、その作業番号の `Sdd-Cur-Task` の行がある最初の SHA である。この並びは、`rev-list` の標準出力の非空行の順である。作業の一覧または対応するコミットを読み出せないときは、マージリクエストを作らず、失敗で止まる。失敗の理由は、その読み出しが既に返す理由をそのまま使う。読み出せないとは、設計に作業の一覧が無いこと、作業の一覧に作業が無いこと、リモートを特定できないこと、デフォルトブランチを特定できないこと、git が失敗すること、のいずれかである。

不具合の修正（`sdd-cur-fix`）のあとに本文を書き直すかは、この要件では決めない。設計が決める。

重なる課題は #173（作業ごとのコミット。この課題の前提）である。比べる相手は、Spec Kit の `tasks.md` である。`tasks.md` は、チェックボックスで進み具合を見せる。

手を入れる対象は、`src/runner.ts`（`pullRequestBody`、`runImplementation`）、`src/git.ts`、`skills/sdd-cur/conventions.md`（「マージリクエストの本文」）、`docs/canonical/runner.md`、`docs/canonical/conventions.md` である。

## 決定

不具合の修正（`sdd-cur-fix`）のあとにマージリクエストの本文を書き直すかは、この要件では決めない。設計が決める。

作業行の末尾に付ける短いハッシュは、常に 7 桁の十六進小文字である。そのコミットの全文のハッシュの先頭 7 文字を、十六進の小文字で書いたものである。`git rev-parse --short` と同じく一意になるまで伸びる省略は、採用しない。

同じ作業番号の `Sdd-Cur-Task` を持つコミットが、受け入れ条件 10 の範囲に二つ以上あるときは、そのうち最も新しい一件の短いハッシュだけを書く。最も新しい一件は、`branchOnlyCommitShas` が返す SHA の並びで、その作業番号の `Sdd-Cur-Task` の行がある最初の SHA である。この並びは、`rev-list` の標準出力の非空行の順である。末尾の形は、受け入れ条件 3 と同じである。

コミッター日時で最も新しい SHA は、採用しない。

作業の一覧または対応するコミットを読み出せないときは、マージリクエストを作らず、失敗で止まる。読み出せないとは、設計に作業の一覧が無いこと、作業の一覧に作業が無いこと、リモートを特定できないこと、デフォルトブランチを特定できないこと、git が失敗すること、のいずれかである。失敗の理由は、その読み出しが既に返す理由をそのまま使う。設計に作業の一覧が無いときの理由は `設計に作業の一覧がありません` である。作業の一覧に作業が無いときの理由は `作業の一覧に作業がありません` である。リモートを特定できないときの理由は `リモートを特定できません` である。デフォルトブランチを特定できないときの理由は `デフォルトブランチを特定できません` である。git の終了コードが 0 でないときの理由は、標準エラーの前後の空白を除いた最初の非空行であり、それが無いときは標準出力の前後の空白を除いた最初の非空行であり、どちらも無いときは `git が失敗しました` である。デフォルトブランチの先端を求める `ls-remote` の終了コードが 0 で SHA が無いときの理由は `git が失敗しました` である。git を起動できないときの理由は `git を実行できません` である。作業の一覧を書かず、課題の URL、印 `sdd-cur: 受け入れ手順`、受け入れ手順だけでマージリクエストを作ることは、採用しない。

この失敗専用の日本語一行に統一することは、採用しない。
