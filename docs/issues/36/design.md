# 36 要求レビューで一意・検証可能・無矛盾を見る

対象は [Issue #36](https://github.com/paterapatera/sdd-cur/issues/36)。要求レビューは、一つの要求が一通りに読め、確かめられ、集まりとして矛盾も未決も無いことを不合格の理由にする。確認コメントの本文は、決められない点を一度に一つにする。

## 受け入れ条件

- 要求レビュー役は、一つの要求が一通りに読めないとき、指摘し、`判定: 不合格` とする。
- 一通りに読めない要求とは、義務を二つ以上含む要求、または二通り以上に読める要求である。
- 要求レビュー役は、一つの要求が確かめられないとき、指摘し、`判定: 不合格` とする。
- 確かめられる要求とは、満たされたか満たされていないかを、その要求に書いてある結果で判定できる要求である。
- 要求レビュー役は、要求の集まりに矛盾があるとき、指摘し、`判定: 不合格` とする。
- 矛盾とは、集まりの中の要求が同時に満たせないことである。
- 要求レビュー役は、要求の集まりに未決が残っているとき、指摘し、`判定: 不合格` とする。
- 未決とは、集まりの中に、まだ一つの結果へ決まっていない点があることである。
- 矛盾と未決を見る集まりは、レビューしている一つの要求ファイルに書いた要求である。
- 要求レビュー役は、見出し、範囲、人が決めた条件、スコアの書き込みに関する従来の指摘を、引き続き指摘する。
- 未決のうち、課題、計画、人が決めた条件から読める結果があるときは、その結果に直す差分を書く。
- 未決のうち、課題、計画、人が決めた条件から読めないときは、差分で結果を決めず、`確認: あり` とする。
- 複数の義務を分けるとき、分けたあとの各文は、課題、計画、人が決めた条件にある義務だけである。分離や差分の提案に、新しい挙動を足さない。
- 受け入れ条件の一つの箇条に、サブエージェント四つ、配置、レビュー、修正案、人に確認しないことまでが入っている形は、義務を二つ以上含む要求として指摘する。
- `skills/sdd-cur/SKILL.md` の確認手順は、要件の「確認」節のとおりである。
- SDD スキルが確認を投稿するとき、決められない点は payload に一つだけ入れる。一つの本文に決定を二つ以上書かない。本文にスコアを書かない。複数の決定とスコアを一つの本文にまとめた確認は、投稿しない。
- 確認コメントの本文の形は、要件への確認と設計への確認で同じである。
- `bun test` は `gh` を起動しない。ホームディレクトリと、実行中の Cursor のスキルおよびサブエージェントは触らない。

### 指摘にするもの

「指摘にするもの」の箇条に、次を足す。既存の箇条は残す。

- 一つの要求が、義務を二つ以上含む。
- 一つの要求が、二通り以上に読める。
- 一つの要求が、満たされたか満たされていないかを、その要求に書いてある結果で判定できない。
- 要求どうしが、同時に満たせない。
- 要求の集まりに、まだ一つの結果へ決まっていない点が残っている。

直後に、次の一文を置く。集まりは、レビューしている一つの要求ファイルに書いた要求である。

次に、次の段落を足す。

- 受け入れ条件の一つの箇条に、サブエージェント四つ、配置、レビュー、修正案、人に確認しないことまでが入っている形は、義務を二つ以上含む要求である。この形は指摘する。
- 未決のうち、課題、計画、人が決めた条件から読める結果があるときは、その結果に直す差分を書く。
- 未決のうち、課題、計画、人が決めた条件から読めないときは、差分で結果を決めず、`確認: あり` とする。
- 複数の義務を分けるとき、分けたあとの各文は、課題、計画、人が決めた条件にある義務だけである。分離や差分の提案に、新しい挙動を足さない。

好み、文体だけの提案、課題に無い仕組みの追加案は、指摘にしない。という既存の一文は残す。

### 出力

設計 30 の「出力」節と同じ四項目である。差分は変える部分だけ。全文は書かない。質問のスコアは書かない。E1、E2、E3 は、人が決めた条件にあるときだけ 1 行を残す。

## スキルの手順

`skills/sdd-cur/SKILL.md` の「確認」だけを、次に合わせる。要件の「確認」節と一文字も違わない意味にする。

- 課題、計画、既存の回答から決められない点だけを payload にする。決められない点は仕様ファイルへ書かない。
- 本文が扱う決められない点は、一つである。その一つの点に選択肢があっても、点は一つである。別の点は、別の確認コメントにする。
- 一つの本文に、決定を二つ以上書かない。本文にスコアを書かない。`[スコア ` で始まる行も書かない。
- 複数の決定とスコアを一つの本文にまとめた確認は、投稿しない。
- 本文の形は、要件への確認と設計への確認で同じである。
- `show` の `nextAnswer` が `null` でないときは投稿しない。`unanswered` が空でないときは、いちばん古い未回答の payload を見せ、未回答の確認があるあいだ、次の確認は投稿しない。まだ要求または設計へ反映していない回答があるあいだも、次の確認は投稿しない。
- どちらのゲートも通過したときだけ、payload を人に見せ、人がその本文を承認したあとだけ `bun src/cli.ts confirm <番号>` を実行する。人が直したときは、直した文字列を改めて見せ、その文字列の承認があるまで `confirm` を実行しない。標準入力は承認された payload だけであり、印の行は入れない。
- 決められない点が複数あるときは、一点ずつ payload を分け、上の手順を繰り返す。一つの `confirm` にまとめない。

「要件」に書いてある、確認の手順に入る前の `show`、payload の承認、`confirm` の実行タイミング、印の行を入れない、は残す。
