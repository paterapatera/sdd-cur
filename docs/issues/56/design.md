# 56 軽微な修正は人を通さずに仕様作成から実装まで進める quick を作る

対象は [Issue #56](https://github.com/paterapatera/sdd-cur/issues/56)。軽微な修正について、人の確認を挟まずに、要件と設計の作成から実装までを一続きで進める quick を作る。

要求の決定どおり、quick の主起動は `run` の poll である。対象は、課題を作った人が課題本文またはラベルで「quick 対象」と明示し、開いていて、業務ラベルが無く、ランナー自身にアサインされた課題である。人のスキル依頼では始めない。Project A は使わない。

## 受け入れ条件

- 課題本文に `quick 対象` という連続した文字列がある、またはラベル名が `quick 対象` と完全一致する課題だけを、quick の対象にする。どちらも無い課題は対象にしない。題だけでは対象にしない。
- quick を選ぶのは `run` の poll である。`skills/sdd-cur/SKILL.md` の着手、要件、設計は、この quick を始めない。
- poll が返す仕事は一つである。種類の優先順は、実装依頼、不具合修正、quick、動作確認OK（完了処理）である。先の種類が一件でもあるときは、後の種類を探さない。
- quick の候補は、開いていて、業務ラベルが一つも無く、`gh` でログインしている利用者が assignees に含まれ、上の明示がある課題である。複数あるときは、課題番号の昇順でいちばん小さい番号を一件取る。
- 対象の課題は、途中で軽微でないと分かったときと、決められない点が出たときを除き、採点付きの質問と確認コメントを挟まずに、要件、設計、実装まで進み、「実装完了」で終わる。
- 要件と設計のパスは `docs/issues/<番号>/requirements.md` と `docs/issues/<番号>/design.md` である。作成、レビュー、修正の段は、今の要求と設計の段と同じである。
- 作業はランナーのクローンだけで行う。作業ブランチ `task-<番号>` をそのクローン上で用意する。要件、設計、実装、push は、そのクローンのそのブランチで行う。
- quick の着手では、「実装中」だけを付ける。「実装依頼」は付けない。外さない。
- 途中で軽微でないと分かったときは、止める。課題コメントで状況を伝える。そのあとラベルを変えない。
- 決められない点が出たときは、推測で仕様へ書かず、止め、課題コメントで状況を伝える。設計、実装、push、「実装完了」へ進まない。
- 実装のあと、受け入れ手順のコメントを書き、「実装中」を外し、「実装完了」を付ける。課題は閉じない。

## 範囲外

次は作らない。

- 課題の作成とクローズ。`issue close` と `--state` は付けない
- 受け入れテストと「動作確認OK」。人が行うまま
- 完了処理（スカッシュマージと「マージ済み」）
- 軽微な修正以外の課題について、今の要件、設計、実装の流れを変えること
- `skills/sdd-cur/SKILL.md` と `skills/sdd-cur-implement/SKILL.md` の手順の変更
- `agents/` の本文と frontmatter の変更
- 業務ラベルの追加と、`workflowLabels` の変更。「quick 対象」を `ensureWorkflowLabels` で作ること
- 確認、回答、受け入れ手順の印の変更。`src/conventions.ts` の変更
- `src/run.ts` のループの形。`src/cli.ts` に quick 用のサブコマンドを足すこと
- `src/git.ts` と `src/github.ts` の関数の追加。`createBranch` を quick から呼ぶこと
- `candidateViews` の条件の変更。quick の課題を着手候補から除くこと
- レビュー回数の新しい上限。実装の 10 回打ち切りの数を変えること
- 軽微でないことを、行数、ファイル数、変更の種類で判定すること
- 失敗したラベルの戻し、作業ツリーの復元。`--force` の push
- ロック。オープンな課題の 101 件目以降。`listIssues` の続きは取らない
- `docs/conventions.md`、README、AGENTS.md、この課題以外の `design.md` と `requirements.md` の書き換え
- Forgejo、Jira、Backlog
- 依存パッケージ。`package.json` の変更

## 関係する課題

### #41 承認の前に副作用を出さない

quick 対象の明示が無く、または poll の条件を満たさない課題には、ラベル、ブランチ、仕様ファイル、コメント、コミット、push、マージリクエストを出さない。process の先頭で条件を満たさなくなっていたときも、同じである。

確認コメントは投稿しない。採点付きの質問はしない。payload の承認を待って `confirm` する段は無い。

push、マージリクエスト、受け入れ手順、「実装完了」は、要件と設計と実装がどちらの止まりにも入らず終わったときだけ行う。

止まりの課題コメントは、要求が求める状況の伝達である。最初の非空行は、確認、回答、受け入れ手順の印にしない。

### #45 レビューの繰り返しの上限

新しい上限は作らない。要件と設計は、今の `skills/sdd-cur/SKILL.md` と同じく、合格まで作成、レビュー、修正を繰り返す。実装は、今の実装スキルの、レビュー不合格 10 回の打ち切りのままである。この課題は、その回数も、要件と設計へ上限を足すことも、変えない。

quick で繰り返しを抜けるのは、合格、軽微でないという報告、決められない点、のどれかである。`確認: あり` で人を待って再開することはしない。

### #39 未決を残したまま進まない

決められない点は、仕様へ書かない。その点があるあいだ、次の段へ進まない。要求にそれがあるときは設計へ進まない。設計にそれがあるときは実装へ進まない。実装へ進んだあとも、push と「実装完了」へ進まない。

次を、決められない点とする。

- 要求作成が返した、質問する未記載
- 要求作成が返した、依存または保留のため質問しない未記載
- レビューの判定行より前が `確認: あり` であるとき。列挙された点
- レビューの最後の非空行が、合格と不合格のどちらでもないとき
- 設計作成が返した、決められない点
- `show` の `unanswered` が空でないとき、または `nextAnswer` が `null` でないとき

この止まりでは `confirm` を実行しない。未決を、人が答えるまで仕様の外に残して次へ進むことはしない。

## quick 対象

`src/sdd.ts` に次を足す。`candidateViews` は変えない。

```ts
export function isQuickTarget(issue: {
  body: string
  labels: readonly string[]
}): boolean
```

- ラベルのどれかが `quick 対象` と一文字も違わないとき、true。
- 本文に `quick 対象` という連続した文字列があるとき、true。前後の文は問わない。
- どちらでもないとき、false。大文字の `Quick` や、空白の無い `quick対象` は、この文字列ではない。
- 題は引数に取らない。

## poll と process

`src/runner.ts` に `selectQuickIssue` を足す。引数の配列は変えない。

```ts
export function selectQuickIssue(
  issues: readonly Issue[],
  login: string,
): Issue | null
```

残す課題は、次をすべて満たすものである。

- `state` が `open`
- assignees に `login` が含まれる
- ラベルに `workflowLabels` の名前が一つも無い
- `isQuickTarget` が true

残った配列を `number` の昇順で並べ、先頭を返す。空なら `null` である。

`poll` の順は、次である。先に仕事が返った時点で、後は呼ばない。

1. 今どおり、`labels: ["実装依頼"]` と assignee と limit 100 で `listIssues` し、`selectImplementationIssue` する。
2. 今どおり、`findFixWorkItem` で不具合修正を探す。
3. `state: "open"`、assignee、limit 100 で `listIssues` する。ラベルでは絞らない。`selectQuickIssue` の結果を返す。
4. `completionCaller` が `runner` のときだけ、今どおり「動作確認OK」を探す。それ以外は `null` である。quick は `completionCaller` では止まらない。

`WorkItem` に種類のフィールドは足さない。`id` は課題番号である。

`process` は、今の分岐の順を保ち、そのあいだに quick を入れる。

1. `id` が番号でなければ `番号が不正です`。
2. `getIssue`。
3. 「実装依頼」があり「実装中」が無いときは、今の `runImplementation` である。quick には入らない。
4. `issueHasFixLabels` のときは、今の不具合修正である。
5. 開いていて、業務ラベルが無く、assignees に `viewerLogin` が含まれ、`isQuickTarget` が true のときは、quick である。
6. `completionCaller` が `runner` であり「動作確認OK」があるときは、今の完了処理である。
7. どれでもないときは、何もせず戻る。

5 の判定は、着手の `editLabels` より前に行う。満たさないときは、ラベルも git も agent も呼ばない。

各外部呼び出しは、拒否したときその呼び出しだけをもう一度行う。二度目も拒否したときは、そこで止まり、それより後は呼ばない。成功した呼び出しはやり直さない。ラベルは戻さない。作業ツリーは戻さない。

## クローン上の quick

quick の `process` は、次の順で、拒否した時点より後は呼ばない。

1. `editLabels` で「実装中」だけを付ける。
2. `getDefaultBranch`。作業ブランチ名は `implementationBranch` の戻り値である。
3. リモートが一つでなければ `リモートを特定できません`。
4. そのリモートのデフォルトブランチを `fetch` する。`fetch` に渡す名前は、作業ブランチ名ではない。
5. `checkoutFetched` に作業ブランチ名を渡す。ローカルの作業ブランチは、その `FETCH_HEAD` になる。`createBranch` は呼ばない。
6. 結果ファイルを、受け入れ手順ファイルと同じ注入で作る。受け入れ手順のファイルとは別の呼び出しである。
7. `agent.quick` に、課題番号とその絶対パスを渡す。
8. 結果ファイルを読み、消す。読みが拒否したときも消す。`agent.quick` が二度拒否したときは、読まずに消し、状況コメントは書かない。
9. 結果が軽微でない、または決められない点のときは、下の「止まり」へ進み、戻る。
10. 結果が続行のときは、作業ツリーの要件と設計がどちらも ready であることを見る。ready でないときは、実装へ進まず、状況コメントも書かない。要件が missing なら `要件がありません`、invalid なら `要件の見出しが不正です`。設計が missing なら `設計がありません`、invalid なら `設計の見出しが不正です`。
11. 今の実装と同じく、別の手順ファイルを作り、`agent.implement` に番号とその絶対パスを渡す。
12. 手順ファイルを読み、`acceptanceComment` に通す。変更が無いときは `実装の変更がありません`。
13. メッセージ `feat: 課題 <番号> を実装する` で一件コミットする。要件、設計、実装は、この一件に入る。段のあいだではコミットしない。
14. そのリモートの作業ブランチへ push する。`--force` は付けない。
15. `createPullRequest`。`base` はデフォルトブランチ、`head` は作業ブランチ、`title` は課題の題、`body` は課題の `url` である。`Fixes` と `Closes` は足さない。
16. `addComment` に、受け入れ手順のコメントを渡す。
17. `editLabels` で「実装中」を外し、「実装完了」を付ける。課題は閉じない。

11 から 17 は、今の `runImplementation` の、着手ラベルと `fetch` と `checkoutFetched` を除いた終わりである。quick は、実装の前に作業ブランチを取り直さない。

「実装中」が付いたあとの仕様の段は、業務ラベルがあることを理由に止まらない。止まる理由は、軽微でないこと、決められない点、agent の失敗、だけである。

## 止まり

どちらの止まりも、課題コメントを一件投稿して process から戻る。`run` のループは失敗にしない。コミット、push、マージリクエスト、受け入れ手順、「実装完了」は行わない。「実装中」を外さない。他のラベルも変えない。課題は閉じない。

軽微でないときの本文の最初の非空行は、次と一文字も違わない。

```
処理の途中で軽微な修正でないと分かりました
```

結果ファイルの 2 行目以降があれば、改行のあとに続ける。

決められない点のときの本文の最初の非空行は、次と一文字も違わない。

```
決められない点があるため止めました
```

結果ファイルの 2 行目以降を、改行のあとに続ける。点が空でも、この一行で投稿し、次の段へは進まない。

どちらの本文も、最初の非空行を確認、回答、受け入れ手順の印にしない。

## スキル

`skills/sdd-cur-quick/SKILL.md` を新しく作る。ランナーが、クローンの作業ツリーで `agent` から起動する。人の依頼では始めない。`install` は、直下のディレクトリをコピーする今の手順のまま、このスキルもコピーする。`src/install.ts` は変えない。

フロントマターは、次である。

```
---
name: sdd-cur-quick
description: クローンの作業ツリーで、quick 対象の課題の要件と設計を、人への質問と確認コメントなしで書く。課題ランナーが agent から起動する。
disable-model-invocation: true
---
```

プロンプトのスキル名のあとにある課題番号と、結果ファイルの絶対パスを使う。親は仕様ファイルを自分では書かない。書くのは、要求と設計の作成役と修正役だけである。

先に `bun src/cli.ts show <番号>` を実行する。`gh` は直接起動しない。

`unanswered` が空でないとき、および `nextAnswer` が `null` でないときは、結果ファイルの最初の非空行を `決められない` にし、分かっている点を 2 行目以降に書き、成功で終える。仕様は書かない。確認コメントは投稿しない。

それ以外のとき、要件の段に入る。サブエージェントは `sdd-cur-req-author`、`sdd-cur-req-reviewer`、`sdd-cur-req-fixer` の名前で起動する。作成と修正に model は渡さない。frontmatter の `model` を使う。

段の形は、今の `skills/sdd-cur/SKILL.md` の「要件」と同じである。違いは、次だけである。

- Cursor の質問機能は使わない。採点付きの選択肢は出さない。
- 質問する未記載、および質問しない未記載があるときは、レビューに入る前に止まる。結果は `決められない` である。その点を要求へ書かない。
- レビューの `確認: あり` では、人に見せて再開しない。結果は `決められない` であり、列挙された点を 2 行目以降に書く。修正は起動しない。`confirm` は実行しない。
- 最後の非空行が合格と不合格のどちらでもないとき、および不合格なのに確認の行が二択のどちらでもないときは、結果は `決められない` である。
- 作成役または修正役が、この課題は軽微な修正ではないと返し、仕様へ書かなかったときは、結果は `軽微でない` である。行数、ファイル数、変更の種類では判定しない。quick スキルは、作成役と修正役を起動するとき、軽微な修正でないと分かったときは仕様へ書かず親へ返すよう渡す。`agents/` のファイルは変えない。その判断を、この返し以外の基準では足さない。
- 業務ラベルが「実装中」であることは、この段を止める理由にしない。
- 業務ラベルが「実装中」であることは、要求作成役を起動しない理由にしない。起動は、作業ブランチの用意とその比較を条件にしない。
- 作業ブランチは用意しない。Project A は使わない。要件は、ランナーが用意したクローンの作業ツリーに書く。デフォルトブランチには書かない。
- 合格のとき、人へ「設計に進める」と伝えて終わらない。同じ agent の起動の中で、設計の段へ進む。
- ファイルを書かず、上の止まりでもないときは、成功で終えない。理由は `要求を書いていません` である。

設計の段のサブエージェントは `sdd-cur-design-author`、`sdd-cur-design-reviewer`、`sdd-cur-design-fixer` である。作成と修正に model は渡さない。回数、モデル、`確認: なし` の修正、合格まで繰り返すことは、要件の段と同じである。作業ブランチは、要求のときにランナーが用意した同じブランチである。デフォルトブランチから作り直さない。

設計の段の違いは、次だけである。

- 質問と確認コメントは、要件の段と同じくしない。
- 人の設計の依頼は待たない。
- 業務ラベルが「実装中」であることは、この段を止める理由にしない。設計作成役を起動しない理由にしない。起動は、作業ブランチの比較を条件にしない。
- 作業ブランチは用意しない。Project A は使わない。設計は、ランナーが用意したクローンの作業ツリーに書く。デフォルトブランチには書かない。
- 設計作成が返した決められない点、`確認: あり`、判定が二択でないときは、結果は `決められない` である。実装の依頼はしない。
- 軽微な修正ではないと返したときは、結果は `軽微でない` である。
- 要件が ready でないときは、設計のサブエージェントを起動しない。成功で終えない。
- ファイルを書かず、上の止まりでもないときは、成功で終えない。理由は `設計を書いていません` である。
- 合格のとき、人へ「実装依頼に進める」と伝えて終わらない。「実装依頼」は付けない。push しない。結果ファイルの最初の非空行を `続行` にし、成功で終える。

レビューの指摘は、ファイルにも課題コメントにも残さない。数えるレビューは、ファイルを書いたあとの最初と、修正のあとである。開始時の連続不合格は 0 である。1 回目と 2 回目は model を渡さない。1 回目と 2 回目が続けて不合格のとき、3 回目から model に `grok-4.7-high` を渡す。合格まで渡す。medium には戻さない。`確認: あり` で止まるときは、回数を増やしたあとでも修正も再レビューもしない。

実装のサブエージェントは、このスキルから起動しない。コミットしない。push しない。マージリクエストを作らない。ラベルを変えない。課題を作らない。課題を閉じない。受け入れ手順を投稿しない。完了処理をしない。

失敗で終えるとき、終了コードは 0 以外である。理由は日本語の一行であり、標準エラーの最初の非空行、それが空のときは標準出力の最初の非空行に書く。軽微でないときと、決められない点のときは、失敗にせず、結果ファイルを書いて成功で終える。
