# 28 動作確認の不具合を PR のコメントに書くとランナーが修正する

対象は [Issue #28](https://github.com/paterapatera/sdd-cur/issues/28)。動作確認で不具合を見つけたとき、その内容をマージリクエストのコメントに書くと、課題ランナーが修正する。

現状、受け入れで不合格になったときのラベルと、誰が直すかは未決である。参照は、計画の未決の 1 項目目と #13 である。この要件は、その未決の 1 項目目を解消する。

## 受け入れ条件

- 修正のきっかけは、人がマージリクエストの会話コメントに書いた不具合である。人は、修正のためにラベルを付けない。
- 課題ランナーの `poll` の優先順は、次である。(1) 実装依頼。(2) 未処理の不具合。(3) 動作確認OK。 (3) は、`sdd-cur.completion` が `runner` のときだけであり、既存の完了の探索と同じである。(2) は、完了の呼び出し元が `runner` であるかどうかにかかわらず探す。
- 不具合の探索対象は、自身がアサインされた課題だけである。自身は、`gh` でログインしている利用者である。条件は、ラベルに「実装完了」があり、「実装中」が無く、「動作確認OK」が無く、「マージ済み」が無いことである。
- 未処理の不具合がある課題が複数あるときは、課題番号の昇順で、いちばん小さい番号の課題を 1 件だけ着手する。実装依頼の探索と同型である。
- head が `task-<番号>` のマージリクエストが 0 件のときは、その課題をスキップする。2 件以上のときは、完了処理が 2 件以上を拒否するのと同型でエラーとし、`run` を停止する。1 件で open のときだけ、そのマージリクエストの会話コメントを読む。
- そのマージリクエストが merged または closed であり、open でないときは、不具合修正の対象外である。その課題はスキップし、他の課題を探す。
- 不具合コメントの印は `sdd-cur: 不具合` である。最初の非空行が印と一文字も違わないとき、その種別である。印より後ろが本文である。1 コメントに複数の不具合を書いてよい。判定は、`src/conventions.ts` の課題コメントの印と同じ規則である。
- 未処理とは、どの修正コメントの fixed ブロックにも、その不具合コメントの id が無いことである。着手のときに未処理である不具合を、一度に処理する。
- 修正が終わったら、ランナーはマージリクエストの会話コメントを 1 つ書く。最初の非空行は `sdd-cur: 修正` である。末尾の fixed ブロックに、今回処理した不具合コメントの id を記録する。形は、回答の反映済みの記録と同じであり、印は `sdd-cur:fixed` である。
- 新しいラベルは作らない。修正の開始で「実装完了」を外し「実装中」を付ける。終了で「実装中」を外し「実装完了」を付ける。
- 修正は、その課題の要件と設計の範囲内だけである。設計に無い挙動は直さない。範囲外の指摘は、修正コメントの本文に「設計の範囲外のため直していない」と理由を 1 行書く。直さなかった不具合の id も fixed に記録する。ラベルは「実装完了」に戻す。
- すべて範囲外であり、コミットが無いときは、失敗にしない。範囲内の指摘があるのに作業ツリーの変更が無いときは、`実装の変更がありません` で失敗する。この失敗のときは、修正コメントを書かず、ラベルは「実装中」のままである。
- 課題の受け入れ手順コメント（`sdd-cur: 受け入れ手順`）は書き直さない。再確認の手順は、修正コメントの本文に書く。
- 読むコメントと書くコメントは、マージリクエストの会話コメントだけである。
- 範囲内の変更は、`task-<番号>` に、メッセージ `fix: 課題 <番号> の不具合を修正する` でコミットし、そのマージリクエストに載せる。
- 修正のスキルは新しく `skills/sdd-cur-fix/` に置く。ランナーは、不具合の本文と、結果を書く一時ファイルを agent に渡す。一時ファイルの扱いは、受け入れ手順の一時ファイルと同じである。
- `docs/plan.md` の未決の 1 項目目を、不合格のときは人がマージリクエストに不具合を書き、課題ランナーが直す、という内容で解消する。ラベルは「実装中」にしてから「実装完了」に戻す。

## 決定

修正のきっかけは、人がマージリクエストの会話コメントに書いた不具合である。人は、修正のためにラベルを付けない。

課題ランナーの `poll` は、仕事を一つ返す。優先順は、次である。

1. 実装依頼。探索の条件は、これまでの実装依頼の探索と同じである。
2. 未処理の不具合。
3. 動作確認OK。 `sdd-cur.completion` が `runner` のときだけ探す。探し方は、既存の完了の探索と同じである。`runner` でないときは、この探索をしない。

2 は、完了の呼び出し元にかかわらず探す。1 に該当する課題があるときは、2 と 3 を探さない。処理のあいだは、次の `poll` を呼ばない。

不具合の探索対象は、自身がアサインされた課題だけである。自身は、`gh` でログインしている利用者である。GitHub Issue の assignees に、その利用者が含まれる課題だけを対象にする。

ラベルの条件は、次のすべてである。

- 「実装完了」がある
- 「実装中」が無い
- 「動作確認OK」が無い
- 「マージ済み」が無い

ラベル条件を満たす課題は、課題番号の昇順で見る。未処理の不具合がある課題が複数あるときは、いちばん小さい番号の課題を 1 件だけ着手する。実装依頼の探索と同型である。

`<番号>` は課題番号の十進であり、先頭の零は付けない。ブランチ名は `task-<番号>` のままである。head が `task-<番号>` のマージリクエストの件数は、完了処理が数えるときと同じである。

- 0 件のときは、その課題をスキップし、次の番号の課題を見る。
- 2 件以上のときは、完了処理が 2 件以上のマージリクエストを拒否するのと同型でエラーとする。理由は `マージリクエストを特定できません` である。`run` はそこで停止する。次の課題は見ない。
- 1 件で、状態が open のときだけ、そのマージリクエストの会話コメントを読む。未処理の不具合があるときは、その課題を着手する。未処理が無いときは、その課題をスキップし、次の番号の課題を見る。
- 1 件で、状態が merged または closed であり、open でないときは、不具合修正の対象外である。その課題はスキップし、他の課題を探す。

会話コメントを読むのは、open のマージリクエストが 1 件の課題だけである。スキップが続いたあと、未処理の不具合がある課題が残らなければ、不具合の仕事は無い。

不具合の印は `sdd-cur: 不具合` である。`docs/conventions.md` に、この種別を足す。最初の非空行が印と一文字も違わないとき、その種別である。印の行に、印以外の文字があるときは、種別は付かない。印より後ろが本文である。1 コメントに複数の不具合を書いてよい。判定の実装は `src/conventions.ts` であり、課題コメントの印と同じ規則である。

処理済みは、修正コメントで記録する。修正コメントの印は `sdd-cur: 修正` である。この印も、最初の非空行が印と一文字も違わないとき、その種別である。約束に、この印と fixed の記録を含める。

修正が終わったら、ランナーはマージリクエストの会話コメントを 1 つ書く。末尾に、今回処理した不具合コメントの id を記録する。形は、回答の反映済みの記録と同じである。印だけが `sdd-cur:fixed` である。

記録の例:

```
<!-- sdd-cur:fixed
IC_kwDOExample123
-->
```

id は、不具合の会話コメントの id である。処理の単位は、コメントの id である。どの修正コメントの fixed ブロックにも id が無い不具合コメントが、未処理である。着手のときに未処理であるものを、一度の修正でまとめて処理する。その一度で書いた修正コメントの fixed に、その id をすべて記録する。

新しいラベルは作らない。使うのは、既存の「実装中」と「実装完了」である。修正の開始で「実装完了」を外し「実装中」を付ける。終了で「実装中」を外し「実装完了」を付ける。「実装中」の課題は、他のクローンの探索から外れる。

修正する範囲は、その課題の要件と設計の範囲内だけである。設計に無い挙動は直さない。範囲外の指摘は、修正コメントの本文に「設計の範囲外のため直していない」と理由を 1 行書く。直さなかった不具合の id も、fixed に記録する。ラベルは「実装完了」に戻す。すべて範囲外であり、コミットが無いときは、失敗にしない。

範囲内の指摘があるのに、作業ツリーの変更が無いときは、`実装の変更がありません` で失敗する。この失敗のときは、修正コメントを書かず、ラベルは「実装中」のままである。

範囲外の指摘を直すときは、人が Project A で設計を直し、push し、不具合を改めて投稿する。改めて投稿したコメントは、新しい id を持つ。その id がどの fixed にも無ければ、未処理である。

課題の受け入れ手順コメントは書き直さない。印は `sdd-cur: 受け入れ手順` のままである。範囲内を直したときの再確認の手順は、修正コメントの本文に書く。

対象にするマージリクエストのコメントは、会話コメントだけである。取得は `gh pr view --json comments` のコメントである。`github.ts` に、この会話コメントの取得を足す。修正コメントの投稿も、課題のコメントではなく、マージリクエストの会話コメントとして行う。

範囲内の変更は、その課題の `task-<番号>` にコミットし、そのマージリクエストに載せる。コミットメッセージは `fix: 課題 <番号> の不具合を修正する` である。新しいブランチは作らない。新しいマージリクエストは作らない。スカッシュマージはしない。課題は閉じない。

修正のスキルは、`skills/sdd-cur-fix/` に新しく置く。エージェントも置く。実装のサブエージェントを、そのエージェントとして流用してよい。`install` は、他のスキルと同じ規則で、このスキルとエージェントをコピーする。

ランナーは、未処理の不具合コメントの本文と、結果を書く一時ファイルを、修正の agent に渡す。一時ファイルの扱いは、受け入れ手順の一時ファイルと同じである。agent は、結果の本文をそのファイルに書く。ランナーはそれを読み、印と fixed ブロックを付けて投稿する。

`sdd-cur-implement` に入力を足す方式は採用しない。

Project A の Cursor で不具合を直す経路は採用しない。

## 対象

課題ランナーが、クローン上の `run` で、動作確認の不具合を直す。不具合は、人がマージリクエストの会話コメントに書く。ランナーは、アサインされた「実装完了」の課題から、未処理の不具合を探し、`task-<番号>` の上で要件と設計の範囲内を直す。

直したあとは、修正コメントで再確認の手順と、処理した不具合の id を残し、ラベルを「実装完了」に戻す。受け入れテストのあいだ、マージリクエストは開いたままである。

`docs/conventions.md` と `src/conventions.ts` に、不具合と修正の印、および fixed の記録を足す。確認、回答、受け入れ手順は、これまでどおり課題のコメントだけである。不具合と修正は、マージリクエストの会話コメントである。

`docs/plan.md` の未決の 1 項目目を解消する。不合格のときは、人がマージリクエストに不具合を書き、課題ランナーが直す。ラベルは「実装完了」を外して「実装中」にし、修正が終わったら「実装完了」に戻す。Project A の Cursor で直す経路は、計画に書かない。未決の 2 項目目は残す。業務フローの合格側、つまり「動作確認OK」と完了処理は、変えない。課題ランナーの役割に、この不具合の修正を含める。

## 範囲外

次は、この要件に含めない。

- 「実装依頼」から最初の「実装完了」までの手順の詳細。受け入れ手順コメントの初回の投稿（#6）
- 完了処理。スカッシュマージと「マージ済み」（#7）
- 受け入れ手順の置き場を変えること（#29）
- Project A の Cursor で不具合を直すこと
- #13 を閉じること。閉じるかどうかは、人が判断する
- レビューコメントと、レビュー本文
- 新しいラベルを作ること
- 「動作確認OK」を付けること。付けるのは人である
- 課題の作成とクローズ
- 計画の未決の 2 項目目。完了処理を、課題ランナーと Cursor のどちらから呼ぶか
- 確認と回答の規則を変えること
- ブランチ名を変えること。名前は `task-<番号>` のままである（#17）
- `sdd-cur-implement` に入力を足すこと
- Forgejo、Jira、Backlog
