# 170 設計にデータモデル、インターフェース、図の任意の節を書けるようにする

<!-- sdd-cur:form -->

対象は [Issue #170](https://github.com/paterapatera/sdd-cur/issues/170)。印がある設計に、任意の節 `## データモデル`、`## インターフェース`、`## 図` を書けるようにする。節が無くても `validate` は失敗しない。節があるときだけ、本文が空でないことを確かめる。本文は、見出しの次の行から、行が `## ` で始まる次の行の直前までであり、空白と改行だけなら空である。出現する各節の本文をそれぞれ検査する。`## 図` があるときは、Mermaid の囲みコードブロックを一つ以上持つことを確かめる。本文が空であるときの違反は `節の本文が空です: <節名>` であり、節名はデータモデル、インターフェース、図である。囲みが無いときの違反は `図に Mermaid の囲みがありません` である。設計作成役は、課題がデータの形を足すか変えるとき `## データモデル` を書き、外から呼ばれる取り決めを足すか変えるとき `## インターフェース` を書き、三つ以上の部品の関係または処理の順を足すか変えるとき `## 図` を書く。いずれも足さず、変えないときは、その節を書かない。課題の大きさでは、節を書くかを判定しない。設計レビュー役は、三つの節が「決定」または受け入れ条件と、同じ事項について値、手順、有無が矛盾するとき指摘する。節にだけ詳細があることは食い違いにしない。書かれていないことだけでは不合格にしない。書く条件を満たさない節があることだけでは不合格にしない。

必須の節、印が無い設計を検査しないこと、曖昧な語の検査、受け入れ条件の形の検査は変えない。

重なる課題は #4 である。比べる相手は、Spec Kit の `/plan` と、cc-sdd の設計である。この課題が足すのは、設計ファイルの中の三つの任意の節である。

## 決定

印がある設計の `## データモデル`、`## インターフェース`、`## 図` の本文は、見出しの次の行から、行が `## ` で始まる次の行の直前までである。切り出しは、既存の `sectionBodies` と同じである。本文が空白と改行だけであるとき、その本文は空である。

同じ見出しが二つ以上あるときは、出現する各節の本文をそれぞれ検査する。どれか一つの本文が空なら、検査は失敗する。

本文が空であるときの違反は `節の本文が空です: <節名>` である。`<節名>` は、データモデル、インターフェース、図のいずれかである。`## 図` の本文に Mermaid の囲みが一つも無いときの違反は `図に Mermaid の囲みがありません` である。この文言は、既存の `必須の節がありません: ` に揃える。`## 図` の本文が空であるときは、`節の本文が空です: 図` と `図に Mermaid の囲みがありません` の両方がある。

Mermaid の囲みは、行全体がバッククォート三つの直後に `mermaid` を続けたものと一致する開始行で開き、行全体がバッククォート三つと一致する行で閉じたブロックを一つと数える。行頭の空白は無い。中身が空でも数える。

設計作成役は、データの形を足さず、変えないとき、`## データモデル` を書かない。外から呼ばれる取り決めを足さず、変えないとき、`## インターフェース` を書かない。三つ以上の部品の関係を足さず、変えないとき、かつ、処理の順を足さず、変えないとき、`## 図` を書かない。課題の大きさという別判定は採用しない。

設計作成役は、三つ以上の部品の関係を足すか変えるときに加え、処理の順を足すか変えるときも、`## 図` を書く。

設計レビュー役は、同じ事項について、値、手順、または有無が矛盾するとき指摘する。節にだけ詳細があることは、食い違いにしない。

設計レビュー役は、書く条件を満たさない節があることだけでは不合格にしない。任意節の過剰は指摘してもよい。この扱いは、節が書いていないことだけでは不合格にしないことと同じである。

REQ-857 は、「仕様の正本」と「要件と設計の形式」へシナリオの規則の文を足すこと、および「要件と設計の形式」へ受け入れ条件 17、受け入れ条件 18、受け入れ条件 41、受け入れ条件 42 で足す文を足すことを除き、配る節の既存の文を変えない、とする。

形式と `validate` の規則は、`docs/canonical/conventions.md` へ、行全体が `## REQ-<番号>` である新しい要求として足す。その規則の文と同じ文を、`skills/sdd-cur/conventions.md` の「要件と設計の形式」へ足す。設計作成役と設計レビュー役の手順は、`agents/sdd-cur-design-author.md` と `agents/sdd-cur-design-reviewer.md` に書く。`docs/canonical/sdd.md` にこの手順を書くことは採用しない。`docs/canonical/sdd.md` は変えない。

`docs/canonical/conventions.md` と `agents/` だけを変え、`skills/sdd-cur/conventions.md` の「要件と設計の形式」へ同じ文を足さないことは、採用しない。

## 範囲外

次は、この要件に含めない。

- 印がある設計の必須の節を増やすこと、または必須の節から外すこと
- 印が無い設計を検査すること
- 曖昧な語の検査を変えること
- 受け入れ条件の項目の形の検査を変えること
- 要件ファイルに、この三つの節の検査を足すこと
- 三つの節が無いことだけで、設計レビューを不合格にすること
- 書く条件を満たさない節があることだけで、設計レビューを不合格にすること
- 節にだけある詳細を、食い違いとして指摘すること
- 課題の大きさで、三つの節を書くかを判定すること
- `validate` が、三つの節の本文の意味を検査すること
- この三つのほかの節を、この課題で足すこと
- Spec Kit の `/plan` のように、`data-model.md`、`contracts/`、`research.md`、`quickstart.md` を別ファイルとして作ること
- #4 の、課題ごとのファイルの置き場所、コメント種別、未反映の回答の判定を変えること
- `docs/conventions.md` の「スキル、サブエージェント、テストの書き方」を変えること
- `docs/canonical/sdd.md` を変えること
