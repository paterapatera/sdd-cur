# 145 設計完了後に「実装依頼する」を選んでも未コミットで request が失敗する

<!-- sdd-cur:form -->

対象は [Issue #145](https://github.com/paterapatera/sdd-cur/issues/145)。#129 で設計の合格のあと「実装依頼する」を選ぶと SDD スキルは `sdd-cur request <番号>` を実行する。いまは、要件と設計を作業ブランチに書いた直後でも未コミットのままであるため、`request` が `未コミットの変更があります` で失敗し、push も「実装依頼」も行われない。`request` が、未コミットの変更がその課題の要件ファイルと設計ファイルだけであるとき、その二ファイルを一つのコミットにしてから、既存の確認と push とラベル付与に進むようにする。それ以外の未コミットではコミットしない。

## 現状

人が、作業ツリーで `bun src/cli.ts request <番号>` を実行すると、その課題番号の作業ブランチを push し、その push が成功したあと、その課題に「実装依頼」を付ける（`docs/canonical/git.md` の 283 行）。

`requestImplementation` は、今のブランチが `implementationBranch` の戻り値と一致しないとき `作業ブランチではありません` で拒否する（`src/request.ts` の 48 行）。続けて `hasChanges` が真のとき `未コミットの変更があります` で拒否する（`src/request.ts` の 53 行）。`openGitHub` 以降は呼ばない（`src/94.test.ts` の 214 行）。

正本は、作業ツリーに未コミットの変更があるときは、何も変えずに `未コミットの変更があります` で失敗する、と定める（`docs/canonical/git.md` の 307 行）。確認の順は、今のブランチ、未コミットの変更、課題の `state`、業務ラベル、要件の `specStatus`、設計の `specStatus`、リモート名、push、ラベル付与である（`docs/canonical/git.md` の 343 行）。

要件と設計のパスは `specPaths` が `docs/issues/<番号>/requirements.md` と `docs/issues/<番号>/design.md` を返す（`src/conventions.ts` の 92 行）。

SDD スキルは、要求作成役と修正役が `docs/issues/<番号>/requirements.md` を書き、設計作成役と修正役が `docs/issues/<番号>/design.md` を書く（`skills/sdd-cur/SKILL.md` の 460 行）。設計のレビューで `action` が `合格` のとき、設計を終える（`skills/sdd-cur/SKILL.md` の 283 行）。#129 のあと、設計の合格の案内で「実装依頼する」を選んだときは、スキルが `sdd-cur request <番号>` を実行する。いまの main の正本は、SDD スキルはこのコマンドを呼ばない、と定める（`docs/canonical/git.md` の 349 行）。

quick スキルはコミットしない、と定める（`skills/sdd-cur-quick/SKILL.md` の 161 行）。

`GitClient` は `commitAll` を持つ（`src/git.ts` の 22 行）。実装の課題ランナーは、実装のあと `commitAll` でコミットする（`src/runner.ts` の 772 行）。

## 決定

- `request` の確認の順は、今のブランチ、未コミットの変更、課題の `state`、業務ラベル、要件の `specStatus`、設計の `specStatus`、リモート名、push、ラベル付与である。未コミットの変更が受け入れ条件 1 の条件を満たすときだけ、その確認では失敗せず、仕様ファイルの自動コミットのあと課題の `state` の確認へ進む。それ以外で未コミットの変更があるときは、何も変えずに `未コミットの変更があります` で失敗する。先の確認が失敗したときは、後の確認とコミットと push とラベル付与はしない。
- 仕様ファイルの自動コミットは、今のブランチが作業ブランチ名と一致し、課題の `state` が `open` であり、業務ラベルが無く、要件と設計の `specStatus` がともに `ready` であり、未コミットの変更がその課題の `docs/issues/<番号>/requirements.md` と `docs/issues/<番号>/design.md` の差分だけであるときだけ行う。その二ファイルを一つのコミットに含める。コミットメッセージは `docs: 課題 <番号> の要件と設計` である。`<番号>` は引数の課題番号であり、十進で、先頭の零は付けない。差分が無いときはコミットを作らない。
- 仕様ファイルの自動コミットのあと、未コミットの変更があるときは、何も変えずに `未コミットの変更があります` で失敗する。
- SDD スキルは git のコミットを行わない。

## 受け入れ条件

- 1. 条件: 今のブランチが引数の課題番号の作業ブランチ名と一致し、課題の `state` が `open` であり、業務ラベルが無く、要件と設計の `specStatus` がともに `ready` であり、未コミットの変更が `docs/issues/<番号>/requirements.md` と `docs/issues/<番号>/design.md` の差分だけである 主体: `request` 結果: その二ファイルを一つのコミットに含めてコミットする
- 2. 条件: 受け入れ条件 1 のコミット 主体: `request` 結果: コミットメッセージは `docs: 課題 <番号> の要件と設計` と一文字も違わない。`<番号>` は引数の課題番号であり、十進で、先頭の零は付けない
- 3. 条件: 受け入れ条件 1 の直前に、二ファイルに差分が無く、他の未コミットの変更も無い 主体: `request` 結果: コミットを新しく作らない
- 4. 条件: 作業ブランチ上で、課題の `state` が `open` であり、業務ラベルが無く、要件と設計が `ready` であり、上の二ファイル以外に未コミットの変更がある 主体: `request` 結果: 何も変えずに `未コミットの変更があります` で失敗する
- 5. 条件: 要件または設計の `specStatus` が `ready` でない 主体: `request` 結果: 仕様用の自動コミットは行わない
- 6. 条件: 今のブランチが作業ブランチ名と一致しない 主体: `request` 結果: 何も変えずに `作業ブランチではありません` で失敗する
- 7. 条件: 設計の合格の案内で人が「実装依頼する」を選び、作業ブランチ上で要件と設計だけが未コミットである 主体: SDD スキル 結果: `sdd-cur request <番号>` を実行する
- 8. 条件: この要件の変更 主体: 正本 結果: `docs/canonical/git.md` の REQ-794、REQ-800、REQ-797、REQ-798 を、この要件の決定に合わせる差分を設計の「正本への差分」に書く
- 9. 条件: `src/94.test.ts` の `requestImplementation` のテスト 主体: テスト 結果: 受け入れ条件 1 から 6、および 10 から 13 をカバーする
- 10. 条件: 受け入れ条件 1 のコミットの直後、または受け入れ条件 3 のとおりコミットを作らなかった直後であり、未コミットの変更が無く、課題の `state` が `open` であり、業務ラベルが無く、要件と設計の `specStatus` が `ready` であり、リモート名の確認が成功した 主体: `request` 結果: 作業ブランチを push する
- 11. 条件: 受け入れ条件 10 の push が成功した 主体: `request` 結果: 「実装依頼」を付ける
- 12. 条件: 要件または設計の `specStatus` が `ready` でなく、未コミットの変更が無い 主体: `request` 結果: 何も変えずに、従来の `specStatus` 失敗と同じ message で失敗する
- 13. 条件: 要件または設計の `specStatus` が `ready` でなく、未コミットの変更がある 主体: `request` 結果: 何も変えずに `未コミットの変更があります` で失敗する
- 14. 条件: 受け入れ条件 7 のとおり `sdd-cur request <番号>` を実行する 主体: SDD スキル 結果: スキル自身は git のコミットを行わない

## 範囲外

- 実装コードや実装中の作業ツリーの自動コミット
- `request` 以外のサブコマンドでの仕様ファイルの自動コミット
- コミットメッセージを人が編集する UI
- 業務ラベル「実装中」が付いている課題での SDD スキルの挙動の変更
