# 201 設計に任意の節「検討した案」を書けるようにする

<!-- sdd-cur:form -->

対象は [Issue #201](https://github.com/paterapatera/sdd-cur/issues/201)。印がある設計に、任意の節 `## 検討した案` を書けるようにする。節が無くても `validate` は失敗しない。節があるときだけ、本文が空でないことを確かめる。設計作成役と設計レビュー役の手順を足す。

重なる課題は #170 である。比べる相手は、Spec Kit の `research.md` である。この課題が足すのは、設計ファイルの中の任意の節 `## 検討した案` である。

## 受け入れ条件

- 1. 条件: 印がある設計に、行全体が `## 検討した案` である行が無い 主体: `validate` 結果: この節が無いことを理由に、終了コードを 1 にしない
- 2. 条件: 節の有無を見る 主体: `validate` 結果: 行全体が `## 検討した案` と一致する行があるとき、その節がある
- 3. 条件: 印がある設計で、`## 検討した案` の本文を取る 主体: `validate` 結果: 本文は、見出しの次の行から、行が `## ` で始まる次の行の直前までである。切り出しは、既存の `sectionBodies` と同じである
- 4. 条件: 受け入れ条件 3 の本文が空白と改行だけである 主体: `validate` 結果: その本文は空である
- 5. 条件: 印がある設計に、行全体が `## 検討した案` である節があり、その本文が空である 主体: `validate` 結果: 終了コードは 1 であり、違反に `節の本文が空です: 検討した案` がある。この節を理由に `図に Mermaid の囲みがありません` を足さない
- 6. 条件: 印がある設計に、行全体が `## 検討した案` と一致する同じ見出しが二つ以上ある 主体: `validate` 結果: 出現する各節の本文をそれぞれ検査する。どれか一つの本文が空なら、終了コードは 1 である
- 7. 条件: 印がある設計に、行全体が `## 検討した案` である節があり、その本文が空でない 主体: `validate` 結果: 本文が空であることを理由に、終了コードを 1 にしない。項目の一行の記法を理由に、終了コードを 1 にしない

## 範囲外

次は、この設計に含めない。

- 印がある設計の必須の節を増やすこと、または必須の節から外すこと
- 印が無い設計を検査すること
- 節が無いことだけで、`validate` を失敗させること
- データモデル、インターフェース、図の検査を変えること
- 要件ファイルに、この節の検査を足すこと
- 項目の一行の記法を、`validate` が検査すること
- この節に、Mermaid の検査を足すこと
- 曖昧な語の検査を変えること
- 受け入れ条件の項目の形の検査を変えること
- Spec Kit の `research.md` のように、比べて退けた案の記録を別ファイルとして作ること
- #170 の、三つの任意の節の規則を変えること
- `docs/conventions.md` の「スキル、サブエージェント、テストの書き方」を変えること
- `docs/canonical/conventions.md` を変えること
- 「決定」に二つ以上の案を比べた結論があるのに `## 検討した案` が無いことだけで、設計レビューを不合格にすること
- 書く条件を満たさないのに `## 検討した案` があることだけで、設計レビューを不合格にすること
- 節にだけある詳細を、「決定」との食い違いとして指摘すること
- `src/cli.ts` を変えること

## 決定

任意の節の見出しは、行全体が `## 検討した案` と一致する行である。必須の節の一覧は変えない。データモデル、インターフェース、図の検査は変えない。

本文の切り出しは、既存の `sectionBodies` を使う。節名は `検討した案` である。同じ見出しが複数あるときは、`sectionBodies` が返す各本文を、それぞれ検査する。

本文が空かどうかは、切り出した文字列を、改行を `\n` にそろえたあと、前後の空白を除いた長さが 0 であるとき、空である。空白は、スペース、タブ、改行、復帰、全角スペースである。データモデルとインターフェースと同じ `isEmptyOptionalSectionBody` を使う。

本文が空のときの違反は `節の本文が空です: 検討した案` である。空の本文ごとに、その違反を一つ返す。図の Mermaid の検査は、この節には使わない。

`src/conventions.ts` の `BASIC_OPTIONAL_SECTIONS` の末尾に `"検討した案"` を足す。`collectOptionalBasicSectionViolations` は、配列の順に各節名を見る。`validateSpecForm` は、印があり `kind` が `design` のとき、今どおり `collectOptionalBasicSectionViolations` と `collectOptionalDiagramSectionViolations` を呼ぶ。`src/cli.ts` は変えない。

`## 検討した案` の項目の一行の記法は、次である。`validate` は、この記法を検査しない。

```
- 案: <案> 判定: 採用|不採用 理由: <理由>
```

行頭は `- ` である。`<案>` は案の概要であり、空白以外の文字を含む。`判定:` の直後は、文字 `採用` または文字 `不採用` のどちらか一つである。`<理由>` はその判定の理由であり、空白以外の文字を含む。一行に複数の案を書かない。

節「要件と設計の形式」へ足す文は、次の三行である。行のあいだに空行は入れない。

```
印がある設計には、任意の節 `## 検討した案` を書いてよい。節が無いときは `validate` は失敗しない。節があるときは、本文が空でないことを検査する。
検討した案の本文が空のときの違反は `節の本文が空です: 検討した案` である。
`## 検討した案` の項目は、「案」「選んだか退けたか」「理由」が分かる一行である。一行の記法は、この課題の設計が決めた記法である。
```

三行を改行でつないだものを塊とする。塊の末尾は、三行目の改行である。塊の中に空行は無い。

節「要件と設計の形式」では、行全体が `` `## 図` があるときは、各本文に Mermaid の囲みコードブロックを一つ以上持つことを検査する。`` である行の次に、空行一つを置き、その次に塊の一行目を置く。ファイル末尾の、行全体が `` 囲みが無いときの違反は `図に Mermaid の囲みがありません` である。`` である行の次に、空行一つを置き、その次に塊の二行目と三行目を置く。必須の節の文と、データモデル、インターフェース、図の検査を書く既存の文は、一文字も変えない。
