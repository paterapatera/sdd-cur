# 94 作業ブランチの push と「実装依頼」の付与を一つのコマンドで行う

対象は [Issue #94](https://github.com/paterapatera/sdd-cur/issues/94)。設計が終わったあと、人が実行する一つの CLI コマンドで、課題番号の作業ブランチを push し、そのあと課題に「実装依頼」を付ける。

#27 は、人は要求と設計を含む作業ブランチを push してから「実装依頼」を付ける、と定める。このコマンドでも、人は作業ブランチを push してから「実装依頼」を付ける。付けるのは人である。

#6 は、課題ランナーが「実装依頼」の課題を、push 済みの作業ブランチの上で実装する。

## 現状

作業ブランチの名前は `task-<番号>` である。`<番号>` は十進の課題番号であり、先頭の零は付けない。この名前を作るのは `implementationBranch` だけである。

人は、要求と設計を含む作業ブランチを push してから「実装依頼」を付ける。`skills/sdd-cur/SKILL.md` は、人が設計の完了を伝えたとき、push と「実装依頼」は人が行う、と定める。push するのは、要求と設計を含む作業ブランチである。SDD スキルは、この push とラベル付与を実行しない。

課題ランナーは「実装依頼」の課題を探す。クローンは、push 済みの作業ブランチを `fetch` し、`checkoutFetched` でその上にいる。要求と設計は、そのブランチに既にある。リモートに作業ブランチが無いときは、この取得に失敗する。リモートの作業ブランチが手元の最新のコミットより古いときは、クローンはリモートにある仕様で実装する。

`src/cli.ts` のサブコマンドは、`install`、`run`、`labels`、`candidates`、`show`、`branch`、`confirm`、`close`、`reflect`、`validate`、`complete`、`restore` である。この中に、作業ブランチの push と「実装依頼」の付与を続けて行うサブコマンドは無い。`branch` は、作業ブランチ名 `task-<番号>` を一行出力する。

`GitClient.push` は `git push -u <remote> <branch>` である。`GitClient` は、今のブランチ名を返さない。`hasChanges` は `git status --porcelain` の出力が空でないとき真である。追跡していないファイルがあるときも真である。

ラベルの変更は `editLabels` の `--add-label` と `--remove-label` だけである。「実装依頼」を付ける CLI のサブコマンドは無い。人は GitHub の画面か `gh` で付ける。業務ラベルの名前は `workflowLabels` の `name` である。いまの名前は「実装依頼」「実装中」「実装完了」「動作確認OK」「マージ済み」「コンフリクト」である。「quick 対象」は業務ラベルではない。

課題の `state` は `open` または `closed` である。要件と設計の状態は `specStatus` である。ファイルが無いとき、および中身が空のときは `missing` である。最初の非空行が `# <番号> ` のあとに題が一つ以上ある見出しであるときは `ready` である。それ以外は `invalid` である。この `ready` は、`validate` の形式検査とは別である。

`src/docs.test.ts` は、`src/cli.ts` の `switch` にあるサブコマンド名の集合と、次の四つの一覧が一致することを確かめる。`docs/policy.md` の構成の表、`AGENTS.md` の「コマンド」の例、README の「開発中の起動」の例、README のそのあとのコマンドの表である。

README は、人が Project A で書いた `docs/issues` をリモートへ push してから、課題に「実装依頼」を付ける、と書く。ラベルの表で「実装依頼」を付ける主体は人である。

`printUsage` の使い方の行は `install` から `complete` までである。`restore` は書かない。

## 受け入れ条件

- サブコマンド名は `request` である。
- 使い方は `bun src/cli.ts request <番号>` である。`<番号>` は課題番号であり、引数で渡す。
- 人が、作業ツリーで `bun src/cli.ts request <番号>` を実行すると、その課題番号の作業ブランチを push し、その push が成功したあと、その課題に「実装依頼」を付ける。
- push する作業ブランチの名前は `task-<番号>` である。`<番号>` は課題番号であり、十進で、先頭の零は付けない。
- 「実装依頼」の名前は、`workflowLabels` の `name` である。別の字面で再定義しない。
- 今のブランチが `task-<番号>` でないときは、何も変えずに日本語の一行で失敗する。`<番号>` は引数の課題番号である。
- 作業ツリーに未コミットの変更があるときは、何も変えずに日本語の一行で失敗する。未コミットの変更があるとは、既存の `hasChanges` が真のときである。`git status --porcelain` の出力が空でないとき真であり、追跡していないファイルがあるときも真である。
- 課題の `state` が `open` でないときは、何も変えずに日本語の一行で失敗する。
- 課題に業務ラベルが一つでもあるときは、何も変えずに日本語の一行で失敗する。
- 業務ラベルは `workflowLabels` の `name` である。「quick 対象」は業務ラベルではない。
- 要件の状態が `ready` でないときは、何も変えずに日本語の一行で失敗する。
- 設計の状態が `ready` でないときは、何も変えずに日本語の一行で失敗する。
- この `ready` は、既存の `specStatus` の `ready` である。
- push に失敗したときは、「実装依頼」を付けない。
- SDD スキルは、このコマンドを呼ばない。
- 課題ランナーは、このコマンドを呼ばない。
- 「実装依頼」を付けるのは人である。
- README は、人が `bun src/cli.ts request <番号>` で作業ブランチを push してから「実装依頼」を付ける、と書く。
- `request` を `src/cli.ts` に足したとき、`docs/policy.md` の構成の表は `request` を含む。
- `request` を `src/cli.ts` に足したとき、`AGENTS.md` の「コマンド」の例の行は `bun src/cli.ts request <番号>` である。
- `request` を `src/cli.ts` に足したとき、README の「開発中の起動」の例の行は `bun src/cli.ts request <番号>` である。
- `request` を `src/cli.ts` に足したとき、README のコマンドの表は `request` を含む。

## 決定

サブコマンド名は `request` である。

使い方は `bun src/cli.ts request <番号>` である。`<番号>` は課題番号であり、引数で渡す。

実行時、今のブランチが `task-<番号>` と一致することを確認する。一致しないときは、何も変えずに日本語の一行で失敗する。`<番号>` は引数の課題番号である。

作業ツリーに未コミットの変更があるとは、既存の `hasChanges` が真のときである。`git status --porcelain` の出力が空でないとき真であり、追跡していないファイルがあるときも真である。

課題番号を今のブランチ名から取ることは採用しない。

未追跡ファイルを未コミットの変更から外すことは採用しない。
