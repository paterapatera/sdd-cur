# 43 レビュー判定を最後の非空行以外からも読む

対象は [Issue #43](https://github.com/paterapatera/sdd-cur/issues/43)。要求、設計、実装のレビュー手順は、判定の印をレスポンス本文の下から、行全体の一致で読む。印が壊れているときは、同じレビューをあと 1 回だけやり直す。確認の印は、不合格のときだけ、判定行より前を下から読む。合格と不合格の意味、不合格で回数を 1 増やすこと、実装の 10 回打ち切り、モデルの上げ方は、設計 30 のままである。

## 受け入れ条件

- 要求、設計、実装のレビュー手順は、レスポンス本文を下から見て、行全体が `判定: 合格` または `判定: 不合格` と一致する行を探す。最初に見つかった行を判定行とする。
- 判定行が `判定: 合格` のとき、その後ろに非空行があっても、三つの手順は合格として進む。
- 判定行が `判定: 不合格` のとき、その後ろに非空行があっても、三つの手順は不合格として進む。
- 行全体が `判定: 合格` または `判定: 不合格` と一致する行が無いとき、三つの手順は、そのレビューをあと 1 回だけやり直す。同じレビューの起動は、合計最大 2 回である。
- 合計 2 回起動しても、行全体が `判定: 合格` または `判定: 不合格` と一致する行が無いときは、要求と設計はレスポンスを人に見せて止まる。実装は理由 `レビューの判定がありません` で失敗して終わる。
- 判定行が `判定: 不合格` のとき、要求と設計のレビュー手順は、判定行より前を下から見て、行全体が `確認: あり` または `確認: なし` と一致する行を探す。最初に見つかった行で確認を分岐する。
- 判定行が `判定: 不合格` のとき、要求と設計のレビュー役は、確認の位置を、判定行より前を下から探して最初に行全体が一致した行として書く。
- 判定行が `判定: 不合格` なのに、判定行より前に行全体が `確認: あり` または `確認: なし` と一致する行が無いとき、要求と設計はレスポンスを人に見せて止まる。修正は起動しない。
- 実装のレビュー手順は、`確認: あり` と `確認: なし` では分岐しない。
- 印が壊れているやり直しは、連続不合格にも、実装の不合格回数にも数えない。やり直したレスポンスの判定行が `判定: 不合格` のときだけ、そのレビューとして 1 増える。
- `bun test` は `gh` を起動しない。ホームディレクトリと、実行中の Cursor のスキルおよびサブエージェントは触らない。

## 印の読み方

`docs/conventions.md` に「レビューの判定」を足す。課題コメントの印、反映済み、マージリクエストの印は、今の節のままである。

本文の改行を `\n` にそろえ、下の行から、行全体が次のどちらかと一文字も違わない行を探す。最初に見つかった行が判定行である。その後ろは見ない。前後の空白を除いて比べない。

| 判定 | 行 |
|---|---|
| 合格 | `判定: 合格` |
| 不合格 | `判定: 不合格` |

一致する行が無いとき、判定は無い。この文書は、それを印が壊れているとする。やり直しと停止は、各レビュー手順が行う。

判定行が不合格のときだけ、その行より前を下から見て、行全体が次のどちらかと一文字も違わない行を探す。最初に見つかった行が確認行である。判定行より後ろは見ない。合格のとき、および判定が無いときは、確認行を探さない。

| 確認 | 行 |
|---|---|
| あり | `確認: あり` |
| なし | `確認: なし` |

`src/conventions.ts` に足す。

```ts
export const reviewJudgmentMarkers = {
  pass: "判定: 合格",
  fail: "判定: 不合格",
} as const

export const reviewConfirmMarkers = {
  yes: "確認: あり",
  no: "確認: なし",
} as const

export type ReviewJudgment = "pass" | "fail" | "absent"

export type ReviewConfirm = "yes" | "no" | "absent"

export type ParsedReview = {
  judgment: ReviewJudgment
  confirm: ReviewConfirm
}

export function parseReview(body: string): ParsedReview
```

`judgment` が `pass` または `absent` のとき、`confirm` は `absent` である。本文に確認の印があっても同じである。`judgment` が `fail` のとき、確認行があれば `yes` または `no`、無ければ `absent` である。判定行が複数あるときは、下から最初の一行だけを判定行とする。その行より上の判定の印は、確認行ではない。

## 手順

質問、作業ブランチ、`show` の止まり、作成、修正へ渡す差分、指摘をどこにも置かないことは変えない。変えるのは、レビューのレスポンスの読み方と、印が壊れているときのやり直しである。

三つの手順は、`parseReview` と同じ一致で読む。最後の非空行だけ、部分一致、空白を除いた一致は書かない。

### 要件

`skills/sdd-cur/SKILL.md` の「要件」のうち、レビュー役のレスポンスを読む段落を、次に変える。数えるレビュー、開始時の連続不合格 0、1 回目と 2 回目は model を渡さない、続けて不合格のとき 3回目から `grok-4.7-high`、という文は残す。

判定行は、レスポンス本文を下から見て、行全体が `判定: 合格` または `判定: 不合格` と一致する最初の行である。一致する行が無いときは、印が壊れている。

印が壊れているときは、同じレビューをあと 1 回だけやり直す。同じレビューの起動は、合計最大 2 回である。このやり直しでは連続不合格を増やさない。モデルは、その数えるレビューと同じものを使う。修正も作成も起動しない。やり直したレスポンスも、同じ探し方で判定行を決める。2 回起動しても判定行が無いときは、修正を起動しない。連続不合格は増やさない。最後のレスポンスを人に見せて止まる。

判定行が `判定: 合格` のときは、その後ろに非空行があっても合格として進む。修正を起動しない。作成も起動しない。連続不合格は増やさない。確認は探さない。人に伝える前に `show` を改めて実行する。`unanswered` が空であり、かつ `nextAnswer` が `null` であるときは、判定が合格なら設計に進むことができる、と伝える。どちらかが残っているときは、確認が `reflect` で終わるまで設計には進まない、と伝える。設計のファイルはこの手順で作らない。課題は閉じない。設計の手順は、人が設計を依頼したときだけ始める。

判定行が `判定: 不合格` のときは、その後ろに非空行があっても不合格として進む。連続不合格を 1 増やす。確認行は、判定行より前を下から見て、行全体が `確認: あり` または `確認: なし` と一致する最初の行である。

確認行が `確認: あり` のときは、列挙された点を人に見せ、修正を起動しない。確認コメントは、この止まりでは投稿しない。人が答えるまで、その部分は要求へ書かない。人が答えたあとは、その答えを人が決めた条件として、レビューと修正指示を再び起動する。この再起動は回数を増やさない。モデルは、その回数と同じものを使う。この再起動の印が壊れているときは、その再起動の中で、同じレビューをあと 1 回だけやり直す。この止まりは、採点付きの質問とは別である。

確認行が `確認: なし` のときは、その差分だけを修正へ渡す。あわせて、レビューに入る前に人が選んだ通常の回答を、人が決めた条件として渡す。修正のあと、レビューと修正指示に戻る。合格になるまで繰り返す。レビューの不合格のあと、要求作成役は起動しない。「作成から合格まで 1 回」および high の作成 1 回は、レビューに入る前の初回の成果物作成（grok-4.7-high）を指す。設計 26 の質問で人が通常の選択肢を選んだあとの要求作成役の再起動は、同じ要求の続きであり、作成の high の 2 回目に数えない。

判定行が `判定: 不合格` であり、確認行が無いときは、修正を起動しない。レビューはやり直さない。レスポンスを人に見せて止まる。

### 設計

`skills/sdd-cur/SKILL.md` の「設計」に残っている、最後の非空行で分岐する段落は、要件と同じ段落に置き換える。読み方、やり直し、確認の分岐、確認が無いときの止まりは、要件と同じである。`確認: あり` の段落は、書かない先を設計にする。人が答えるまで、その部分は設計へ書かない。合格のあとの伝達と、`確認: なし` のあとに設計作成役を起動しないことだけが、ほかに要件と違う。

判定行が `判定: 合格` のときは、修正を起動しない。作成も起動しない。連続不合格は増やさない。確認は探さない。設計を終える。要求ファイルはこの手順で作らない。課題は閉じない。判定が合格なら実装依頼に進むことができる、と人に伝えて終わる。人が設計の完了を伝えたときは、push と「実装依頼」は人が行う。push するのは、要求と設計を含む作業ブランチである。

確認行が `確認: なし` のときは、その差分だけを修正へ渡す。修正のあと、レビューと修正指示に戻る。合格になるまで繰り返す。不合格のあと、設計作成役は起動しない。

### 実装

`skills/sdd-cur-implement/SKILL.md` の「レビュー」のうち、判定の読み方と回数の増やし方を、次に変える。フロントマター、`## 実装`、`## 禁止`、失敗のときの終了コードと理由の書き方、合格後の手順本文は残す。

不合格の回数は、この一回の agent 起動の中だけで数える。開始時は 0 である。ファイルにも課題コメントにも書かない。ランナーが `implement` を再試行しても、回数は引き継がない。判定行が `判定: 不合格` のときに 1 増やす。印が壊れているやり直しでは増やさない。1 回目と 2 回目のレビューは model を渡さない。1 回目と 2 回目が続けて不合格のとき、3回目から model に `grok-4.7-high` を渡す。合格まで渡す。10 回目も、その回が 3 以上なら high を渡してから判定を見る。やり直しは、その回と同じ model である。

判定行は、レスポンス本文を下から見て、行全体が `判定: 合格` または `判定: 不合格` と一致する最初の行である。その後ろに非空行があっても、その判定で進む。`確認: あり` と `確認: なし` では分岐しない。

一致する行が無いときは、同じレビューをあと 1 回だけやり直す。同じレビューの起動は、合計最大 2 回である。回数は増やさない。2 回目も無いときは、修正を起動しない。理由は `レビューの判定がありません` である。agent は失敗で終える。`実装レビューが不合格のまま10回に達した` にはしない。

判定行が `判定: 合格` のときは、修正を起動しない。最初の本文が実装と合わないときだけ、親が同じパスの本文を書き直す。印の行は書かない。成功で終える前の本文は、空でなく、最初の非空行は印ではない。

判定行が `判定: 不合格` のときは、増やした回数が 10 のときは、修正も次のレビューも起動しない。理由は `実装レビューが不合格のまま10回に達した` である。agent は失敗で終える。増やした回数が 9 以下のときは、人に確認しない。修正指示は変える部分の差分だけであり、全文は書かない。差分だけを修正へ渡す。修正のあと、レビューと修正指示に戻る。不合格のあと、実装作成役は起動しない。

10 回目のレビューで印が壊れているときは、まだ不合格ではない。同じ model で、そのレビューをもう 1 回起動する。2 回目の判定行が `判定: 不合格` のとき、回数は 10 になり、10 回の理由で失敗する。2 回目も印が壊れているときは、回数を増やさず、`レビューの判定がありません` で失敗する。2 回目の判定行が `判定: 合格` のときは、合格として進む。

## レビュー役

フロントマター、指摘の観点、禁止は変えない。変えるのは、出力の判定と、要求と設計の確認の位置である。

要求と設計のレビュー役は、確認を、判定行より前の一行として書く。その行の全体は `確認: あり` または `確認: なし` である。親は、判定行より前を下から見て、最初に一致した行で確認を分ける。合格のときは、判定が `判定: 合格` であり、確認は `確認: なし` である。指摘が一つでもあるときは `判定: 不合格` である。

三つのレビュー役とも、判定は、行全体が `判定: 合格` または `判定: 不合格` と一致する一行である。この行の後ろに非空行があっても、判定はこの行である。

実装のレビュー役は、人に確認しない。`確認: あり` も `確認: なし` も書かない。
