# 69 実装するものが無い課題は設計までに閉じ、実装の agent は履歴を書き換えない

対象は [Issue #69](https://github.com/paterapatera/sdd-cur/issues/69)。要件の手順または設計の手順が合格し、次へ進めると人に伝える直前に、課題の期待がすでに main で満たされていると根拠つきで示せるときは、SDD スキルが判断と根拠を人に示し、閉じるか閉じないかを尋ねる。閉じるを選んだときだけ、通常のコメントを書いて課題を閉じる。実装、修正、quick の agent は、ブランチの先頭を動かす git 操作をしない。課題ランナーは、起動した agent の前後で `HEAD` が違っていたら、作業コピーを戻さず、コミットも push もせず、失敗で止まる。

重なる課題は #23 と #27 である。

## 受け入れ条件

- 要件の手順が合格し、設計に進めると人に伝える直前、および設計の手順が合格し、実装依頼に進めると人に伝える直前に、課題の期待がすでに main で満たされているかを判断する。課題番号、ファイル、行を根拠として、すでに main で満たされていると示せるときは、その案内の前に、SDD スキルが判断と根拠を人に示す。
- すでに main で満たされていると、課題番号、ファイル、行を根拠として示せるときは、Cursor の質問機能で、閉じるか閉じないかの二択を出す。閉じるを選んだときだけ、判断と根拠を課題のコメントに書き、課題を閉じる。そのとき SDD スキルは `bun src/cli.ts close <番号>` を使う。標準入力は、印のない判断と根拠である。
- そのコメントは、確認、回答、受け入れ手順の印を使わない。本文に判断と根拠を書いた通常のコメントである。新しい印を先頭行に付けない。
- `AGENTS.md`、SDD スキル、そのサブエージェントにある「課題を閉じない」という定めは、この課題で変える。変えるのは、人が閉じるを選んだときに SDD スキルが閉じる場合だけである。
- 課題ランナーは課題を閉じない。
- すでに main で満たされていると、課題番号、ファイル、行を根拠として示せないときは、二択は出さず、課題を閉じない。
- 閉じないを選んだときは、課題を閉じない。要件と設計の通常の手順を続ける。
- その回の要件または設計の手順を止め、ファイルを承認前のままにすることはしない。
- 実装、修正、quick の agent は、ブランチの先頭を動かす git 操作をしない。`reset`、`checkout`、`rebase` のように、先頭を動かす操作を含む。対象は `skills/sdd-cur-implement`、`skills/sdd-cur-fix`、`skills/sdd-cur-quick` と、実装のサブエージェントである。
- 課題ランナーは、起動した agent の起動前と終了後で `HEAD` が変わっていたら、作業コピーは戻さず、コミットも push もせず、失敗で止まる。失敗の理由は `agent がブランチの先頭を変えました` であり、`Error` で返す。
- `bun test` は `gh`、`git`、`agent` を起動しない。

## スキルの手順

`skills/sdd-cur/SKILL.md` のフロントマターは、次と一文字も違わない。

```
---
name: sdd-cur
description: このプロジェクトの課題について、着手候補の提示、要件、設計、確認コメントの投稿、未反映の回答の取り込みを行う。着手、要件、設計、確認、回答の取り込みを依頼されたときに使う。課題は作らない。人が閉じるを選んだときに SDD スキルが閉じる場合を除き、課題は閉じない。ラベルの変更、実装、受け入れ手順、完了処理はしない。
disable-model-invocation: true
---
```

`name` と `disable-model-invocation` は今のままである。着手、確認、回答の既存の必須文言は残す。`gh` は直接起動しない。ラベルは変えない。実装依頼は人が付ける。push は人が行う。実装は課題ランナーが行う。受け入れ手順は投稿しない。完了処理は行わない。書いてよいのは、今どおり `docs/specs/<番号>/requirements.md` と `docs/specs/<番号>/design.md` だけである。

「禁止」の課題を閉じない一文は、次に変える。

課題は作らない。人が閉じるを選んだときに SDD スキルが閉じる場合を除き、課題は閉じない。

### 満たされているかの判断

判断は、次の案内を人に伝える直前だけに行う。

- 要件の手順で、判定が合格であり、人に伝える前の `show` のあと、`unanswered` が空であり、かつ `nextAnswer` が `null` であるときに伝える「判定が合格なら設計に進むことができる」
- 設計の手順で、判定が合格のときに伝える「判定が合格なら実装依頼に進むことができる」
- 回答の手順で、合格のあとの案内が、上の二つと同じであるとき

`unanswered` が空でない、または `nextAnswer` が `null` でないために、その案内を伝えないときは、判断しない。二択も出さない。課題を閉じない。今の、確認が `reflect` で終わるまで進まない旨の伝え方は残す。

判断は、課題の期待がすでに main で満たされているかである。行うのは SDD スキルである。要求のサブエージェントと設計のサブエージェントは、この判断をしない。二択を出さない。コメントを書かない。課題を閉じない。

課題番号、ファイル、行を根拠として示せるときは、案内の前に、その判断と根拠を人に示す。続けて、Cursor の質問機能で二択を出す。選択肢の文言は `閉じる` と `閉じない` である。人がどちらかを選ぶまで、案内は伝えない。コメントは書かない。課題は閉じない。

示せないときは、二択を出さない。課題を閉じない。案内を伝える。

`閉じない` を選んだときは、課題を閉じない。要件と設計の通常の手順を続ける。案内を伝える。設計の手順は、人が設計を依頼したときだけ始める。人が設計の完了を伝えたときの push と「実装依頼」は、今どおり人が行う。

`閉じる` を選んだときは、`bun src/cli.ts close <番号>` を実行する。標準入力は、判断と根拠を書いた本文だけである。印の行は入れない。`confirm` は使わない。コメントの最初の非空行は、`sdd-cur: 確認`、`sdd-cur: 回答`、`sdd-cur: 受け入れ手順` のいずれでもない。新しい印を先頭行に付けない。`gh` は直接起動しない。ラベルは変えない。設計に進める旨は伝えない。実装依頼に進める旨は伝えない。

どちらの選択でも、その回に書いた要件ファイルと設計ファイルは、承認前の内容へ戻さない。手順を止めて、ファイルを承認前のままにすることはしない。

`src/cli.ts` にサブコマンド `close` を足す。使い方の行は `sdd-cur close <番号>` であり、`sdd-cur confirm <番号>` の直後に置く。引数が番号一つでないときは、使い方を書いて終了コード 1 である。番号は `parseIssueNumberString` で読む。標準入力は `confirm` と同じ `readStdinAll` で読む。印は付けない。`confirmationBody` は使わない。読んだ文字列を、`createGitHub` の `addComment` の本文にする。`addComment` が成功したあと、同じ `createGitHub` で課題を閉じる。`addComment` が拒否したときは、課題を閉じない。

課題を閉じる操作は `createGitHub` に足す。引数は `issue`、`close`、課題番号の十進だけである。`--state` は付けない。スキルは `gh` を直接起動しない。課題ランナーはこの操作を呼ばない。

## AGENTS.md

`AGENTS.md` の、課題を閉じない定めと、`issue close` の定めを変える。構成のサブコマンドの列には、`confirm` の直後に `close` を足す。それ以外の節は変えない。

課題を作るのは人である。SDD スキルも課題ランナーも、課題を作らない。人が閉じるを選んだときに SDD スキルが閉じる場合を除き、課題は閉じない。課題ランナーは課題を閉じない。お客さまの確認が取れてから、人が閉じる。

ラベルの変更は `issue edit` の `--add-label` と `--remove-label` だけである。`issue close` は、人が閉じるを選んだときに SDD スキルが課題を閉じる場合だけ付ける。課題ランナーは付けない。`--state` は付けない。

## ランナー

課題ランナーは課題を閉じない。`issue close` は付けない。`src/runner.ts` の `runImplementation`、`runQuick`、`runFix` に、起動した agent の前後で `HEAD` を比べる手順を足す。`poll` は変えない。

`GitClient` に `headCommit` を足す。呼ぶ引数は `rev-parse` と `HEAD` である。識別子は、標準出力の最初の非空行から、前後の空白を除いたものである。識別子が空のとき、および git が失敗したときは、その読み取りの失敗である。読み取りが拒否したときは、他の git 呼び出しと同じく、その読み取りだけをもう一度行う。二度目も拒否したときは、そこで止まる。

比べるのは、その agent を起動する直前の識別子と、その起動が成功または失敗で戻った直後の識別子である。記録するのは、ランナー自身の `checkoutFetched` のあと、その agent の直前である。

違っていたときは、その agent を再び起動しない。再試行で二度目の起動を始めない。コミットも push もしない。受け入れ手順のコメント、修正コメント、完了のラベル変更はしない。作業コピーを戻す git 操作はしない。`reset` も `checkout` もしない。着手で付けたラベルは戻さない。失敗の理由は `agent がブランチの先頭を変えました` であり、`Error` で返す。

同じであり、その起動が失敗したときは、今どおりその起動だけをもう一度行う。同じであり、その起動が成功したときは、作業ツリーの変更の有無から後は今のままである。変更が無いときの `実装の変更がありません` は残す。

対象の起動は、次である。

- `runImplementation` の `implement`
- `runQuick` の `quick` と、そのあと呼ぶ `implement`
- `runFix` の `fix`

`quick` の直後に識別子が違っていたときは、`implement` を呼ばない。`fix` の直後に違っていたときは、範囲外だけの成功にも進まない。
