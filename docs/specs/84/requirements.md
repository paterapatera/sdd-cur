# 84 プロジェクト全体の方針を一つのファイルにまとめる

対象は [Issue #84](https://github.com/paterapatera/sdd-cur/issues/84)。誰のための道具か、技術の前提、構成、破ってはいけない原則を、一つのファイルにまとめる。要求と設計の作成役とレビュー役は、毎回そのファイルを読む。

手を入れる対象は、新しい方針のファイル、`AGENTS.md`、README、要求と設計の作成役とレビュー役のエージェントファイルである。方針のファイルの名前と置き場所は、設計が決める。

重なる課題は #83（ドキュメントとスキルのずれを直し、ずれをテストで見つける）である。#83 は、方針の置き場所をまとめることを範囲外としている。

比べる相手は、Spec Kit の constitution と、cc-sdd の steering である。

## 現状

方針の正本になるファイルは無い。

技術の前提は、`AGENTS.md` と README に分かれて書いてある。

- `AGENTS.md` は、このプロジェクト専用の SDD スキルと課題ランナーを、Bun で直接実行する TypeScript として作る、と書く。依存パッケージは置かない、と書く。GitHub の操作は `createGitHub` から呼び、`gh` を子プロセスで起動する、と書く。利用者向けのメッセージ、ドキュメント、コミットメッセージの説明は日本語で書く、と書く。
- README の「前提」は、Bun、ログイン済みの `gh`、依存パッケージは置かない、TypeScript は Bun が直接実行する、と書く。README に、日本語で書く、という記述は無い。

誰のための道具かと、構成は、`AGENTS.md` と README の両方にある。

- `AGENTS.md` の冒頭は、このリポジトリが `@paterapatera/sdd-cur` であり、このプロジェクト専用の SDD スキルと課題ランナーである、と書く。「構成」の表は、場所と役割を書く。`src/cli.ts` の行は、サブコマンドの列挙を含む。
- README の冒頭は、`@paterapatera/sdd-cur` がこのプロジェクト専用の SDD スキルと課題ランナーである、と書く。課題の作成、要件、設計、お客さまへの確認は人が Cursor で行う、と書く。実装と、選んだ場合の完了処理は、課題ランナーが別のクローンで行う、と書く。「役割」は、SDD スキルと課題ランナーの動く場所を書く。「ディレクトリ」は、場所と役割を書く。

破ってはいけない原則は、`AGENTS.md`、README、各スキルの「禁止」、各サブエージェントの「禁止」に、少しずつ違う言い方で繰り返されている。

- `AGENTS.md` は、人が明示して起動したときに `skills/sdd-cur-create-issue` が課題を作る、と書く。課題ランナーは課題を作らない、と書く。人が閉じるを選んだときに SDD スキルが閉じる場合を除き、課題は閉じない、と書く。課題ランナーは課題を閉じない、と書く。お客さまの確認が取れてから、人が閉じる、と書く。設計に書いた「範囲外」は作らない、と書く。設計が無い挙動は足さない、と書く。
- README の「役割」は、課題を作るのは人である、と書く。SDD スキルも課題ランナーも、課題は作らない、と書く。「ラベル」は、課題は閉じない、と書く。お客さまの確認が取れてから、人が閉じる、と書く。
- `skills/sdd-cur/SKILL.md` の「禁止」は、課題は作らない、と書く。人が閉じるを選んだときに SDD スキルが閉じる場合を除き、課題は閉じない、と書く。
- `skills/sdd-cur-create-issue/SKILL.md` の「禁止」は、作った課題は閉じない、と書く。依頼が無いときは課題を作らない、と書く。
- `skills/sdd-cur-implement/SKILL.md`、`skills/sdd-cur-quick/SKILL.md`、`skills/sdd-cur-fix/SKILL.md`、`skills/sdd-cur-complete/SKILL.md` の「禁止」は、課題を作らない、課題を閉じない、と書く。
- 「禁止」があるサブエージェントは、課題を作らない、課題を閉じない、と書く。要求と設計の作成役、レビュー役、修正役は、加えて、人が閉じるを選んだときに課題を閉じるのは SDD スキルである、このサブエージェントは課題を閉じない、と書く。実装レビュー役に「禁止」の見出しは無く、本文に、課題を作らない、課題を閉じない、と書く。
- 「設計に書いた『範囲外』は作らない」という文は、`AGENTS.md` にある。各スキルと各サブエージェントの「禁止」は、この文そのものでは書いていない。

要求と設計の作成役とレビュー役の起動時に、プロジェクト全体の方針を読む手順は無い。

- 要求作成役は、課題番号、題、課題本文、既存の要求ファイル、人が決めた条件を読む。
- 要求レビュー役は、要求ファイル、課題本文、人が決めた条件を読む。`docs/specs/` にある既存の `requirements.md` と `design.md` を読む。
- 設計作成役は、課題番号、題、課題本文、その課題の要件、既存の設計ファイルを読む。
- 設計レビュー役は、設計ファイル、課題本文、その課題の要件、人が決めた条件を読む。`docs/specs/` にある既存の `requirements.md` と `design.md` を読む。

## 受け入れ条件

- 誰のための道具か、技術の前提、構成、破ってはいけない原則の正本は、一つのファイルにある。
- 技術の前提には、Bun で直接実行すること、依存パッケージを置かないこと、GitHub の操作は `gh` だけであること、日本語であることを含む。
- 破ってはいけない原則には、課題を閉じること、範囲外を作ることについての、今の原則を含む。
- 課題を作ることについては、人が明示して起動したときに `skills/sdd-cur-create-issue` が課題を作り、課題ランナーは課題を作らない、という文言を、`AGENTS.md` の言い方に揃えて正本に含む。
- README の文言を正本と統合することは、この課題の受け入れには含めない。
- README と正本の食い違いの解消は #83 の範囲とする。
- そのファイルは、そのファイルを変えるのは課題を通したときだけである、と書く。
- `AGENTS.md` は、そのファイルを指す。
- `AGENTS.md` は、そのファイルに書いた、誰のための道具か、技術の前提、構成、破ってはいけない原則を、同じ内容では繰り返さない。
- README は、そのファイルを指す。
- README は、そのファイルに書いた、誰のための道具か、技術の前提、構成、破ってはいけない原則を、同じ内容では繰り返さない。
- 要求作成役は、起動時にそのファイルを読む。
- 要求レビュー役は、起動時にそのファイルを読む。
- 要求レビュー役は、レビューしている要求のうち、そのファイルの原則と食い違う記述を指摘する。
- 設計作成役は、起動時にそのファイルを読む。
- 設計レビュー役は、起動時にそのファイルを読む。
- 設計レビュー役は、レビューしている設計のうち、そのファイルの原則と食い違う記述を指摘する。
- 各スキルの「禁止」と、各サブエージェントの「禁止」の文言は、この課題では変えない。

## 決定

課題を作ることについての方針ファイル正本の文言は、`AGENTS.md` の言い方に揃える。人が明示して起動したときに `skills/sdd-cur-create-issue` が課題を作り、課題ランナーは課題を作らない、という内容を正本に含める。

README は正本を指す形に寄せる。README と正本の食い違いの解消は #83 の範囲とする。

## 名前と置き場所

方針のファイルの名前と置き場所は、この要件では決めない。設計が決める。

## 範囲外

- 原則そのものを変えること
- ドキュメントとスキルのずれを直し、ずれをテストで見つけること（#83）
