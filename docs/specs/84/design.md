# 84 プロジェクト全体の方針を一つのファイルにまとめる

対象は [Issue #84](https://github.com/paterapatera/sdd-cur/issues/84)。誰のための道具か、技術の前提、構成、破ってはいけない原則の正本を `docs/policy.md` に置く。文言は、いまの `AGENTS.md` に揃える。README の文は正本へ混ぜない。

重なる課題は #83 である。`docs/specs/83/design.md` は書き換えない。README と正本の食い違いを、一方に揃えて解消することは、#83 の範囲である。

## 受け入れ条件

- 破ってはいけない原則には、課題を閉じること、範囲外を作ることについての、今の原則を含む。
- 課題を作ることについては、人が明示して起動したときに `skills/sdd-cur-create-issue` が課題を作り、課題ランナーは課題を作らない、という文言を、`AGENTS.md` の言い方のまま正本に含む。
- README の文言を正本と統合することは、この課題の受け入れには含めない。
- README と正本の食い違いの解消は #83 の範囲とする。
- `docs/policy.md` は、そのファイルを変えるのは課題を通したときだけである、と書く。
- `AGENTS.md` は、`docs/policy.md` を指す。
- `AGENTS.md` は、`docs/policy.md` に書いた、誰のための道具か、技術の前提、構成、破ってはいけない原則を、同じ内容では繰り返さない。
- README は、`docs/policy.md` を指す。
- README は、`docs/policy.md` に書いた、誰のための道具か、技術の前提、構成、破ってはいけない原則を、同じ内容では繰り返さない。
- 要求作成役は、起動時に `docs/policy.md` を読む。
- 要求レビュー役は、起動時に `docs/policy.md` を読む。
- 要求レビュー役は、レビューしている要求のうち、`docs/policy.md` の原則と食い違う記述を指摘する。
- 設計作成役は、起動時に `docs/policy.md` を読む。
- 設計レビュー役は、起動時に `docs/policy.md` を読む。
- 設計レビュー役は、レビューしている設計のうち、`docs/policy.md` の原則と食い違う記述を指摘する。
- 各スキルの「禁止」と、各サブエージェントの「禁止」の文言は、この課題では変えない。

## 範囲外

次は、この要件に含めない。

- 各スキルと、各サブエージェントの「禁止」の書き換え。四役の「禁止」も変えない
- 四役以外のサブエージェントの本文。修正役と実装の三役に、`docs/policy.md` を読む手順は足さない
- 原則そのものを変えること。正本の文は、いまの `AGENTS.md` の意味のままである
- ドキュメントとスキルのずれを直し、ずれをテストで見つけること（#83）。`docs/specs/83/design.md` は書き換えない
- README の文言を正本へ統合すること
- README と正本の食い違いを、文言を揃えて解消すること。対象は、README の「役割」にある課題作成の二文と、正本の表に無く説明の違う案内である
- README の「開発中の起動」と「公開後の起動」
- `docs/conventions.md`、`src/conventions.ts`、`src/cli.ts`、`src/install.ts`、そのほかの実装
- この課題以外の `requirements.md` と `design.md`
- 課題の作成とクローズ。ラベルの変更。確認コメント。受け入れ手順。完了処理
- 依存パッケージ。`package.json` の変更

既存のテストが、この課題で移した文の古い場所を見ているときは、その期待の場所を変える。新しいずれ検出は足さない。

```markdown
# 方針

## 誰のための道具か

このリポジトリは `@paterapatera/sdd-cur` である。このプロジェクト専用の SDD スキルと課題ランナーである。

## 技術の前提

SDD スキルと課題ランナーは、Bun で直接実行する TypeScript として作る。依存パッケージは置かない。

GitHub の操作は `createGitHub` から呼ぶ。`gh` を子プロセスで起動し、認証は `gh` のログインに任せる。このモジュールはトークンも環境変数も読まない。

利用者向けのメッセージ、ドキュメント、コミットメッセージの説明は日本語で書く。識別子は英語にする。失敗の理由は日本語の一行にし、`Error` で返す。

## 破ってはいけない原則

人が明示して起動したときに、`skills/sdd-cur-create-issue` が課題を作る。課題ランナーは課題を作らない。人が閉じるを選んだときに SDD スキルが閉じる場合を除き、課題は閉じない。課題ランナーは課題を閉じない。お客さまの確認が取れてから、人が閉じる。

設計に書いた「範囲外」は作らない。設計が無い挙動は足さない。

ラベルの変更は `issue edit` の `--add-label` と `--remove-label` だけである。`issue close` は、人が閉じるを選んだときに SDD スキルが課題を閉じる場合だけ付ける。課題ランナーは付けない。`--state` は付けない。
```

README にある「ログイン済みの `gh`」「課題の作成、要件、設計、お客さまへの確認は人が Cursor で行う」「実装と、選んだ場合の完了処理は、課題ランナーが別のクローンで行う」は、このファイルに書かない。
