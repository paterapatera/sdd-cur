# 95 課題ランナーの処理ごとに、かかった時間と agent の起動回数を出す

対象は [Issue #95](https://github.com/paterapatera/sdd-cur/issues/95)。課題ランナーのログに、処理ごとのかかった時間と、Cursor `agent` を起動した回数を出す。どの課題、どの段に時間がかかっているかを見えるようにする。

手を入れる対象は `src/run.ts`、`src/runner.ts`、`src/agent.ts` である。

重なる課題は #6（課題ランナー）である。

## 現状

`runLoop` は、処理の開始に `処理を開始します: <id>` を書く（`src/run.ts` の 83 行）。この行に、かかった時間は無い。

`runLoop` は、処理の終了に `処理を終了します: <id>` を書く（`src/run.ts` の 96 行）。この行に、かかった時間は無い。

処理が失敗したとき、`runLoop` は理由の一行を `logError` へ渡す（`src/run.ts` の 88 行）。続けて終了コード 1 で戻る（`src/run.ts` の 94 行）。`処理を終了します` は、この戻りより後ろにある（`src/run.ts` の 96 行）。

`log` の一行は標準出力へ書く（`src/cli.ts` の 157 行）。`logError` の一行は標準エラーへ書く（`src/cli.ts` の 159 行）。

起動が失敗したあと、ブランチの先頭が変わっていなければ、`runAgentWithHeadCheck` は同じ起動をもう一度行う（`src/runner.ts` の 112 行）。先頭の比較は、そのやり直しの前にある（`src/runner.ts` の 110 行）。最初の起動は、回数をログに出さない（`src/runner.ts` の 108 行）。やり直した起動も、回数をログに出さない（`src/runner.ts` の 112 行）。

`quick` は、最初の `runAgentWithHeadCheck` が失敗し、その失敗がブランチ先頭の変化でないとき、`runAgentWithHeadCheck` をもう一度行う（`src/runner.ts` の 677 行）。

Cursor `agent` の起動結果は、標準出力と標準エラーと終了コードである（`src/agent.ts` の 217 行）。サブエージェントの起動回数とレビュー回数は、この結果に無い。

## 受け入れ条件

- `処理を開始します` を書いた処理が正常終了したとき、その処理にかかった時間と、その処理で起動した agent の種類ごとの回数を、既存の `処理を終了します` の行に足す。
- 正常終了のとき、時間と回数のために別の行は足さない。
- その行は、標準出力に書く。
- その行に足す時間と回数に、処理の id は含めない。
- 正常終了の行は、`処理を終了します: <id>` の末尾に、空白一つと括弧を足した形である。
- 括弧の中の先頭は、かかった時間である。
- 開き括弧とかかった時間のあいだに、空白は無い。
- 閉じ括弧の直前に、空白は無い。
- 1 回以上起動した種類があるとき、かかった時間の直後に空白一つを置き、`種類=回数` を書く。
- `種類=回数` の `=` の前後に、空白は無い。
- 種類が複数あるとき、となりあう `種類=回数` のあいだは、空白一つである。
- 種類を書く順は、`quick`、`implement`、`fix` である。
- 起動した種類が無いとき、括弧の中はかかった時間だけである。
- かかった時間が 2 分 15 秒で、`quick` が 1 回、`implement` が 2 回、`fix` が 0 回のときの正常終了の行は、`処理を終了します: <id> (2m15s quick=1 implement=2)` である。
- `処理を開始します` を書いたあとで `process` が失敗したとき、失敗の理由の日本語一行は、今どおり標準エラーに書く。
- `処理を開始します` を書いたあとで `process` が失敗したとき、その処理にかかった時間と、その処理で起動した agent の種類ごとの回数を、理由の一行の直後に、標準エラーの一行として書く。
- その一行は、課題コメントの投稿より前に書く。
- 失敗のときのその一行は、括弧だけである。
- 失敗のときの括弧の中は、正常終了の括弧の中と同じ形である。
- その一行に、処理の id は含めない。
- かかった時間が 2 分 15 秒で、`quick` が 1 回、ほかの種類が 0 回のときの失敗の一行は、`(2m15s quick=1)` である。
- その失敗の課題コメントの本文は、失敗の理由の一行のままである。
- かかった時間は、`処理を開始します` を書いてから、正常終了では `処理を終了します` の行を書くまで、失敗では時間と回数の一行を書くまでである。
- 課題コメントの投稿の待ちは、かかった時間に含めない。
- かかった時間の表記は、分と秒である。
- 60 秒は、1 分へ繰り上げる。
- 表記に使う秒は、0 以上 59 以下である。
- 分が 60 以上のときは、分を時間へ繰り上げない。
- かかった時間の単位は、分と秒のままである。
- 分が 1 以上で秒が 1 以上のときは、分の十進、`m`、秒の十進、`s` を、空白を置かずにこの順で書く。
- 分が 0 で秒が 1 以上のときは、秒の十進と `s` だけを書く。
- 秒が 0 で分が 1 以上のときは、分の十進と `m` だけを書く。
- 1 秒未満のときは、`0s` と書く。
- 1 秒以上の経過にある 1 秒未満の端数は、切り捨てる。
- 59.6 秒の表記は、`59s` である。
- 59.9 秒の表記は、`59s` である。
- かかった時間が 2 分 15 秒のときの表記は、`2m15s` である。
- かかった時間が 15 秒のときの表記は、`15s` である。
- かかった時間が 2 分のときの表記は、`2m` である。
- かかった時間が 65 分 30 秒のときの表記は、`65m30s` である。
- 分、秒、回数の十進は、先頭の零を付けない。
- 種類は、`quick`、`implement`、`fix` である。
- 回数は、その処理の中でランナーが、その種類の agent を起動した回数である。
- 時間と回数の一行には、1 回以上起動した種類だけを書く。
- 起動が 0 回の種類は書かない。
- 起動が失敗したあとのやり直しも、回数に含める。
- agent の中のサブエージェントの起動は、回数に含めない。
- agent の中のレビュー回数は、回数に含めない。
- かかった時間と回数の一行は、ファイルに書かない。
- かかった時間と回数の一行は、GitHub に書かない。

## 決定

括弧の形、種類と回数、失敗時の一行の位置、分秒表記と端数切り捨ては、課題の一行での終了時と失敗時の出力と、人の確認により定める。

かかった時間の表記は、分と秒であり、例は `2m15s` である。

正常終了のとき、かかった時間と起動回数は、既存の `処理を終了します` の行に足し、別の行は足さない。

正常終了のその行は、標準出力に書く。

失敗のとき、かかった時間と起動回数は、理由の一行のあとに、標準エラーの一行として書く。

正常終了で足す時間と回数にも、失敗のときの時間と回数の一行にも、処理の id は含めない。

時間と回数の一行には、1 回以上起動した種類だけを書く。

起動が 0 回の種類は書かない。

正常終了の行は、`処理を終了します: <id>` の末尾に、空白一つと括弧を足した形である。

括弧の中は、かかった時間で始まる。開き括弧の直後と、閉じ括弧の直前に、空白は無い。

1 回以上起動した種類は、かかった時間のあとに、空白一つを置いて `種類=回数` で書く。`=` の前後に空白は無い。種類が複数のとき、あいだは空白一つである。順は `quick`、`implement`、`fix` である。

起動した種類が無いとき、括弧の中はかかった時間だけである。

かかった時間が 2 分 15 秒で、`quick` が 1 回、`implement` が 2 回、`fix` が 0 回のときの正常終了の行は、`処理を終了します: <id> (2m15s quick=1 implement=2)` である。

失敗のときの時間と回数の一行は、正常終了と同じ括弧だけである。

かかった時間が 2 分 15 秒で、`quick` が 1 回、ほかの種類が 0 回のときの失敗の一行は、`(2m15s quick=1)` である。

60 秒は、1 分へ繰り上げる。表記に使う秒は、0 以上 59 以下である。

分が 0 で秒が 1 以上のときは、秒の十進と `s` だけを書く。15 秒の表記は `15s` である。

秒が 0 で分が 1 以上のときは、分の十進と `m` だけを書く。2 分の表記は `2m` である。

1 秒未満のときは、`0s` と書く。

1 秒以上の経過にある 1 秒未満の端数は、切り捨てる。四捨五入は採用しない。59.6 秒の表記は `59s` である。59.9 秒の表記は `59s` である。

分が 60 以上のときは、分を時間へ繰り上げない。単位は分と秒のままである。65 分 30 秒の表記は `65m30s` である。

分、秒、回数の十進は、先頭の零を付けない。

失敗のときの時間と回数の一行は、理由の一行の直後であり、課題コメントの投稿より前である。

課題コメントの投稿の待ちは、かかった時間に含めない。

## 関係する課題

課題は、次を関係するとする。

- #6（課題ランナー: 実装依頼から実装完了まで）
- #1（パッケージ骨格と install / run CLI）
- #82（失敗した課題に理由を残し、人が着手前のラベルへ戻せるようにする）

#6 は、処理のあいだ次の課題を取らない。この要件が時間と回数を書くのは、その処理が終わるときと、`処理を開始します` のあとで `process` が失敗するときである。

#1 の設計は、標準出力に `処理を開始します: <id>`、`処理を終了します: <id>`、`終了します` を書く。この要件は、正常終了の `処理を終了します: <id>` の末尾に、かかった時間と回数の括弧を足す。その行は一行のままである。

#82 は、`process` が失敗したとき、理由の日本語一行を標準エラーに書き、同じ文字列を課題コメントにする。この要件は、その理由の一行を残す。失敗のとき、かかった時間と回数は、その理由の一行の直後の別の一行であり、課題コメントの投稿より前に書く。課題コメントには書かない。投稿の待ちは、かかった時間に含めない。

## 範囲外

次は、この要件に含めない。

- agent の中のサブエージェントの起動回数とレビュー回数を数えること
- ログをファイルや GitHub に残すこと
- 失敗の理由の課題コメントをやめること（#82）
