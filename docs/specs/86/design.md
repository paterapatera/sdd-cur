# 86 今のシステム全体を表す仕様の正本を作り、課題の差分を実装の PR で反映する

対象は [Issue #86](https://github.com/paterapatera/sdd-cur/issues/86)。課題ごとの `docs/specs/<番号>/` とは別に、今のシステムの挙動を表す仕様の正本を `docs/spec/` に置く。課題の設計には正本への差分を書き、実装のマージリクエストで正本へ反映する。

既存の `docs/specs/` を正本へ移すことと、レビュー役が読む範囲を正本に絞ることは、#87 である。この設計は、それらをしない。

重なる課題は #85 と #7 である。`docs/specs/85/design.md` と `docs/specs/7/design.md` は書き換えない。#7 の完了処理は変えない。

## 受け入れ条件

- 正本は `docs/spec/<領域>.md` に置く。課題ごとの `docs/specs/<番号>/` とは別である。
- `<領域>` は英小文字で始まり、英小文字と数字が続き、区切りのハイフンを含んでよい。ハイフンは先頭、末尾、連続には使わない。
- 正本の各要求の識別子は、`REQ-` に、十進で先頭の零の無い 1 以上の整数を続けたものである。同じ識別子は正本に一度だけある。
- 変更は、識別子を変えない。
- `docs/conventions.md` は、課題ごとの要件と設計の置き場所に加え、`docs/spec/` を正本の置き場所として定める。
- 課題ごとの `docs/specs/<番号>/requirements.md` と `design.md` の置き場所は、今の「課題ごとのファイル」のままである。
- 設計の作成役が書く課題の設計には、`## 正本への差分` がある。
- 差分の項目は、識別子ごとの追加、変更、削除である。見出しは `### 追加 <領域> REQ-<番号>`、`### 変更 <領域> REQ-<番号>`、`### 削除 <領域> REQ-<番号>` である。
- 追加は、正本に無い識別子の要求を、その領域のファイルへ足す。
- 変更は、正本にある識別子の要求の内容を、項目の本文へ変える。
- 削除は、正本にある識別子の要求を正本から除く。
- 追加、変更、削除の項目の本文は、その識別子の要求の内容である。追加と変更の本文は正本に残す内容であり、削除の本文は正本から除く内容である。差分の節だけで、何が変わるかが読める。
- 実装の作成役は、コードと同じ作業ツリーで、その差分を `docs/spec/` へ反映する。要求ファイルと設計ファイルは変えない。
- 正本の変更は、その実装のマージリクエストに入る。`commitAll` は `git add -A` のままである。
- スカッシュマージのあと、main の正本とコードは一致する。完了処理は、スカッシュマージと「マージ済み」の付与のままである。
- 実装レビュー役は、作業ツリーの正本が、その課題の設計にある差分どおりに変わったかを見る。
- #85 の検査は、追加する識別子が正本にまだ無いことを見る。
- #85 の検査は、変更する識別子と削除する識別子が正本にあることを見る。見ている正本は、差分を反映する前の正本である。
- 設計のレビュー役は、正本への差分の節の各項目が、識別子付きの追加、変更、削除のいずれかとして書かれていることを見る。
- 設計のレビュー役は、変更と削除の項目に、その識別子の要求の内容が含まれていることを見る。
- 設計のレビュー役は、差分だけで、何が変わるかが読めることを見る。
- 識別子が当時の正本に対して追加、変更、削除のどれに該当するかの機械確認は、#85 の検査が行う。
- 設計のレビュー役は、#85 の検査を通った前提で、差分が課題の受け入れ条件と矛盾しないことを見る。
- 設計のレビュー役は、#85 の検査を通った前提で、他の課題の `docs/specs/` との食い違いと巻き戻しを、従来どおり見る。
- 設計のレビュー役は、マージ後の正本が差分どおりかを見ない。
- 正本が、その課題の設計にある差分どおりに変わったかを見るのは、実装レビュー役である。

## 正本

領域ファイルの最初の非空行は `# <領域>` である。`<領域>` は、ファイル名から `.md` を除いたものと一文字も違わない。

要求の見出しは、行全体が `## REQ-<番号>` である。本文は、その次の行から、次の行頭が `## ` である行の直前までである。そこまで見出しが無いときは、ファイルの末尾までである。先頭と末尾の空行を除いて、本文は 1 文字以上である。

追加は、項目の `<領域>` のファイルの末尾へ、見出しと本文を足す。ファイルが無いときは、`# <領域>` のファイルを作ってから足す。既存の要求の順は変えない。

変更は、項目の `<領域>` のファイルにある、その識別子の本文だけを、項目の本文へ置き換える。見出しの行は変えない。ほかのファイルへ移さない。

削除は、その識別子の見出しと本文を、正本から除く。

この課題が置くファイルは、次の形である。中身の要求は、「正本への差分」の追加を、その順で書く。

```
# spec

## REQ-1

本文
```

## 差分の節

節の見出しは、行全体が `## 正本への差分` と一文字も違わない最初の一行である。節の本文は、その次の行から、次の行頭が `## ` である行の直前までである。`### ` で始まる行は、節を終わらせない。

項目の見出しは、節の中で、行全体が次のいずれかと一文字も違わない行である。

- `### 追加 <領域> REQ-<番号>`
- `### 変更 <領域> REQ-<番号>`
- `### 削除 <領域> REQ-<番号>`

`<領域>` は、決定の領域の名前である。`REQ-<番号>` は、決定の識別子である。字面は `REQ-` と `String(番号)` を連結したものと一致する。

項目の本文は、その見出しの次の行から、次の行頭が `### ` または `## ` である行の直前までである。先頭と末尾の空行を除いて、1 文字以上である。

同じ識別子は、一つの節に一度だけ書く。項目が無い節は、差分が無い。実装は `docs/spec/` を変えない。

設計の作成役は、課題の設計ごとにこの節を書く。正本のファイルは書かない。

## 検査

```ts
export function canonicalIdsFromMarkdown(markdown: string): string[]

export function readCanonicalIds(root: string): Promise<string[]>

export function validateCanonicalDelta(
  designMarkdown: string,
  canonicalIds: readonly string[],
): string[]
```

三つの関数は、`gh` を呼ばない。`canonicalIdsFromMarkdown` と `validateCanonicalDelta` はファイルを読まず、拒否しない。

`canonicalIdsFromMarkdown` は、改行を `\n` にそろえ、行全体が `## REQ-<番号>` である行の識別子を、上から返す。`<番号>` は、十進で先頭の零が無く、1 以上である。それ以外の行は返さない。同じ識別子が二度あれば、二度返す。

`readCanonicalIds` は、`root` の下の `docs/spec` を見る。ディレクトリが無いときは、空配列である。あるときは、直下のファイルのうち、名前が `.md` で終わるものを、ファイル名の昇順で読む。各ファイルを `canonicalIdsFromMarkdown` に渡し、その順で連結して返す。ディレクトリは読まない。読み取りが失敗したときは、`正本を読めません` で拒否する。

`validateCanonicalDelta` は、最初の、行全体が `## 正本への差分` である行から、次の行頭が `## ` である行の直前までを節とする。その見出しが無いときは、空配列である。節の中で、行全体が三つの項目見出しのいずれかである行だけを、上から項目とする。それ以外の行は、項目にしない。本文は見ない。

各項目の識別子を、引数の `canonicalIds` に含まれるかで見る。反映後の集合は作らない。

| 項目 | 識別子が集合にある | 違反 |
|---|---|---|
| 追加 | ある | `追加する識別子が正本にあります: <識別子>` |
| 追加 | 無い | 書かない |
| 変更 | ある | 書かない |
| 変更 | 無い | `変更する識別子が正本にありません: <識別子>` |
| 削除 | ある | 書かない |
| 削除 | 無い | `削除する識別子が正本にありません: <識別子>` |

違反は、項目の上から積む。違反が無いときは空配列である。

#85 の `validate` が、設計ファイルを形式検査の対象にするとき、`readCanonicalIds(process.cwd())` の結果と、その設計ファイルの文字列を `validateCanonicalDelta` に渡す。返った各違反を、`docs/specs/<番号>/design.md: <違反>` として、形式の違反のあとに標準エラーへ書く。一つでもあるときは、終了コードは 1 である。形式検査の対象にしない設計ファイルでは、この関数を呼ばない。要件ファイルでは呼ばない。設計 85 が検査をスキップする条件は、変えない。

`src/cli.ts` に `validate` の case があるときは、その case に上の呼び出しを足す。case が無いときは、case を新設しない。`src/cli.ts` は変えない。
