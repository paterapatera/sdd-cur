# 89 要件の現状に main の根拠を必須にし、設計に変えるファイルの一覧を書く

対象は [Issue #89](https://github.com/paterapatera/sdd-cur/issues/89)。要件の「現状」の各項目の根拠は、（`パス` の N 行）の表記だけである。設計には、見出しが `## 変えるファイル` と一文字も違わない一覧を書く。どちらも、レビューと #85 の検査で確かめる。

手を入れる対象は、要求と設計の作成役とレビュー役、実装レビュー役、#85 の検査である。

重なる課題は #85 である。比べる相手は、cc-sdd の validate-gap である。

設計 85 が検査する印、必須の節、受け入れ条件の形、番号の重複、設計のテストからの参照、反映済みの記録、曖昧な語は残す。この設計は、その上に根拠と変えるファイルの一覧を足す。`docs/specs/85/design.md` は書き換えない。

## 受け入れ条件

- 要件の「現状」の各項目の根拠は、（`パス` の N 行）の表記だけである。
- 根拠のパスは、リポジトリ相対パスである。
- 根拠の N は、一つの行番号である。
- 行の範囲は、根拠に書かない。
- 要求レビュー役は、根拠が（`パス` の N 行）の表記だけになっていない「現状」の項目を指摘する。
- 印がある要件ファイルでは、根拠に書いたファイルが main に無いとき、#85 の検査は失敗する。
- 印がある要件ファイルでは、根拠の N が 1 未満のとき、#85 の検査は失敗する。
- 印がある要件ファイルでは、根拠の N が、その main 上のファイルの行数を超えるとき、#85 の検査は失敗する。
- 設計の、変えるファイルの一覧の節の見出しは、`## 変えるファイル` と一文字も違わない。
- 設計レビュー役は、`## 変えるファイル` と一文字も違わない見出しが無い設計を指摘する。
- 印がある設計ファイルでは、#85 の検査は、`## 変えるファイル` に書いたパスを、作業ツリー上で見る。
- 設計の時点でまだ無いファイルを、`## 変えるファイル` に書いたことだけでは、#85 の検査は失敗しない。
- 実装レビュー役は、一覧に無いファイルの変更を指摘する。
- 印が無いファイルは、#85 の検査がスキップする。
- 印が無いファイルのスキップだけでは、#85 の検査は失敗しない。
- 「現状」の節が無いことだけでは、#85 の検査は失敗しない。
- `## 変えるファイル` が無いことだけでは、#85 の検査は失敗しない。

## 検査

#85 の検査は、`bun src/cli.ts validate <番号>` である。印は、設計 85 の `hasFormMarker` である。印が無いファイルは、`validateSpecForm` が空配列を返す。根拠と一覧も見ない。そのスキップだけでは、終了コードを 1 にしない。

`validateSpecForm` は、設計 85 のとおり、引数の文字列を変えず、ファイルを読まず、`gh` を呼ばない。`git` も起動しない。main を読むのは、`cmdValidate` だけである。

節の本文は、決定の「節の本文」のとおりである。見る前に、改行を `\n` にそろえる。要件の見出しは、行全体が `## 現状` である。この見出しが無いときは、根拠については失敗しない。設計の見出しは、行全体が `## 変えるファイル` である。この見出しが無いときは、そのことだけでは失敗しない。

根拠の表記は、決定の字面である。表記は一行の中で探す。改行をまたがない。「現状」の本文にある表記を、上から、重ならないように一つずつ見る。表記が一つも無いことだけでは、失敗しない。表記の前後に文があることだけでは、失敗しない。表記が無いときは、`git show` を実行しない。

表記の N は、数字列を十進整数として解釈した値である。`007` の値は 7 である。メッセージに書く `<N>` は、この値を、先頭の零の無い十進で書いたものである。

表記ごとに、`cmdValidate` は `git show main:<パス>` を一度実行する。引数は、決定の「main の読み取り」のとおりである。終了コードが 0 のときは、標準出力が空でも内容を得たものとする。終了コードが 0 以外のとき、および起動できないときは、内容を得られない。内容を得られないときは、違反 `根拠のファイルが main にありません: <パス>` を書く。得られた内容の行数は、決定の「行数」のとおりである。

値が 1 未満のときは、違反 `根拠の行番号が不正です: <N>` を書く。ファイルの内容を得られて、値が 1 以上であり、値が行数より大きいときは、違反 `根拠の行番号がファイルの行数を超えています: <パス> <N>` を書く。`<パス>` と `<N>` のあいだは、半角空白一つである。値が行数と等しいときは、この違反を書かない。ファイルの内容を得られないときは、行数の違反を書かない。

一つの表記では、ファイルの違反、行番号が 1 未満である違反、行数を超える違反のうち、当たるものを書く。一つの表記が失敗しても、うしろの表記を飛ばさない。

`## 変えるファイル` があるときは、決定の「一覧のパス」のとおりに、節本文の各行からパスを得る。パスが `..` で始まるとき、またはパスが `/` で始まるとき、その行の順に、違反 `変えるファイルのパスが不正です: <パス>` を書く。同じパスが二度あっても、行の数だけ書く。それ以外のパスは、作業ツリーに無くても違反にしない。この一覧の検査は、`git` を起動しない。作業ツリーと main の差分を見ない。

設計 85 が積む違反は残る。その相対順も残る。各ファイルでは、そのファイルの `validateSpecForm` の違反をすべて書いたあと、上の違反を書く。要件の根拠の違反を書いたあと、設計の `validateSpecForm` の違反を書く。そのあと、設計の一覧の違反を書く。ファイルを読む順と、違反を書く順は、要件、設計である。要件の読み取りが拒否されたときは、設計 85 のとおり、設計を読まず、形式の違反は書かない。

失敗と成功の終了コード、空の標準出力、標準エラーの `<相対パス>: <違反>`、ファイルを作らないこと、ファイルを変えないことは、決定の「失敗の形」のとおりである。この設計が足す違反は、決定の「足す違反」の四つだけである。

根拠の表記が無いファイルでは、`git show` を実行しなくても、今の `validate` の結果は変わらない。`## 変えるファイル` が無いファイルでは、一覧のパスを見なくても、今の `validate` の結果は変わらない。

- 印がある要件で、表記の N の値が、その main 上のファイルの行数を超えるときは、終了コード 1 である。違反は `根拠の行番号がファイルの行数を超えています: <パス> <N>` である。字面 `007` で行数が 6 のとき、`<N>` は `7` である。
- 字面 `007` で、パスが main にあり、行数が 7 のときは、この根拠については失敗しない。
- 印がある要件に、設計 85 の違反と根拠の違反が両方あるときは、`validateSpecForm` の違反が先、根拠の違反があとである。
- 要件と設計の両方に、この設計が足す違反があるときは、要件の行がすべて先、設計の行があとである。設計では、`validateSpecForm` の違反が先、一覧の違反があとである。
- 印がある設計の節本文の行が `- ../a` のときは、違反 `変えるファイルのパスが不正です: ../a` である。行が `- /a` のときは、違反 `変えるファイルのパスが不正です: /a` である。
- 行頭が `- ` でない `../a` も、違反 `変えるファイルのパスが不正です: ../a` である。
- 行が `- ./a` であることだけでは、終了コード 1 にしない。
- 印がある設計の `## 変えるファイル` に、作業ツリーにまだ無いパスを書いたことだけでは、終了コード 1 にしない。
- 根拠の表記が無い印あり要件は、`git` を起動しなくても、終了コード 0 である。
- 根拠の表記があり、内容を得るときは、起動する git は `git show main:<パス>` だけである。`main:<パス>` は一つの引数である。他の git は起動しない。試験は、引数を記録する `git` を `PATH` の先頭へ置く。記録された起動は、`show` と `main:<パス>` だけである。その `git` は、試験が用意したパスのとき、用意した内容を標準出力へ書き、終了コード 0 で終わる。用意が無いパスは、終了コード 0 以外で終わる。
- 設計 85 が既に失敗にする、必須の節の欠落は、この課題のあとでも失敗のままである。
- 成功のときも失敗のときも、検査の対象ファイルの内容は、起動前と同じである。

## 実装の順序

1. 五つのエージェントの本文へ、指定の文を足す。frontmatter は変えない。既存の文は残す。
2. `cmdValidate` へ、根拠と変えるファイルの一覧の検査を足す。各ファイルでは、`validateSpecForm` の違反のあとへ足す。main の読み取りは、`git show main:<パス>` だけである。`validateSpecForm` はファイルを読まず、`git` を起動しない。
3. `src/89.test.ts` を、「テスト」のとおり書く。既存の `src/*.test.ts` に、新しい `test` は足さない。
4. `## 正本への差分` を、`docs/spec/conventions.md`、`docs/spec/sdd.md`、`docs/spec/implement.md` へ反映する。要求ファイルと設計ファイルは変えない。
5. `bun test` が成功することを確かめる。`gh` は起動しない。
