# 89 要件の現状に main の根拠を必須にし、設計に変えるファイルの一覧を書く

対象は [Issue #89](https://github.com/paterapatera/sdd-cur/issues/89)。要件の「現状」の各項目は、バッククォートで囲んだリポジトリ相対パスと、一つの行番号だけを根拠として書く。設計には、見出しが `## 変えるファイル` である一覧を書く。どちらも検査とレビューで確かめる。

手を入れる対象は、要求と設計の作成役とレビュー役、実装レビュー役、#85 の検査である。

重なる課題は #85 である。

比べる相手は、cc-sdd の validate-gap である。

## 現状

印がある要件で必須の節は「受け入れ条件」だけである。それ以外の節は任意である（`docs/conventions.md` の 193 行）。

印がある設計で必須の節は「受け入れ条件」「範囲外」「決定」「テスト」である（`docs/conventions.md` の 195 行）。`REQUIRED_SECTIONS` の設計も、この四つだけである（`src/conventions.ts` の 528 行）。

印が無いファイルを、`validateSpecForm` は検査しない（`src/conventions.ts` の 740 行）。

`validateSpecForm` が印があるファイルで積む違反は、必須の節（`src/conventions.ts` の 747 行）、受け入れ条件の形（`src/conventions.ts` の 754 行）、番号の重複（`src/conventions.ts` の 755 行）、設計のテストからの参照（`src/conventions.ts` の 762 行）、反映済みの記録（`src/conventions.ts` の 767 行）、曖昧な語（`src/conventions.ts` の 770 行）である。根拠に書いたファイルがあること、根拠の行がファイルの行数を超えていないこと、一覧に書いたファイルがあることは、これらの行には無い。

要求作成役の起動時に読むのは `docs/policy.md` である（`agents/sdd-cur-req-author.md` の 12 行）。書いてよい挙動は、対象課題と、人がこの依頼で決めた条件だけである（`agents/sdd-cur-req-author.md` の 25 行）。現状の各項目へ main のファイルと行を書く文は、この手順に無い。

要求レビュー役が指摘するのは、次に当たるものだけである（`agents/sdd-cur-req-reviewer.md` の 63 行）。この列挙に、要件の「現状」の項目が main のファイルと行を根拠に持つかは無い。

設計作成役は、課題の設計に `## 正本への差分` の節を書く（`agents/sdd-cur-design-author.md` の 32 行）。書く手順の見出しは `## 書いてよいこと` である（`agents/sdd-cur-design-author.md` の 23 行）。この手順に、変えるファイルの一覧の節は無い。

設計レビュー役が指摘するのは、次に当たるものだけである（`agents/sdd-cur-design-reviewer.md` の 54 行）。この列挙に、変えるファイルの一覧の節が無いかは無い。

実装レビュー役が指摘するものは、作業ツリーの実装が要求どおりでないこと（`agents/sdd-cur-implement-reviewer.md` の 92 行）、設計通りでないこと（`agents/sdd-cur-implement-reviewer.md` の 93 行）、`docs/spec/` が設計の `## 正本への差分` どおりでないこと（`agents/sdd-cur-implement-reviewer.md` の 94 行）、設計の「テスト」節の実行が失敗したこと（`agents/sdd-cur-implement-reviewer.md` の 95 行）、その節の実行すべき記述をすべて実行していないこと（`agents/sdd-cur-implement-reviewer.md` の 97 行）、受け入れ手順が設計の受け入れ条件を確かめられないこと（`agents/sdd-cur-implement-reviewer.md` の 100 行）である。一覧に無いファイルの変更は、この列挙に無い。

## 受け入れ条件

- 要件の「現状」の各項目の根拠は、（`パス` の N 行）の表記だけである。
- 根拠のパスは、リポジトリ相対パスである。
- 根拠の N は、一つの行番号である。
- 行の範囲は、根拠に書かない。
- 要求レビュー役は、根拠が（`パス` の N 行）の表記だけになっていない「現状」の項目を指摘する。
- 印がある要件ファイルでは、根拠に書いたファイルが main に無いとき、#85 の検査は失敗する。
- 印がある要件ファイルでは、根拠の N が 1 未満のとき、#85 の検査は失敗する。
- 印がある要件ファイルでは、根拠の N が、その main 上のファイルの行数を超えるとき、#85 の検査は失敗する。
- 設計の、変えるファイルの一覧の節の見出しは、`## 変えるファイル` と一文字も違わない。
- 設計レビュー役は、`## 変えるファイル` と一文字も違わない見出しが無い設計を指摘する。
- 印がある設計ファイルでは、#85 の検査は、`## 変えるファイル` に書いたパスを、作業ツリー上で見る。
- 設計の時点でまだ無いファイルを、`## 変えるファイル` に書いたことだけでは、#85 の検査は失敗しない。
- 実装レビュー役は、一覧に無いファイルの変更を指摘する。
- 印が無いファイルは、#85 の検査がスキップする。
- 印が無いファイルのスキップだけでは、#85 の検査は失敗しない。
- 「現状」の節が無いことだけでは、#85 の検査は失敗しない。
- `## 変えるファイル` が無いことだけでは、#85 の検査は失敗しない。

## 決定

要件の「現状」の各項目の根拠は、（`パス` の N 行）の表記だけである。

根拠のパスは、リポジトリ相対パスである。

根拠の N は、一つの行番号である。

行の範囲は、根拠に書かない。

印がある要件ファイルでは、根拠に書いたファイルが main に無いとき、#85 の検査は失敗する。

印がある要件ファイルでは、根拠の N が 1 未満のとき、#85 の検査は失敗する。

印がある要件ファイルでは、根拠の N が、その main 上のファイルの行数を超えるとき、#85 の検査は失敗する。

設計の、変えるファイルの一覧の節の見出しは、`## 変えるファイル` と一文字も違わない。

印がある設計ファイルでは、#85 の検査は、`## 変えるファイル` に書いたパスを、作業ツリー上で見る。

設計の時点でまだ無いファイルを、`## 変えるファイル` に書いたことだけでは、#85 の検査は失敗しない。
