# 88 設計に作業の一覧を持たせ、実装を作業ごとに進める

対象は [Issue #88](https://github.com/paterapatera/sdd-cur/issues/88)。設計に作業の一覧の節を持たせ、実装の agent は、その順に、作業ごとに実装作成役を起動する。

要求の決定どおり、節の見出しは「作業の一覧」である。設計は節見出し「実装の順序」を使わない。既存設計のその見出しは、本課題の実装で置き換える。どの作業にも入っていない設計の受け入れ条件は、`bun src/cli.ts validate <番号>` が失敗させる。

比べる相手は、Spec Kit と cc-sdd の `tasks.md` である。重なる課題は #85 である。

## 受け入れ条件

- 1. 設計作成役が書く設計には、行全体が `## 作業の一覧` である節がある。
- 2. 設計作成役が書く設計は、節見出し `## 実装の順序` を使わない。
- 3. 作業の一覧の各作業は、この設計の「作業の一覧の書式」の番号を持つ。
- 4. 印がある設計では、各作業が、その設計の形を満たす受け入れ条件の番号のうち、その作業が満たすものを `[<番号>]` で挙げる。
- 6. 一度に実装できる大きさの目安は、この設計の「一度に実装できる大きさ」のとおりである。
- 7. 設計レビュー役は、形を満たす受け入れ条件の番号のうち、どの作業にも無いものを不合格として指摘する。
- 8. 設計レビュー役は、目安を超える作業を不合格として指摘し、作業の一覧の中で作業を分ける修正を求める。
- 9. 作業を分けても目安を満たせないとき、設計レビュー役はレビュー応答に、行全体が `課題全体が大きすぎる` である行を書き、人に示す内容を列挙する。この判定に、件数、行数、ファイル数などの固定の数値や式は使わない。
- 10. その示しは `skills/sdd-cur/SKILL.md` が人に行う。課題を分けるときに課題を作るのは人である。設計レビュー役は課題を作らない。
- 11. 行 `課題全体が大きすぎる` がある不合格のあと、同じ課題の設計修正役へは進まない。SDD スキルは人の判断を待つ。
- 12. 実装の agent は `skills/sdd-cur-implement/SKILL.md` であり、作業の一覧の順に、作業ごとに実装作成役を起動する。
- 13. 作業ごとに起動する実装作成役は、その作業が挙げた受け入れ条件に直結する実装だけを行う。他の受け入れ条件に直結する実装は触らない。
- 14. レビューと修正の段、および受け入れ手順の本文を書くことは、すべての作業の実装作成役が終わったあとに一度だけ行う。作業ごとには行わない。
- 15. 本課題が改めるのは、実装段の作成段だけである。実装作成役の起動回数は、作業の数である。要求と設計の段の作成は、要件 30 の一回のままである。作成ラウンドは 1 である。すべての作業のあと、1 回目の実装レビューに入る。
- 16. ある作業の実装作成役が作業ツリーを変えなかったときは、その場で理由 `実装作成が作業ツリーを変えませんでした` として止める。次の作業へ進まない。
- 17. 設計に `## 作業の一覧` が無いとき、実装の agent は実装作成役を起動せず、理由 `設計に作業の一覧がありません` で失敗する。
- 18. 印がある設計で、形を満たす受け入れ条件の番号のうち、どの作業にも無いものがあるとき、`bun src/cli.ts validate <番号>` は失敗する。違反の文言は `受け入れ条件が作業の一覧に入っていません: <番号>` であり、日本語の一行である。
- 19. どの作業にも入っていない受け入れ条件は、テストから参照されていない受け入れ条件と同じく、レビューの前の形式検査の出力を設計の修正役へ渡して直す。
- 20. 既存の `docs/specs/*/design.md` にある、行全体が `## 実装の順序` である見出しは、`## 作業の一覧` に置き換える。節の本文は変えない。課題 23 の設計は変えない。
- 21. 課題ランナーがコミットする回数は変えない。実装の agent はコミットしない。
- 22. 設計に `## 作業の一覧` があり、実装の agent が作業として読む行が一つも無いとき、実装の agent は実装作成役を起動せず、理由 `作業の一覧に作業がありません` で失敗する。終了コードと理由の書き方は、節が無いときの `設計に作業の一覧がありません` と同じである。

## 作業の一覧の書式

見出し行は、行全体が `## 作業の一覧` と一文字も違わない行である。本文は、その次の行から、行頭が `## ` である行の直前までである。そのような行が無いときは、ファイルの末尾までである。`### ` で始まる行は、節を終わらせない。

印がある設計の作業の項目は、行頭が `- ` である行である。行頭より前に空白がある行は、項目ではない。項目行は、次をこの順で連結する。

1. `- `（ハイフン、半角空白）
2. 番号。規則は、設計 85 の受け入れ条件の番号と同じである。十進であり、先頭の零は無く、1 以上である。字面は `String(番号)` と一致する
3. `. `（ピリオド、半角空白）
4. 本文。1 文字以上である。先頭と末尾は半角空白でない

本文中の `[<番号>]` が、その作業が満たす受け入れ条件の番号である。角括弧は ASCII の `[]` である。番号の探し方は、設計 85 のテスト項目と同じである。1 以上であり、字面が `String(番号)` と一致するものだけを参照とする。印がある設計では、各作業の本文が、この参照を一つ以上持つ。

作業の番号が飛んでいても、重なっていても、この書式としては失敗にしない。`validate` は、作業の番号の重複、欠番、参照先が受け入れ条件に無いことを、失敗にしない。

例は、次である。

```
- 1. `src/cli.ts` にサブコマンドを足す。[1]
- 2. スキルの手順を変える。[2][3]
```

印が無い設計の、置換後の作業は、置換前の行のままである。行頭が `<番号>. ` であり、`- ` では始まらない。この行に `[<番号>]` は無くてよい。`validate` は印が無いファイルを見ない。

## 一度に実装できる大きさ

一つの作業が一度に実装できる大きさであるとは、次のとおりである。

- `[<番号>]` を一つ以上持つ作業では、その番号の受け入れ条件に直結する実装を、他の受け入れ条件に直結する実装を含めず、実装作成役の一回の起動で書き終えられる
- `[<番号>]` が無い作業では、その作業の行に書かれた実装を、一回の起動で書き終えられる

目安を超えるのは、上を満たさず、作業の一覧の中でその作業を複数の作業に分ければ、分けた各作業が上を満たすときである。

課題全体が大きすぎるのは、作業の一覧の中で作業をどう分けても、分けたあとのどれかが上を満たさないときである。受け入れ条件の件数、行数、ファイル数、その他の固定の数値や式では判定しない。

この目安を見るのは、設計レビュー役である。`validate` は見ない。

## 設計の手順

変えるファイルは、`agents/sdd-cur-design-author.md`、`agents/sdd-cur-design-reviewer.md`、`skills/sdd-cur/SKILL.md` の「設計」である。フロントマターは変えない。`src/agents.test.ts` が今求める本文の文言は残す。

### 設計作成役

設計作成役は、設計ファイルに作業の一覧の節を書く。節見出し `## 実装の順序` は書かない。

作業の項目は、「作業の一覧の書式」の、印がある設計の項目である。各項目は、その作業が満たす受け入れ条件の番号を `[<番号>]` で一つ以上挙げる。要件の受け入れ条件の番号は挙げない。

### 設計レビュー役

今の指摘に、次を足す。どれも不合格である。指摘が一つでもあるときの判定は、今のとおり `判定: 不合格` である。

- 行全体が `## 作業の一覧` である節が無い
- 行全体が `## 実装の順序` である節がある
- 形を満たす受け入れ条件の番号のうち、どの作業の `[<番号>]` にも無いものがある。差分は、その番号を既存の作業の本文へ足すか、その番号を挙げる作業を足す修正である
- 印がある設計の作業の項目に、`[<番号>]` が一つも無い。差分は、その作業が満たす番号を `[<番号>]` で足す修正である
- 目安を超える作業がある。指摘に `目安を超える` を書く。差分は、作業の一覧の中で、その作業を目安を満たす複数の作業に分ける修正である。このとき、行 `課題全体が大きすぎる` は書かない

形を満たす受け入れ条件の項目が一つも無いときは、番号がどの作業にも無いことだけでは指摘しない。印が無い既存設計を、番号が無いことだけで不合格にしない。

作業をどう分けても目安を満たせないときは、次のとおり書く。

- 指摘に、行全体が `課題全体が大きすぎる` である行を書く。どの受け入れ条件が、分けても一回の実装作成役では書き終えられないかを列挙する。この列挙が、人に示す内容である
- 差分は「差分なし」である
- 確認は `確認: なし` である。この行は、課題、要件、人が決めた条件から読めない点ではない
- 判定は `判定: 不合格` である
- 課題を作る文は書かない。課題の番号や題の案は書かない

出力の四項目は、設計 30 のままである。

### SDD スキル

`skills/sdd-cur/SKILL.md` の「設計」で、判定行が `判定: 不合格` のとき、今の手順で連続不合格を増やしたあと、確認行を見る前に、判定行より前を見る。行全体が `課題全体が大きすぎる` と一文字も違わない行があるときは、確認行では分岐しない。

このときは、レビュー応答を人に見せる。設計修正役を起動しない。設計作成役を起動しない。レビューを再び起動しない。確認コメントは投稿しない。課題を作らない。実装依頼に進めるとは伝えない。人の判断を待つ。

この行が無いときは、今の `確認: あり` と `確認: なし` のままである。要求の段は変えない。設計の段の、作成役を起動する回数は変えない。`validate` をレビューの前に実行する手順は、設計 85 のままである。

## 実装の agent

変えるファイルは、`skills/sdd-cur-implement/SKILL.md` の「実装」と、`agents/sdd-cur-implement-author.md` である。フロントマターは変えない。`## レビュー` と `## 禁止` の、今の文言は残す。`src/agents.test.ts` と `src/runner.test.ts` が今求める文言は残す。

### スキルの起動

実装作成役を一度だけ起動する段落を、次に変える。

1. `docs/specs/<番号>/design.md` を読む。
2. 行全体が `## 作業の一覧` である最初の見出しが無いときは、実装作成役を起動しない。理由は `設計に作業の一覧がありません` である。agent は失敗で終える。終了コードは 0 以外である。理由は日本語の一行であり、標準エラーの最初の非空行、それが空のときは標準出力の最初の非空行に書く。
3. 見出しがあるときは、「作業の一覧の書式」の本文を取る。
4. 本文の上から、作業の行を集める。作業の行は、行頭が `- <番号>. ` である行と、行頭が `<番号>. ` である行である。どちらでもない行は、作業ではない。
5. 集めた作業の行が一つも無いときは、実装作成役を起動しない。理由は `作業の一覧に作業がありません` である。agent は失敗で終える。終了コードと理由の書き方は、見出しが無いときの `設計に作業の一覧がありません` と同じである。
6. 集めた順に、実装作成役を起動する。同時には起動しない。次の作業は、前の作業が作業ツリーを変えたあとである。`model` は渡さない。渡すものは、課題番号、題、要件と設計のパス、その作業の行、その行の `[<番号>]` である。
7. その起動が作業ツリーを変えなかったときは、次の作業を起動しない。受け入れ手順の本文を書かない。レビューを起動しない。理由は `実装作成が作業ツリーを変えませんでした` である。1 回の agent 起動の失敗である。終了コードと理由の書き方は、今のその失敗と同じである。
8. すべての作業の起動が作業ツリーを変えたあと、親が受け入れ手順の本文を、渡された絶対パスへ一度だけ書く。印の行は書かない。作業ごとに書かない。書いたものを作業ごとに結合しない。
9. そのあと、今の「レビュー」に入る。1 回目の実装レビューは、このときである。作業ごとにレビューしない。作業ごとに修正しない。

作業の一覧を上から一度起動することが、作成ラウンド 1 回である。レビューの不合格のあと、実装作成役は起動しない。二度目の作成ラウンドは無い。

スキルはコミットしない。`src/runner.ts` は変えない。

### 実装作成役

親が渡した一つの作業だけを実装する。

`[<番号>]` が一つ以上あるときは、その番号のうち、設計の「受け入れ条件」節にあるものに直結する実装だけを行う。他の受け入れ条件に直結する実装は触らない。節に無い番号は、実装の対象にしない。複数の作業が同じ番号を挙げたときは、それぞれの起動が、その番号に直結する実装を行ってよい。

`[<番号>]` が無いときは、その作業の行に書かれた実装だけを行う。他の作業の行に書かれた実装は行わない。

要求ファイルと設計ファイルは変えない。手順ファイルは変えない。作業ツリーを変えないときは、実装を書かずに止まる。

## 形式検査

足す先は、設計 85 の `validateSpecForm` である。引数、印が無いときの空配列、既存の違反の順と文言は変えない。この課題は、設計 85 の検査を新たに定義しない。関数が作業ツリーに無いときは、設計 85 の実装をこの課題の中で作らない。

`kind` が `design` であり、印があるときだけ、次を積む。場所は、設計 85 の違反の並びの、テスト参照の違反のうしろ、反映済みの違反の前である。

対象の番号は、その設計の、形を満たす受け入れ条件の番号である。形が不正な行は、対象にしない。作業の項目は、印がある設計の、`- <番号>. ` の行だけである。`<番号>. ` の行は、作業に数えない。

対象の番号のうち、どの作業の `[<番号>]` にも無いものを、`受け入れ条件が作業の一覧に入っていません: <番号>` として、番号の昇順で、一度ずつ積む。`## 作業の一覧` が無いときは、作業はゼロである。対象の番号は、すべてこの違反になる。必須の節の違反には、作業の一覧を足さない。`必須の節がありません: 作業の一覧` は書かない。

同じ番号が複数の作業にあっても、この違反にはしない。作業が参照する番号が、形を満たす受け入れ条件に無くても、そのための違反は書かない。

`kind` が `requirements` のときは、この違反を積まない。

コマンドの終了コード、標準出力が空であること、標準エラーの一行が `docs/specs/<番号>/design.md: ` に違反の文言を続けることは、設計 85 のままである。したがって、失敗の理由は日本語の一行である。

検査が失敗したときは、設計 85 のとおり、設計レビュー役を起動せず、標準エラーの全文を `sdd-cur-design-fixer` に渡す。新しい渡し方は作らない。実行するのは、設計 85 のとおり、`skills/sdd-cur/SKILL.md` と `skills/sdd-cur-quick/SKILL.md` がレビューの前に実行する `bun src/cli.ts validate <番号>` である。本課題は、quick のスキルの文言を変えない。

`docs/conventions.md` の、設計 85 が足した節の末尾に、次を足す。設計 85 が書いた箇条の字面は変えない。その節がまだ無いときは、ファイルの末尾に、同じ四つの箇条を足す。既存の節の字面は変えない。

- 印がある設計の作業の一覧の見出しは `## 作業の一覧` である
- 作業の項目は、行頭が `- ` であり、`- <番号>. ` に続く本文を持つ
- 作業が満たす受け入れ条件の番号は、本文の `[<番号>]` である
- 形を満たす受け入れ条件の番号のうち、どの作業の `[<番号>]` にも無いものは、`受け入れ条件が作業の一覧に入っていません: <番号>` で失敗する

## 既存設計の置換

`docs/specs/*/design.md` の、行全体が `## 実装の順序` と一文字も違わない行だけを、`## 作業の一覧` に置き換える。節の本文は、一文字も変えない。受け入れ条件の項目へ番号は足さない。印は付けない。`[<番号>]` は足さない。

この見出しが無い設計は変えない。課題 23 の `docs/specs/23/design.md` は、その見出しが無いので変えない。`requirements.md` は変えない。

置換後の `<番号>. ` の行は、実装の agent が読む作業の行である。`[<番号>]` が無いので、実装作成役はその行に書かれた実装だけを行う。
