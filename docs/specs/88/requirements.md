# 88 設計に作業の一覧を持たせ、実装を作業ごとに進める

対象は [Issue #88](https://github.com/paterapatera/sdd-cur/issues/88)。設計に、受け入れ条件と結び付いた作業の一覧の節を持たせる。実装の agent は、作業ごとに実装作成役を起動する。

比べる相手は、Spec Kit と cc-sdd の `tasks.md` である。

重なる課題は #85 である。

## 現状

この作業ツリーの `docs/specs/*/design.md` は 43 件ある。42 件に「実装の順序」の節がある。節は、実装の手順の箇条である。各箇条は、その手順が満たす受け入れ条件の番号を挙げていない。課題 23 の設計には、「実装の順序」の節が無い。

設計作成役 `sdd-cur-design-author` の手順に、作業の一覧を書くことは無い。設計レビュー役 `sdd-cur-design-reviewer` が指摘するものに、どの作業にも入っていない受け入れ条件は無い。一度に実装できる大きさを超える作業も無い。

`skills/sdd-cur-implement/SKILL.md` は、実装作成役 `sdd-cur-implement-author` を一度起動する。作業ツリーを変えないで止まったときは、レビューを起動しない。理由は `実装作成が作業ツリーを変えませんでした` である。agent は失敗で終える。作業ツリーを変えたあとは、受け入れ手順の本文をレビューの前に一度書き、レビューと修正の段に入る。作業ごとに実装作成役を起動する手順は、このスキルに無い。

課題ランナーは、実装の agent が終わったあと、変更があるときにコミットを一つ作る。`skills/sdd-cur-implement/SKILL.md` はコミットしない。

#85 の要件は、形式検査のサブコマンド名を `validate` とし、呼び出しを `bun src/cli.ts validate <番号>` とする。この作業ツリーの `src/cli.ts` のサブコマンドに `validate` は無い。#85 の要件では、新形式の印がある設計ファイルの受け入れ条件のうち、そのファイルの「テスト」節から参照されていないものがあるとき、検査は失敗する。作業の一覧に入っているかは見ない。#85 の要件は、要求作成役と設計作成役の手順を変えない、としている。

## 受け入れ条件

- 設計作成役が書く設計には、作業の一覧の節がある。
- 作業の一覧の節の見出しは「作業の一覧」である。
- 設計は「実装の順序」を使わない。
- 既存設計の「実装の順序」は、本課題の実装で「作業の一覧」に置き換える。
- 作業の一覧の各作業は、番号を持つ。
- 作業の一覧の各作業は、設計ファイルの「受け入れ条件」節の番号のうち、その作業が満たすものを挙げる。
- 設計レビュー役は、どの作業にも入っていない受け入れ条件を指摘する。
- 一度に実装できる大きさの目安は、設計で書く。
- 設計レビュー役は、一度に実装できる大きさを超える作業を、不合格として指摘する。
- その指摘は、作業の一覧の中で作業を分ける修正を求める。
- 課題全体が大きすぎるときだけ、課題を分けることを人に示す。
- その示しは、親である SDD スキルが人に行う。
- 設計レビュー役は、その示しをレビュー応答で列挙する。
- 「課題全体が大きすぎる」の判定に、要件は固定の数値や式を書かない。
- 作業を作業の一覧の中で分けても一度に実装できる大きさの目安を満たせないとき、設計レビュー役はレビュー応答で「課題全体が大きすぎる」と述べる。
- 課題を分けるときに、課題を作るのは人である。
- 設計レビュー役は、課題を作らない。
- 設計レビュー役が課題を分けることを人に示したあと、同じ課題の設計修正役へは進まない。
- そのあと、SDD スキルは人の判断を待つ。
- 実装の agent は、`skills/sdd-cur-implement/SKILL.md` である。
- 実装の agent は、作業ごとに実装作成役を起動する。
- 実装の agent は、作業の一覧の順に実装作成役を起動する。
- 作業ごとに起動する実装作成役は、その作業が挙げた設計の受け入れ条件に直結する実装だけを行う。
- その作業では、他の受け入れ条件に直結する実装は触らない。
- レビューと修正の段は、作業ごとの実装作成役の起動がすべて終わったあとに行う。
- レビューと修正の段は、作業ごとに行わない。
- 実装の agent は、受け入れ手順の本文を、すべての作業の実装作成役が終わったあと、レビュー段の前に一度だけ書く。
- 本課題は、実装段のみ要件 30 を改める。要求と設計の段は、要件 30 のままである。
- 1 回の agent 起動における実装の「作成」段は、作業の一覧の順に実装作成役を起動する。起動回数は、作業の数に応じる。作業が複数あるときは、複数回である。
- すべての作業の実装作成役が終わってから、1 回目の実装レビューに入る。
- 作成ラウンドは 1 である。
- ある作業の実装作成役が作業ツリーを変えなかったときは、その場で失敗として止める。
- そのとき、次の作業へ進まない。
- その失敗は、1 回の agent 起動として、現行の `実装作成が作業ツリーを変えませんでした` と同様に扱う。
- 設計に「作業の一覧」の節が無いとき、実装の agent は実装作成役を起動せず失敗する。
- 設計の受け入れ条件の番号のうち、どの作業にも入っていないものがあるとき、#85 の形式検査（`bun src/cli.ts validate <番号>`）は失敗する。
- その失敗の理由は、日本語の一行である。
- どの作業にも入っていない受け入れ条件は、テストから参照されていない受け入れ条件で失敗するのと同様、機械検査で直す。
- 課題ランナーがコミットする回数は、変えない。

## 決定

作業の一覧の節の見出しは「作業の一覧」に固定する。

設計は「実装の順序」を使わない。

既存設計の「実装の順序」は、本課題の実装で「作業の一覧」に置き換える。

「実装の順序」のままにすることは採用しない。

作業の一覧の各作業が挙げる受け入れ条件の番号は、設計ファイルの「受け入れ条件」節の番号である。

#85 の検査がどの作業にも入っていない受け入れ条件を見るときの対象も、設計の受け入れ条件の番号である。

要件の受け入れ条件の番号は採用しない。

設計の受け入れ条件の番号のうち、どの作業にも入っていないものがあるとき、#85 の形式検査（`bun src/cli.ts validate <番号>`）は失敗する。

失敗の理由は日本語の一行である。

どの作業にも入っていない受け入れ条件は、テストから参照されていない受け入れ条件で失敗するのと同様、機械検査で直す。

設計レビュー役だけで足りることは採用しない。

作業ごとに起動する実装作成役は、その作業が挙げた設計の受け入れ条件に直結する実装だけを行う。その作業では、他の受け入れ条件に直結する実装は触らない。

各作業で設計全体を毎回実装することは採用しない。

実装の agent は、受け入れ手順の本文を、すべての作業の実装作成役が終わったあと、レビュー段の前に一度だけ書く。

作業ごとに書くことは採用しない。

作業ごとに書いて結合することも採用しない。

ある作業の実装作成役が作業ツリーを変えなかったときは、その場で失敗として止める。次の作業へ進まない。1 回の agent 起動として、現行の `実装作成が作業ツリーを変えませんでした` と同様に扱う。

変更なしをスキップして次へ進むことは採用しない。

設計に「作業の一覧」の節が無いとき、実装の agent は実装作成役を起動せず失敗する。

後方互換で 1 回だけ起動することは採用しない。

「実装の順序」だけがあるときにそれで複数起動することも採用しない。

一度に実装できる大きさの目安は、設計で書く。

一度に実装できる大きさを超える作業は、設計レビューで不合格として指摘する。

作業の一覧の中で作業を分ける修正を求める。

課題全体が大きすぎるときだけ、課題を分けることを人に示す。

示すのは、親である SDD スキルである。

設計レビュー役は、その内容をレビュー応答で列挙する。

「課題全体が大きすぎる」の判定に、要件は固定の数値や式を書かない。

作業を作業の一覧の中で分けても一度に実装できる大きさの目安を満たせないとき、設計レビュー役はレビュー応答で「課題全体が大きすぎる」と述べる。

設計レビュー役は、課題を作らない。

作業の大きさと課題分割を同じ目安だけで扱うことは採用しない。

課題分割を人の任意だけにすることは採用しない。

設計レビュー役が課題を分けることを人に示したあと、同じ課題の設計修正役へは進まない。

親である SDD スキルは、人の判断を待つ。

示しは参考情報として設計修正を通常続けることは採用しない。

本課題は、実装段のみ要件 30 を改める。要求と設計の段は、要件 30 のままである。

1 回の agent 起動における実装の「作成」段は、作業の一覧の順に実装作成役を起動する。起動回数は、作業の数に応じる。作業が複数あるときは、複数回である。

すべての作業の実装作成役が終わってから、1 回目の実装レビューに入る。

作成ラウンドは 1 である。

## 範囲外

次は、この要件に含めない。

- 作業ごとのコミット。課題ランナーがコミットする回数は変えない
- 失敗した作業からの再開
- 作業を並列に実装すること
