# 85 要件と設計の形を決め、CLI で形式を検査する

対象は [Issue #85](https://github.com/paterapatera/sdd-cur/issues/85)。受け入れ条件に番号と決まった文の形を持たせ、設計のテストと結び付ける。機械的に見られる形式は CLI で検査し、LLM のレビューの前に直す。

受け入れ条件の文の形は、設計で決める。

比べる相手は、cc-sdd の EARS 形式と、OpenSpec の `openspec validate` である。

## 現状

`docs/conventions.md` が要件と設計に求めるのは、最初の非空行が `# <番号> ` で始まり、その後ろに題が一つ以上あることだけである。判定は `src/conventions.ts` の `isSpecHeading` である。

設計には「受け入れ条件」「範囲外」「決定」「テスト」の節があることが多い。これらを必須とする決まりは、`docs/conventions.md` に無い。受け入れ条件の項目に番号は無い。設計の「テスト」節の項目は、確かめる受け入れ条件の番号を持たない。

要件の受け入れ条件も、番号の無い箇条である。

`src/cli.ts` のサブコマンドは、`install`、`run`、`labels`、`candidates`、`show`、`branch`、`confirm`、`close`、`reflect`、`complete` である。課題番号を受け取って要件と設計の形式を検査するサブコマンドは無い。

反映済みの回答は、要件または設計のファイル末尾に、`docs/conventions.md` の記録の形で、取り込んだ回答コメントの `id` だけを書く。印は `sdd-cur:reflected` である。

要求レビュー役 `sdd-cur-req-reviewer` は、一つの要求が二通り以上に読めないか、満たされたかを判定できるかを、LLM で見る。要求作成役 `sdd-cur-req-author` と設計作成役 `sdd-cur-design-author` の手順に、受け入れ条件へ番号を付けること、および設計の「テスト」節へ確かめる番号を書くことは、無い。

`skills/sdd-cur/SKILL.md` は、要求のレビュー役 `sdd-cur-req-reviewer` と、設計のレビュー役 `sdd-cur-design-reviewer` を起動する前に、形式の検査を実行しない。要求の修正役は `sdd-cur-req-fixer`、設計の修正役は `sdd-cur-design-fixer` である。

`skills/sdd-cur-quick/SKILL.md` は、人を通さずに進める軽微な修正のスキルである。要件の段で `sdd-cur-req-reviewer` を、設計の段で `sdd-cur-design-reviewer` を起動する前に、形式の検査を実行しない。

## 受け入れ条件

- 新形式の印がある要件ファイルと、新形式の印がある設計ファイルの受け入れ条件の各項目は、番号を持つ。
- 新形式の印がある要件ファイルと、新形式の印がある設計ファイルの受け入れ条件の各項目は、条件、主体、結果が分かる決まった文の形で書く。
- 受け入れ条件の文の形は、設計で決める。
- 新形式の印がある設計ファイルの「テスト」節の各項目は、確かめる受け入れ条件の番号を持つ。
- その番号は、設計ファイルの受け入れ条件の番号である。
- `docs/conventions.md` は、受け入れ条件の各項目が番号を持つことを規則として書く。
