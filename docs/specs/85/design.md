# 85 要件と設計の形を決め、CLI で形式を検査する

対象は [Issue #85](https://github.com/paterapatera/sdd-cur/issues/85)。新形式の印がある要件と設計について、受け入れ条件の番号と文の形、設計のテストからの参照、必須の節、反映済みの記録、曖昧な語を検査する。呼び出しは `bun src/cli.ts validate <番号>` である。

見出し、パス、反映済みの記録の形は、設計 4 と `docs/conventions.md` のままである。この設計は、その上に印と `validate` を足す。比べる相手は、cc-sdd の EARS 形式と、OpenSpec の `openspec validate` である。

## 受け入れ条件

- 新形式の印は、先頭の空行を除いた最初の非空行の、次の非空行が `<!-- sdd-cur:form -->` と一文字も違わないことである。
- 印が無いファイルは、`validate` がそのファイルの検査をスキップする。スキップしただけでは、終了コードを 1 にしない。
- 印がある要件ファイルと、印がある設計ファイルの受け入れ条件の各項目は、番号を持つ。
- その各項目は、条件、主体、結果が、この順のラベルで分かる一行である。
- 印がある設計ファイルの「テスト」節の各項目は、その設計ファイルの受け入れ条件の番号を `[<番号>]` で持つ。
- その番号がテストから参照されていないとき、検査は失敗する。
- `docs/conventions.md` は、印、受け入れ条件の番号と文の形、設計のテストの参照、曖昧な語の一覧を規則として書く。
- 上の形式の判定は、`src/conventions.ts` の `validateSpecForm` にある。
- 形式検査のサブコマンド名は `validate` である。呼び出しは `bun src/cli.ts validate <番号>` である。
- 要件ファイルで必須の節は、「受け入れ条件」である。それ以外の節は任意である。
- 設計ファイルで必須の節は、「受け入れ条件」「範囲外」「決定」「テスト」である。
- 印があるファイルで、必須の節が抜けているとき、検査は失敗する。
- 番号の重複は、各ファイルの中の、形を満たす受け入れ条件の番号だけを見る。要件と設計は別々に見る。
- 印があるファイルに反映済みの開始行が無いときは、その形では失敗しない。開始行があるときは、`readReflectedIds` が拒否しない形だけを認める。
- 印があるファイルに、この設計で固定した曖昧な語があるとき、検査は失敗する。一覧は `docs/conventions.md` と `src/conventions.ts` にある。
- 成功の終了コードは 0 である。失敗の終了コードは 1 である。失敗の理由は、標準エラーへ、日本語の一行ずつ書く。
- `skills/sdd-cur/SKILL.md` と `skills/sdd-cur-quick/SKILL.md` は、要求のレビュー役を起動する前に、要件ファイルがあるときだけ、この検査を実行する。
- 同じ二つのスキルは、設計のレビュー役を起動する前に、設計ファイルがあるときだけ、この検査を実行する。
- その段のファイルが無いときは、検査を実行しない。実行しないことだけでは失敗にしない。
- 要求の段で検査が失敗したときは、`sdd-cur-req-reviewer` を起動しない。標準エラーを `sdd-cur-req-fixer` に渡す。
- 設計の段で検査が失敗したときは、`sdd-cur-design-reviewer` を起動しない。標準エラーを `sdd-cur-design-fixer` に渡す。
- 要求作成役と設計作成役の手順は、変えない。
- `validate` をレビューの前に実行するのは、この二つのスキルだけである。
- `bun test` は `gh` を起動しない。

## 決定

| 項目 | 内容 |
|---|---|
| 印 | `sdd-cur:form`。行は `<!-- sdd-cur:form -->` である。先頭の空行を除いた最初の非空行の、次の非空行がこの行と一文字も同じときだけ、新形式である |
| 旧形式 | 上の行が無いファイルである。別の印は置かない。`validate` は検査をスキップする。スキップだけでは終了コードを 1 にしない |
| このファイル | 印は付けない。曖昧な語の一覧を本文に書く。項目は、今の設計ファイルと同じ、番号の無い箇条である。`validate` は印が無いので、このファイルを検査しない |
| 文の形 | 受け入れ条件の項目は一行である。条件、主体、結果を、この順のラベルで書く。EARS の WHEN と shall が分ける三つの役と同じ三つを見る。英語の WHEN、shall と、OpenSpec のシナリオ（GIVEN、WHEN、THEN）は、印にも検査にも使わない |
| 意味 | 検査しない。レビュー役が今どおり見る |
| 必須の節 | 要件は `## 受け入れ条件` だけである。`## 現状` や `## 範囲外` などは任意である。設計は `## 受け入れ条件`、`## 範囲外`、`## 決定`、`## テスト` である。見出しの行は、この文字列と一文字も違わない |
| 番号 | ファイルの中の、形を満たす受け入れ条件だけで重複を見る。1 から連続でなくてよい。要件の番号と設計の番号が同じでも、ファイルが別なら重複ではない |
| テストの参照 | 設計ファイルだけである。項目は行頭の `- ` であり、`[<番号>]` でその設計の受け入れ条件を参照する。参照されない受け入れ条件があると失敗する。要件ファイルの「テスト」節は見ない |
| 反映済み | 印があるファイルで `readReflectedIds` を呼ぶ。開始行が無いときは空配列であり、失敗しない。拒否されたときは、その理由で失敗する。印が無いファイルでは呼ばない |
| 曖昧な語 | 下の一覧で固定する。改行をそろえた本文の部分文字列である。囲みコードブロックの中も見る。大文字と小文字は区別する。一覧は `docs/conventions.md` と `ambiguousWords` に、同じ順で置く |
| 判定 | `validateSpecForm`。ファイルは読まない。文字列を受け取り、違反の配列を返す。拒否しない。`gh` は呼ばない |
| コマンド | `bun src/cli.ts validate <番号>`。番号は `parseIssueNumberString` で読む。ファイルは `readSpecFile` で読む。`gh` は起動しない |
| 無いファイル | コマンドは、無いファイルをスキップする。スキップだけでは終了コードを 1 にしない。両方無いときも、終了コードは 0 である。スキルは、その段のファイルが無いとき、コマンドを実行しない |
| 失敗 | 終了コードは 1 である。標準出力は空である。理由は標準エラーへ、日本語の一行ずつである。成功と失敗の見分けは、終了コードだけである |
| スキル | レビュー役を起動する直前にだけ実行する。作成役の前には実行しない。失敗はレビューの連続不合格に数えない。レビュー役の判定行、確認行、やり直し、回数、モデルは変えない |
| 修正役へ渡すもの | 失敗したコマンドの標準エラーの全文である。行をファイルで絞り込まない。レビューの差分は渡さない |

曖昧な語の一覧は、次の十八語である。この順で固定する。

```

できるだけ

使いやすく
柔軟に

一般的に
望ましくは
できれば
TBD
TODO
FIXME
```

`不適切に` は `適切に` を含む。部分文字列なので、違反になる。`fixme` は `FIXME` と違う。違反にしない。

## 印

```ts
export const formMarker = "sdd-cur:form"
export const formMarkerLine = `<!-- ${formMarker} -->`
```

`formMarkerLine` は、`<!--`、半角空白、`formMarker`、半角空白、`-->` を、この順で連結した文字列である。`src/conventions.ts` ではこの定数を使い、行の字面を別の場所で組み立て直さない。

```ts
export function hasFormMarker(markdown: string): boolean
```

`hasFormMarker` は、改行を `\n` にそろえる。`\r\n` と単独の `\r` は `\n` になる。`trim` して空でない行を、上から順に見る。そのような行が 2 行未満のときは false である。2 行目が `formMarkerLine` と一文字も同じときだけ true である。1 行目の内容は見ない。比較は、`trim` した値では見ない。行の前後に空白があれば false である。印が 3 行目以降の非空行にあるときも false である。

## 受け入れ条件の形

印があるファイルの、最初の `## 受け入れ条件` の本文が、受け入れ条件である。本文は、その見出し行の次の行から、行頭が `## ` である行の直前までである。そこまで見出しが無いときは、ファイルの末尾までである。`### ` で始まる行は、節を終わらせない。同じ見出しがうしろに再びあっても、二度目以降は別の節の始まりであり、受け入れ条件の項目には使わない。

本文の行のうち、`trim` して空の行は飛ばす。それ以外の各行は、次をこの順で連結した一行でなければならない。

1. `- `（ハイフン、半角空白）
2. 番号。十進であり、先頭の零は無く、1 以上の安全な整数である。字面は `String(番号)` と一致する
3. `. 条件: `（ピリオド、半角空白、`条件:`、半角空白）
4. 条件。1 文字以上である。先頭と末尾は半角空白でない。文字列 ` 主体: ` を含まない
5. ` 主体: `（半角空白、`主体:`、半角空白）
6. 主体。1 文字以上である。先頭と末尾は半角空白でない。文字列 ` 結果: ` を含まない
7. ` 結果: `（半角空白、`結果:`、半角空白）
8. 結果。1 文字以上である。先頭と末尾は半角空白でない

全角のコロン、全角の空白、`．` は使わない。この形を満たす行だけが、番号を持つ項目である。満たさない行は、`受け入れ条件の形が不正です: <行>` である。`<行>` は、その行の字面である。番号の重複には数えない。

重複は、形を満たす項目の番号が、同じファイルの中に二度以上あることである。違反は、`受け入れ条件の番号が重複しています: <番号>` である。`<番号>` は十進で、先頭の零は無い。同じ番号は一度だけ、昇順で書く。

要件の `validateSpecForm` は、この節だけを見る。設計も、同じ形である。

節の見出しが無いときは、項目の検査はしない。

## 必須の節

見出し行は、行全体が次と一文字も違わない行である。

| ファイル | 必須の見出し |
|---|---|
| 要件 | `## 受け入れ条件` |
| 設計 | `## 受け入れ条件`、`## 範囲外`、`## 決定`、`## テスト` |

印があるファイルで、必須の見出しが一つも無いとき、違反は `必須の節がありません: <節名>` である。`<節名>` は、見出しの `## ` よりうしろである。要件では「受け入れ条件」、設計では「受け入れ条件」「範囲外」「決定」「テスト」の順で、無いものだけを書く。

`## 範囲外` と `## 決定` の本文は、節があること以外は検査しない。曖昧な語と反映済みは、ファイル全体を見る。

## 設計のテスト

印がある設計ファイルで、`## 受け入れ条件` と `## テスト` の両方があるときだけ、参照を検査する。どちらかが無いときは、参照の違反は書かない。必須の節の違反は、別に書く。

テストの項目は、`## テスト` の本文のうち、行頭が `- ` である行である。行頭より前に空白がある行は、項目ではない。本文の、項目でない行は参照に使わない。

項目行のうち、`[1-9]` で始まり、そのあと数字が続く、角括弧の番号を探す。角括弧は ASCII の `[]` である。その番号が 1 以上の安全な整数であり、字面が `String(番号)` と一致するものだけを、その項目の参照とする。一つも無い項目は、`テストが受け入れ条件を参照していません: <行>` である。

参照した番号が、その設計ファイルの、形を満たす受け入れ条件の番号に無いときは、`テストが参照する受け入れ条件がありません: <番号>` である。同じ番号は一度だけ、項目の上から、項目の中では左から、最初に現れた順で書く。

形を満たす受け入れ条件の番号のうち、どの項目の参照にも無いものは、`受け入れ条件がテストから参照されていません: <番号>` である。番号の昇順で、一度ずつ書く。

要件の `validateSpecForm` は、要件ファイルに「テスト」節があっても、参照の違反は書かない。

## 反映済み

印があるファイルでは、`readReflectedIds` を呼ぶ。空配列のときは、反映済みの違反は書かない。拒否されたときは、その理由の文字列を、そのまま一つの違反にする。理由は、設計 4 の `反映済みの記録が複数あります` と `反映済みの記録を解釈できません` のままである。この設計は、記録の形を足さない。

印が無いファイルでは、`readReflectedIds` を呼ばない。記録が壊れていても、`validate` は失敗にしない。`show` と `reflect` が記録を読む規則は、変えない。

## 曖昧な語

```ts
export const ambiguousWords: readonly string[]
```

`ambiguousWords` は、決定の十八語を、その順で持つ。要素の追加、削除、入れ替えはしない。

印があるファイルでは、改行を `\n` にそろえた本文に、各語が部分文字列として含まれるかを、一覧の順に見る。含まれる語ごとに、`曖昧な語があります: <語>` を一つ書く。同じ語が二度以上あっても、違反は一つである。前後の文字では区切らない。囲みコードブロックの中も、反映済みの記録の中も、見る。

印が無いファイルでは、この検査をしない。

## 判定

```ts
export function validateSpecForm(
  kind: "requirements" | "design",
  markdown: string,
): string[]
```

`validateSpecForm` は引数の文字列を変えない。ファイルは読まない。`gh` は呼ばない。拒否しない。

`hasFormMarker` が false のときは、空配列である。必須の節が無くても、曖昧な語があっても、反映済みの記録が壊れていても、空配列である。

true のときは、次の順で違反を積む。

1. 必須の節が無いもの。上の節名の順
2. 「受け入れ条件」の見出しがあるとき、形が不正な行。上から
3. そのあと、重複する番号。昇順
4. `kind` が `design` であり、受け入れ条件とテストの見出しが両方あるとき、参照の違反。項目が参照を持たない行、参照先が無い番号、テストから参照されない番号、の順
5. 反映済みの違反。あれば一つ
6. 曖昧な語。一覧の順

`kind` が `requirements` のとき、4 は積まない。返す配列は、この順である。違反が無いときは空配列である。

## コマンド

`src/cli.ts` の `printUsage` に、一行を足す。場所は `sdd-cur reflect <番号> <requirements|design>` の次、`sdd-cur complete <番号>` の前である。他の行の字面と順は変えない。使い方は、次の十一行である。各行の末尾は改行である。

```
sdd-cur install [project-root]
sdd-cur run [--interval-min <1 以上 1440 以下の整数>]
sdd-cur labels
sdd-cur candidates
sdd-cur show <番号>
sdd-cur branch <番号>
sdd-cur confirm <番号>
sdd-cur close <番号>
sdd-cur reflect <番号> <requirements|design>
sdd-cur validate <番号>
sdd-cur complete <番号>
```

`wantsHelp` は変えない。`--help` と `-h` は、今どおり使い方を書いて終了コード 0 である。

引数が番号一つでないときは、使い方を書いて終了コード 1 である。番号の理由は書かない。番号は `parseIssueNumberString` で読む。拒否されたときは、`番号が不正です` を標準エラーへ一行書き、終了コード 1 である。使い方は書かない。

ファイルは、`specPaths` のパスを、`readSpecFile` で読む。作業ディレクトリは `process.cwd()` である。標準エラーに書くパスは、`specPaths` の `/` 区切りの相対パスである。絶対パスにはしない。

読み取りは、要件、設計の順である。`readSpecFile` が拒否したときは、その理由を標準エラーへ一行書き、終了コード 1 である。形式の違反は書かない。要件の読み取りが拒否されたときは、設計を読まない。`exists` が false のファイルはスキップする。`validateSpecForm` は呼ばない。

`exists` が true のファイルは、`validateSpecForm` に渡す。要件は `"requirements"`、設計は `"design"` である。返った各違反を、`<相対パス>: <違反>` の一行にする。要件の違反をすべて書いたあと、設計の違反を書く。違反が一つでもあるときは、終了コード 1 である。一つも無いとき、および両方をスキップしたときは、終了コード 0 である。

成功のときも失敗のときも、標準出力は空である。ファイルは作らない。変えない。`gh`、`git`、`agent` は起動しない。トークンと環境変数は読まない。

`switch` に `validate` を足す。未知のサブコマンドは、今どおり使い方を書いて終了コード 1 である。

## 無いファイル

コマンドが見る二つのファイルは、別々にスキップする。一方が無く、他方が印ありで違反を持つときは、終了コード 1 であり、標準エラーには違反のあるファイルの行だけがある。一方が無く、他方が印無しのとき、および両方が無いときは、終了コード 0 であり、標準出力も標準エラーも空である。

スキルは、レビュー役を起動する直前にだけ、コマンドを実行する。その段のファイルが作業ツリーに無いときは、コマンドを実行しない。実行しないことだけでは、失敗にしない。レビュー役も修正役も、ファイルが無いことだけでは起動しない。ファイルを書いていないときの既存の止まりは、そのままである。

要求の段のファイルは `docs/specs/<番号>/requirements.md` である。設計の段のファイルは `docs/specs/<番号>/design.md` である。その段のファイルがあるとき、コマンドは両方のパスを見る。他方のファイルが無いときは、コマンドがスキップする。そのスキップだけでは、終了コードは 1 にならない。

印が無いファイルをスキップしただけの終了コード 0 のときは、今までどおりレビュー役を起動する。

## スキル

対象は `skills/sdd-cur/SKILL.md` と `skills/sdd-cur-quick/SKILL.md` だけである。作成役を起動する手順の文言は変えない。レビュー役の判定行、確認行、印が壊れているときのやり直し、連続不合格、回数、モデルの文言は変えない。足すのは、レビュー役を起動する直前の検査である。

実行は、リポジトリのルート、または quick が書くクローンの作業ツリーで、`bun src/cli.ts validate <番号>` である。`<番号>` は、その手順の課題番号である。`gh` は直接起動しない。

終了コードが 0 のときは、今までどおりレビュー役を起動する。

終了コードが 0 以外のときは、レビュー役を起動しない。標準エラーの全文を、その段の修正役に渡す。レビューの差分は渡さない。判定行も確認行も、この失敗からは読まない。この失敗は、レビューの連続不合格に数えない。

修正役が戻ったあとは、レビュー役を起動する前に、同じコマンドを再び実行する。

段と修正役は、次である。回答の節で検査が成功したあと、レビューが不合格のときの止まりは、今のままである。回答の節の設計側で、レビューの不合格から設計の修正役を起動しないことも、今のままである。

| 場所 | 実行する条件 | 失敗したときに渡す修正役 |
|---|---|---|
| `sdd-cur` の要件 | 要件ファイルがある。要求のレビュー役を起動する直前 | `sdd-cur-req-fixer` |
| `sdd-cur` の設計 | 設計ファイルがある。設計のレビュー役を起動する直前 | `sdd-cur-design-fixer` |
| `sdd-cur` の回答で、側が `requirements` | 要件ファイルがある。要求のレビュー役を起動する直前 | `sdd-cur-req-fixer`。設計の作成も設計の修正も、この失敗のあいだは続けない |
| `sdd-cur` の回答で、側が `design` | 設計ファイルがある。設計のレビュー役を起動する直前 | `sdd-cur-design-fixer`。設計の作成手順も設計の修正手順も、この失敗のあいだは続けない |
| `sdd-cur-quick` の要件 | 要件ファイルがある。要求のレビュー役を起動する直前 | `sdd-cur-req-fixer` |
| `sdd-cur-quick` の設計 | 設計ファイルがある。設計のレビュー役を起動する直前 | `sdd-cur-design-fixer` |

`reflect` が失敗してレビュー役を起動しないときは、`validate` も実行しない。要求作成役を起動する前、および設計作成役を起動する前には、実行しない。

## 約束の文書

`docs/conventions.md` の既存の節は、字面を変えない。末尾に、次の規則を足す。

- 新形式の印は、上の `formMarkerLine` である。例は、囲みコードブロックの中に一つだけ置く。囲みの外に、その行は書かない
- 印が無いファイルを、`validate` は検査しない。スキップだけでは失敗にしない
- 印がある要件の必須の節は「受け入れ条件」だけである。それ以外は任意である
- 印がある設計の必須の節は「受け入れ条件」「範囲外」「決定」「テスト」である
- 受け入れ条件の項目は、`- <番号>. 条件: <条件> 主体: <主体> 結果: <結果>` の一行である。番号は、そのファイルの中で重複しない
- 印がある設計の「テスト」節の、行頭が `- ` である項目は、その設計の受け入れ条件の番号を `[<番号>]` で参照する。参照されない受け入れ条件があると、検査は失敗する
- 反映済みの開始行が無いときは、その形では失敗しない。開始行があるときの形は、既存の「反映済みの回答」と同じであり、`readReflectedIds` が拒否しないことである
- 曖昧な語は、決定の十八語である。一つの囲みコードブロックの非空行が、`ambiguousWords` と一文字も違わず、過不足が無く、同じ順である

`src/conventions.ts` の既存のエクスポートの字面と意味は、変えない。足すのは、`formMarker`、`formMarkerLine`、`ambiguousWords`、`hasFormMarker`、`validateSpecForm` である。

## テスト

`src/conventions.test.ts` に置き、`bun:test` の `describe` と `test` を使う。`gh` は起動しない。一時ディレクトリは、この節の関数テストでは使わない。

- `hasFormMarker` は、先頭の空行を飛ばし、2 行目の非空行が `<!-- sdd-cur:form -->` のときだけ true である。印が最初の非空行であるとき、3 行目以降の非空行であるとき、行の前後に空白があるとき、行が無いときは false である。`\r\n` の本文でも、2 行目の非空行が印のときは true である。
- `ambiguousWords` は、決定の十八語と、同じ順で、過不足が無い。
- `validateSpecForm` は、印が無いとき空配列である。必須の節が無く、曖昧な語があり、反映済みの記録が壊れていても、空配列である。
- 印がある要件で、`## 受け入れ条件` と、形を満たす項目が一つあるときは、空配列である。`## 現状` が同時にあっても、空配列である。`## 受け入れ条件` が無いときは、`必須の節がありません: 受け入れ条件` だけである。
- 印がある設計で、四つの必須の見出しが無いときは、四つの `必須の節がありません` を、受け入れ条件、範囲外、決定、テストの順で返す。
- 受け入れ条件の本文で、空行以外が形を満たさないときは、`受け入れ条件の形が不正です: <行>` を、上から返す。先頭の零がある番号、ピリオドの直後に空白が無い行、条件が空の行、全角コロンの行は、この違反である。
- 形を満たす同じ番号が二度あるときは、`受け入れ条件の番号が重複しています: <番号>` を、番号の昇順で一度ずつ返す。形が不正な行は、重複に数えない。
- 要件としての検査と、設計としての検査は、呼び出しが別である。番号が両方で 1 でも、それぞれの戻り値は他方を見ない。
- 印がある設計で、受け入れ条件の 1 と 2 があり、テストの項目が `[1]` だけのときは、`受け入れ条件がテストから参照されていません: 2` がある。項目行に `[<番号>]` が無いときは、`テストが受け入れ条件を参照していません: <行>` である。受け入れ条件に無い番号は、`テストが参照する受け入れ条件がありません: <番号>` である。字下げされた `- ` は項目ではない。
- 印がある要件に「テスト」節があり、項目が番号を参照していなくても、参照の違反は無い。
- 印があるファイルに反映済みの開始行が無いときは、反映済みの違反は無い。開始行が二つあるときは `反映済みの記録が複数あります` である。終了行が無いときは `反映済みの記録を解釈できません` である。形を満たす記録は、違反にしない。
- 印があるファイルに一覧の語があるときは、`曖昧な語があります: <語>` を、一覧の順に、語ごとに一つ返す。`不適切に` は `適切に` の違反になる。`fixme` は違反にしない。囲みコードブロックの中の語も違反になる。
- 複数の違反は、判定の節の順である。

文書の確認も、同じテストファイルで行う。

- `docs/conventions.md` の既存の、三つのコメント印、`sdd-cur:reflected`、`requirements.md`、`design.md` は残る。
- `<!-- sdd-cur:form -->` は、囲みコードブロックの中に一つだけあり、囲みの外には無い。
- `- <番号>. 条件: <条件> 主体: <主体> 結果: <結果>` と、`[<番号>]` と、四つの必須の見出しの行が含まれる。
