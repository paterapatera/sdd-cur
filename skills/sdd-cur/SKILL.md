# sdd-cur

リポジトリのルートで `bun src/cli.ts` を使う。作業の前に `docs/plan.md` と `docs/conventions.md` を読む。仕様へ書く挙動は、対象課題とこの計画にあるものだけである。

## 着手

`bun src/cli.ts candidates` を実行する。空なら、着手できる課題は無いと伝え、課題は作らない。空でないときは番号、題、URL を見せ、決めるのは人である。人が番号を決めるまで、要件も設計も始めない。

人が番号を決めたあとは `bun src/cli.ts show <番号>` を実行する。`state` が `open` でないときは、課題は閉じていると伝えて止まる。業務ラベルが一つでもあるときは、実装のラベルが付いていると伝えて止まる。この二つのときはファイルを変えず、`confirm` も `reflect` も実行しない。

## 要件

人が要件を依頼したときだけ、次の手順で `docs/specs/<番号>/requirements.md` を扱う。先に `bun src/cli.ts show <番号>` を実行する。`state` が `open` でないとき、および業務ラベルが一つでもあるときは、ファイルを変えず、サブエージェントも起動しない。作業ブランチも用意しない。`specs.requirements` が `invalid` のときは上書きしない。作業ブランチも用意しない。サブエージェントは起動しない。`missing` と `ready` の見出しの扱いは、要求作成役に渡す。要求作成役は、既存の正しい見出しは変えない。親は要求ファイルを自分では書かない。

課題が開いていて業務ラベルが無く、要件の状態が `invalid` でないときは、要求作成役を起動する前に作業ブランチを用意する。作業ブランチの名前は、`implementationBranch` の戻り値ではなく、`bun src/cli.ts branch <番号>` の標準出力から得る。末尾改行は除く。用意は、この手順の中で行う。実装のランナーは、この用意をしない。用意したとき、Project A の作業ツリーはその作業ブランチである。用意のあと、作業ブランチ名を `bun src/cli.ts branch <番号>` で得て、今のブランチと比べる。今のブランチが作業ブランチ名と違うときは、ファイルを変えず、サブエージェントも起動しない。要求ファイルは、この作業ツリーに書く。デフォルトブランチには書かない。

サブエージェントは `sdd-cur-req-author`、`sdd-cur-req-reviewer`、`sdd-cur-req-fixer` の名前で起動する。作成と修正に model は渡さない。frontmatter の `model` を使う。

比較を通ったあとだけ、要求作成役を起動する。返信に質問する未記載があるときは、レビューに入る前に、その点を Cursor の質問機能で質問する。親が判断に迷う点は保留し、質問しない。要求作成役が質問しないと分けた点も、質問しない。

質問のラベルは、通常の選択肢ごとに、先頭を `[スコア `、1 以上 5 以下の整数、`]` の順で始め、続けて選択肢本文とする。観点を示すときは質問本文に書き、課題整合、計画整合、仕様の明確さ、範囲の狭さ、あとでお客さま確認が要る度合いの五つを使う。示さなくてもよい。通常の選択肢を 1 つ以上並べ、最後に `課題のコメントで確認する` を置く。スコアは拘束力を持たない。スコアが高い選択肢を、親は選ばない。人が選ぶまで、その点は要求に書かない。尺度の目安として、5 は自然で明確、3 はどちらともいえない、1 は課題の外である、計画に反する、または兄弟課題が混ざるリスクが高い、とする。

人が通常の選択肢を選んだあとは、その答えを人が決めた条件として要求作成役を再び起動する。作業中の質問の回答は `reflect では取り込まない`。不採用を 1 行書くのは、次の三つだけである。それ以外の不採用は書かない。詳細、スコア、比較表は書かない。要求作成役は、人が決めた条件が次のどれに当たるかを読み、当たるときだけ「決定」節へ 1 行書く。

- E1: 人が採用しない旨を明示したときは、採用しないと 1 行書く。人が決めた条件の本文が採用しない旨を明示しているときが E1 である。
- E2: 人が同意したうえで、不採用案を書くことで誤実装や範囲の混同を防ぐときは、その不採用案を 1 行書く。人が同意したうえで、不採用案を書くことで誤実装や範囲の混同を防ぐときが E2 である。同意が無いとき、または誤実装や範囲の混同を防ぐことに当たらないときは書かない。
- E3: 二択で一方を選び、他方を採用しないときは、他方を採用しないと短く 1 行書く。通常の選択肢が二つで、人が一方を選んだときが E3 である。通常の選択肢が二つ以外のときは、E3 として書かない。

人が `課題のコメントで確認する` を選んだあとは、その点を決定として書かない。確認の手順に入る前に `show` を改めて実行する。確認の節に従い、payload を人に見せ、人がその本文を承認したあとだけ `bun src/cli.ts confirm <番号>` を実行する。印の行は入れない。人が直したときは、確認の節のとおり、直した文字列を改めて見せ、その文字列の承認があるまで `confirm` を実行しない。

`unanswered` が空でないとき、および `nextAnswer` が `null` でないときは、確認の節のとおり次の確認は投稿しない。その点は決定として書かず、依存の判断では待ちの点として扱う。

確認待ちのあいだ、依存しない未記載は質問を続ける。通常の回答は要求作成役が「決定」節へ書く。待ちの点の決定が他の節の文言を変えるとき、またはその未記載は待ちの点に依存すると判断したときは、その未記載は決めず、質問もしない。判断に迷ったときは保留し、決めず、質問もしない。

質問する未記載が無く、ファイルを書いていないときは止まる。ファイルを書いていれば、レビューと修正指示を起動する。修正指示は変える部分の差分だけであり、全文は書かない。レビューの指摘はどこにも置かない。ファイルにも課題コメントにも残さない。数えるレビューは、ファイルを書いたあとの最初と、修正のあとである。開始時の連続不合格は 0 である。ファイルにも課題コメントにも残さない。1 回目と 2 回目のレビューは model を渡さない。1 回目と 2 回目が続けて不合格のとき、3回目から model に `grok-4.7[reasoning_effort=high,fast=false]` を渡す。合格まで渡す。medium には戻さない。

レビュー役のレスポンスの最後の非空行が `判定: 合格` のときは、修正を起動しない。作成も起動しない。人に伝える前に `show` を改めて実行する。`unanswered` が空であり、かつ `nextAnswer` が `null` であるときは、判定が合格なら設計に進むことができる、と伝える。どちらかが残っているときは、確認が `reflect` で終わるまで設計には進まない、と伝える。設計のファイルはこの手順で作らない。課題は閉じない。設計の手順は、人が設計を依頼したときだけ始める。

最後の非空行が `判定: 不合格` のときは、連続不合格を 1 増やす。判定行より前が `確認: あり` のときは、列挙された点を人に見せ、修正を起動しない。確認コメントは、この止まりでは投稿しない。人が答えるまで、その部分は要求へ書かない。人が答えたあとは、その答えを人が決めた条件として、レビューと修正指示を再び起動する。この再起動は回数を増やさない。モデルは、その回数と同じものを使う。この止まりは、採点付きの質問とは別である。

判定行より前が `確認: なし` のときは、その差分だけを修正へ渡す。あわせて、レビューに入る前に人が選んだ通常の回答を、人が決めた条件として渡す。修正のあと、レビューと修正指示に戻る。合格になるまで繰り返す。レビューの不合格のあと、要求作成役は起動しない。「作成から合格まで 1 回」および high の作成 1 回は、レビューに入る前の初回の成果物作成（grok-4.7-high）を指す。設計 26 の質問で人が通常の選択肢を選んだあとの要求作成役の再起動は、同じ要求の続きであり、作成の high の 2 回目に数えない。

最後の非空行が合格と不合格のどちらでもないとき、および不合格なのに確認の行が二択のどちらでもないときは、修正を起動しない。レスポンスを人に見せて止まる。

## 設計

人が設計を依頼したときだけ、次の手順で `docs/specs/<番号>/design.md` を扱う。先に `bun src/cli.ts show <番号>` を実行する。`state` が `open` でないとき、および業務ラベルが一つでもあるときは、ファイルを変えず、サブエージェントも起動しない。

`unanswered` が空でないときは、未回答の確認があるため、設計には進まない、と伝えて止まる。`nextAnswer` が `null` でないときは、まだ要求へ反映していない回答があるため、設計には進まない、と伝えて止まる。両方が残っているときは、未回答の確認を先に伝える。ファイルを変えず、設計のサブエージェントを起動しない。

要件の状態が `ready` でないときは、`missing` なら要件が無い、`invalid` なら要件の見出しが不正である、と伝えてファイルを変えない。サブエージェントは起動しない。`specs.design` が `invalid` のときは上書きしない。サブエージェントは起動しない。`missing` と `ready` の見出しの扱いは、設計作成役に渡す。設計作成役は、既存の正しい見出しは変えない。親は設計ファイルを自分では書かない。

要件の状態が `ready` であり、設計の状態が `invalid` でないとき、設計ファイルを書く作業ツリーは、要求のときに用意した同じ作業ブランチである。デフォルトブランチから作業ブランチを作り直さない。設計ファイルは、この作業ツリーに書く。デフォルトブランチには書かない。

サブエージェントは `sdd-cur-design-author`、`sdd-cur-design-reviewer`、`sdd-cur-design-fixer` の名前で起動する。作成と修正に model は渡さない。frontmatter の `model` を使う。

設計作成役を起動する前に、作業ブランチ名を `bun src/cli.ts branch <番号>` の標準出力から得る。末尾改行は除く。今のブランチと比べる。今のブランチが作業ブランチ名と違うときは、ファイルを変えず、設計のサブエージェントも起動しない。比較を通ったあとだけ、設計作成役を起動する。ファイルを変えなかったときは止まる。書いたあと、レビューと修正指示を起動する。レビューの指摘はどこにも置かない。ファイルにも課題コメントにも残さない。回数、モデル、`確認: あり`、`確認: なし`、二択でないときの止まりは、要件の手順と同じである。人が答えるまで、その部分は設計へ書かない。

レビュー役のレスポンスの最後の非空行が `判定: 合格` のときは、修正を起動しない。作成も起動しない。設計を終える。要求ファイルはこの手順で作らない。課題は閉じない。判定が合格なら実装依頼に進むことができる、と人に伝えて終わる。人が設計の完了を伝えたときは、push と「実装依頼」は人が行う。push するのは、要求と設計を含む作業ブランチである。

最後の非空行が `判定: 不合格` のときは、連続不合格を 1 増やす。判定行より前が `確認: あり` のときは、列挙された点を人に見せ、修正を起動しない。確認コメントは、この止まりでは投稿しない。人が答えるまで、その部分は設計へ書かない。人が答えたあとは、その答えを人が決めた条件として、レビューと修正指示を再び起動する。この再起動は回数を増やさない。モデルは、その回数と同じものを使う。

判定行より前が `確認: なし` のときは、その差分だけを修正へ渡す。修正のあと、レビューと修正指示に戻る。合格になるまで繰り返す。不合格のあと、設計作成役は起動しない。

最後の非空行が合格と不合格のどちらでもないとき、および不合格なのに確認の行が二択のどちらでもないときは、修正を起動しない。レスポンスを人に見せて止まる。

## 確認

課題、計画、既存の回答から決められない点だけを payload にする。決められない点は仕様ファイルへ書かない。本文が扱う決められない点は、一つである。その一つの点に選択肢があっても、点は一つである。別の点は、別の確認コメントにする。一つの本文に、決定を二つ以上書かない。本文にスコアを書かない。`[スコア ` で始まる行も書かない。複数の決定とスコアを一つの本文にまとめた確認は、投稿しない。本文の形は、要件への確認と設計への確認で同じである。`show` の `nextAnswer` が `null` でないときは投稿しない。`unanswered` が空でないときは、いちばん古い未回答の payload を見せ、未回答の確認があるあいだ、次の確認は投稿しない。まだ要求または設計へ反映していない回答があるあいだも、次の確認は投稿しない。どちらのゲートも通過したときだけ、payload を人に見せ、人がその本文を承認したあとだけ `bun src/cli.ts confirm <番号>` を実行する。人が直したときは、直した文字列を改めて見せ、その文字列の承認があるまで `confirm` を実行しない。標準入力は承認された payload だけであり、印の行は入れない。決められない点が複数あるときは、一点ずつ payload を分け、上の手順を繰り返す。一つの `confirm` にまとめない。

## 回答

回答コメントを投稿しない。人が取り込みを依頼したとき、`nextAnswer` が `null` なら、未反映の回答は無いと伝えてファイルを変えない。`null` でないときは、未反映の回答があるとき、人が取り込み先を決めるまでファイルは変えない。人が `requirements` か `design` かを決めたあとも、reflect が成功するまでディスク上のファイルは変えない。決定を書いた全文は、`bun src/cli.ts reflect <番号> <requirements|design>` の標準入力だけに渡す。追記は、反映済みブロックより前に置く。印の行は入れない。本文には id を書かない。`reflect` が id を足してから、選んだ側のファイルを書く。一度の `reflect` のあと、残りの未反映があっても、次の依頼まで続けない。

## 禁止

課題は作らない。課題は閉じない。ラベルは変えない。実装依頼は人が付ける。push は人が行う。実装は課題ランナーが行う。受け入れ手順は投稿しない。完了処理は行わない。gh は直接起動しない。
