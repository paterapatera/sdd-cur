# sdd-cur

リポジトリのルートで `bun src/cli.ts` を使う。作業の前に `docs/plan.md` と `docs/conventions.md` を読む。仕様へ書く挙動は、対象課題とこの計画にあるものだけである。

## 着手

`bun src/cli.ts candidates` を実行する。空なら、着手できる課題は無いと伝え、課題は作らない。空でないときは番号、題、URL を見せ、決めるのは人である。人が番号を決めるまで、要件も設計も始めない。

人が番号を決めたあとは `bun src/cli.ts show <番号>` を実行する。`state` が `open` でないときは、課題は閉じていると伝えて止まる。業務ラベルが一つでもあるときは、実装のラベルが付いていると伝えて止まる。この二つのときはファイルを変えず、`confirm` も `reflect` も実行しない。

## 要件

人が要件を依頼したときだけ、次の手順で `docs/specs/<番号>/requirements.md` を扱う。先に `bun src/cli.ts show <番号>` を実行する。`state` が `open` でないとき、および業務ラベルが一つでもあるときは、ファイルを変えず、サブエージェントも起動しない。作業ブランチも用意しない。`specs.requirements` が `invalid` のときは上書きしない。作業ブランチも用意しない。サブエージェントは起動しない。`missing` と `ready` の見出しの扱いは、要求作成役に渡す。要求作成役は、既存の正しい見出しは変えない。親は要求ファイルを自分では書かない。

課題が開いていて業務ラベルが無く、要件の状態が `invalid` でないときは、要求作成役を起動する前に作業ブランチを用意する。作業ブランチの名前は `implementationBranch` の戻り値である。用意は、この手順の中で行う。実装のランナーは、この用意をしない。用意したとき、Project A の作業ツリーはその作業ブランチである。要求ファイルは、この作業ツリーに書く。デフォルトブランチには書かない。

サブエージェントは `sdd-cur-req-author`、`sdd-cur-req-reviewer`、`sdd-cur-req-fix-proposer`、`sdd-cur-req-fixer` の名前で起動する。model は渡さない。

要求作成役を起動する。ファイルを変えなかったときは止まる。書いたあと、レビュー役を起動する。レビューの指摘はどこにも置かない。ファイルにも課題コメントにも残さない。レビュー役のレスポンスの最後の非空行が `判定: 合格` のときは、修正案役も修正役も起動しない。要件定義を終える。設計のファイルはこの手順で作らない。課題は閉じない。判定が合格なら設計に進むことができる、と人に伝えて終わる。設計の手順は、人が設計を依頼したときだけ始める。

最後の非空行が `判定: 不合格` のときは、修正案役を起動する。最後の非空行が `確認: あり` のときは、列挙された点を人に見せ、修正役を起動しない。確認コメントは、この止まりでは投稿しない。人が答えるまで、その部分は要求へ書かない。人が答えたあとは、その答えを人が決めた条件として修正案役を再び起動する。

最後の非空行が `確認: なし` のときは、その修正案だけを修正役へ渡す。修正のあと、レビュー役に戻る。合格になるまで繰り返す。

レビュー役または修正案役の最後の非空行が、上の二択のどちらでもないときは、修正案役も修正役も起動しない。レスポンスを人に見せて止まる。

## 設計

人が設計を依頼したときだけ、次の手順で `docs/specs/<番号>/design.md` を扱う。先に `bun src/cli.ts show <番号>` を実行する。`state` が `open` でないとき、および業務ラベルが一つでもあるときは、ファイルを変えず、サブエージェントも起動しない。要件の状態が `ready` でないときは、`missing` なら要件が無い、`invalid` なら要件の見出しが不正である、と伝えてファイルを変えない。サブエージェントは起動しない。`specs.design` が `invalid` のときは上書きしない。サブエージェントは起動しない。`missing` と `ready` の見出しの扱いは、設計作成役に渡す。設計作成役は、既存の正しい見出しは変えない。親は設計ファイルを自分では書かない。

要件の状態が `ready` であり、設計の状態が `invalid` でないとき、設計ファイルを書く作業ツリーは、要求のときに用意した同じ作業ブランチである。デフォルトブランチから作業ブランチを作り直さない。設計ファイルは、この作業ツリーに書く。デフォルトブランチには書かない。

サブエージェントは `sdd-cur-design-author`、`sdd-cur-design-reviewer`、`sdd-cur-design-fix-proposer`、`sdd-cur-design-fixer` の名前で起動する。model は渡さない。

設計作成役を起動する。ファイルを変えなかったときは止まる。書いたあと、レビュー役を起動する。レビューの指摘はどこにも置かない。ファイルにも課題コメントにも残さない。レビュー役のレスポンスの最後の非空行が `判定: 合格` のときは、修正案役も修正役も起動しない。設計を終える。要求ファイルはこの手順で作らない。課題は閉じない。判定が合格なら実装依頼に進むことができる、と人に伝えて終わる。人が設計の完了を伝えたときは、push と「実装依頼」は人が行う。push するのは、要求と設計を含む作業ブランチである。

最後の非空行が `判定: 不合格` のときは、修正案役を起動する。最後の非空行が `確認: あり` のときは、列挙された点を人に見せ、修正役を起動しない。確認コメントは、この止まりでは投稿しない。人が答えるまで、その部分は設計へ書かない。人が答えたあとは、その答えを人が決めた条件として修正案役を再び起動する。

最後の非空行が `確認: なし` のときは、その修正案だけを修正役へ渡す。修正のあと、レビュー役に戻る。合格になるまで繰り返す。

レビュー役または修正案役の最後の非空行が、上の二択のどちらでもないときは、修正案役も修正役も起動しない。レスポンスを人に見せて止まる。

## 確認

課題、計画、既存の回答から決められない点だけを payload にする。決められない点は仕様ファイルへ書かない。`show` の `nextAnswer` が `null` でないときは投稿しない。`unanswered` が空でないときは、いちばん古い未回答の payload を見せ、未回答の確認があるあいだ、次の確認は投稿しない。どちらでもないとき、payload を人に見せ、人がその本文を承認したあとだけ `bun src/cli.ts confirm <番号>` を実行する。人が直したときは、直した文字列を改めて見せ、その文字列の承認があるまで `confirm` を実行しない。標準入力は承認された payload だけであり、印の行は入れない。

## 回答

回答コメントを投稿しない。人が取り込みを依頼したとき、`nextAnswer` が `null` なら、未反映の回答は無いと伝えてファイルを変えない。`null` でないときは、未反映の回答があるとき、人が取り込み先を決めるまでファイルは変えない。人が `requirements` か `design` かを決めたあとも、reflect が成功するまでディスク上のファイルは変えない。決定を書いた全文は、`bun src/cli.ts reflect <番号> <requirements|design>` の標準入力だけに渡す。追記は、反映済みブロックより前に置く。印の行は入れない。本文には id を書かない。`reflect` が id を足してから、選んだ側のファイルを書く。一度の `reflect` のあと、残りの未反映があっても、次の依頼まで続けない。

## 禁止

課題は作らない。課題は閉じない。ラベルは変えない。実装依頼は人が付ける。push は人が行う。実装は課題ランナーが行う。受け入れ手順は投稿しない。完了処理は行わない。gh は直接起動しない。
