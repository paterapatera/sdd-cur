# 約束

スキルと課題ランナーが同じ規則を使う。判定の実装は `src/conventions.ts` にある。

## 課題ごとのファイル

課題番号を `<番号>` とする。十進で、先頭の零は付けない。

| ファイル | 内容 |
|---|---|
| `docs/issues/<番号>/requirements.md` | 要件 |
| `docs/issues/<番号>/design.md` | 設計 |

各ファイルの最初の非空行は、`# <番号> ` のあとに題が一つ以上ある見出しである。

## 仕様の正本

今のシステムの挙動を表す仕様の正本は、`docs/canonical/` に置く。課題ごとの要件と設計とは別である。

| ファイル | 内容 |
|---|---|
| `docs/canonical/<領域>.md` | その領域の要求 |

`<領域>` は英小文字で始まり、英小文字と数字が続き、区切りのハイフンを含んでよい。ハイフンは先頭、末尾、連続には使わない。

要求の識別子は、`REQ-` のあとに、十進で先頭の零の無い 1 以上の整数を続けたものである。同じ識別子は正本に一度だけある。変更は識別子を変えない。

課題の設計の `## 正本への差分` は、識別子ごとの追加、変更、削除である。項目の見出しは `### 追加 <領域> REQ-<番号>`、`### 変更 <領域> REQ-<番号>`、`### 削除 <領域> REQ-<番号>` のいずれかである。

課題ごとの `docs/issues/<番号>/requirements.md` と `docs/issues/<番号>/design.md` の置き場所は、「課題ごとのファイル」のままである。
`sdd-cur spec-apply <番号>` は、設計の `## 正本への差分` を、作業ツリーの `docs/canonical/` に書く。差分対象の識別子だけを書き換える。
期待値の計算は `spec-diff` と同じ手順である。

シナリオの一行は、行全体が `- シナリオ: 条件: <条件> 主体: <主体> 結果: <結果>` である。
`<条件>` と `<主体>` と `<結果>` は、それぞれ空白以外の文字を含む。
追加と変更の項目の本文には、その一行が一つ以上ある。
シナリオは見出しにしない。
印がある設計で、追加または変更の項目にその一行が無いと、`validate` は失敗する。
既存の要求は、変更されるときにだけシナリオを足し、一括では書き換えない。
削除の項目にはシナリオを要しない。

## レビューが読む範囲

要求レビュー役が食い違いと巻き戻りを探すときに読んで比べる範囲は、正本と、対象課題の `docs/issues/<番号>/requirements.md` の「関係する課題」に挙げた課題の仕様だけである。正本は `docs/canonical/` に置く。

設計レビュー役が食い違いと巻き戻りを探すときに読んで比べる範囲は、正本と、対象課題の `docs/issues/<番号>/design.md` の「関係する課題」に挙げた課題の仕様だけである。正本は `docs/canonical/` に置く。

挙げた課題の仕様は、その課題の `docs/issues/<番号>/requirements.md` と `docs/issues/<番号>/design.md` である。

既存の `docs/issues/<番号>/` は消さず、履歴として残す。

## 課題コメントの種別

確認と回答は、課題のコメントだけに書く。要件、設計、コミットメッセージ、マージリクエストには書かない。

コメントの最初の非空行が、次の印と一文字も違わないとき、その種別になる。印の行の前後に空白があれば、種別は付かない。

| 種別 | 印 |
|---|---|
| お客さまへの確認 | `sdd-cur: 確認` |
| 人による回答 | `sdd-cur: 回答` |
| 受け入れ手順 | `sdd-cur: 受け入れ手順` |

印の行より後ろが本文である。確認と回答は、古いコメントから見て、未対応のうちいちばん古い確認に回答を一つ付ける。課題コメントにある受け入れ手順は、同じ順の最後の一件である。課題ランナーが書く現在の手順は、マージリクエストの本文から取る。

未回答の確認があるあいだ、次の確認は投稿しない。

## 反映済みの回答

要件または設計へ取り込んだ回答は、そのファイル末尾に、取り込んだ回答コメントの `id` だけを記録する。確認文も回答文も書かない。

記録の例:

```
<!-- sdd-cur:reflected
IC_kwDOExample123
-->
```

## 未反映の回答

確認と組になった回答のうち、要件と設計のどちらの記録にも `id` が無いものが、まだ取り込んでいない回答である。

## マージリクエストの会話コメント

不具合と修正は、マージリクエストの会話コメントだけに書く。課題のコメント、要件、設計、コミットメッセージには書かない。

コメントの最初の非空行が、次の印と一文字も違わないとき、その種別になる。印の行の前後に空白があれば、種別は付かない。判定は、課題コメントの印と同じ規則である。

| 種別 | 印 |
|---|---|
| 不具合 | `sdd-cur: 不具合` |
| 修正 | `sdd-cur: 修正` |

印の行より後ろが本文である。1 コメントに複数の不具合を書いてよい。処理の単位は、コメントの id である。

確認、回答、受け入れ手順の印と、課題コメントの規則は、変えない。

## 処理済みの不具合

修正コメントの末尾に、その修正で処理した不具合コメントの `id` だけを記録する。形は、反映済みの記録と同じである。印だけが `sdd-cur:fixed` である。

記録の例:

```
<!-- sdd-cur:fixed
IC_kwDOExample123
-->
```

どの修正コメントのこの記録にも `id` が無い不具合コメントが、未処理である。

`sdd-cur:reflected` は、要件と設計のファイルに書く、反映済みの回答の記録のままである。`sdd-cur:fixed` は、マージリクエストの修正コメントに書く。

## レビューの判定

判定の読み方は `src/conventions.ts` の `parseReview` にある。

本文の改行を `\n` にそろえ、下の行から、行全体が次のどちらかと一文字も違わない行を探す。最初に見つかった行が判定行である。その後ろは見ない。前後の空白を除いて比べない。

| 判定 | 行 |
|---|---|
| 合格 | `判定: 合格` |
| 不合格 | `判定: 不合格` |

一致する行が無いとき、判定は無い。この文書は、それを印が壊れているとする。やり直しと停止は、各レビュー手順が行う。

判定行が不合格のときだけ、その行より前を下から見て、行全体が次のどちらかと一文字も違わない行を探す。最初に見つかった行が確認行である。判定行より後ろは見ない。合格のとき、および判定が無いときは、確認行を探さない。

| 確認 | 行 |
|---|---|
| あり | `確認: あり` |
| なし | `確認: なし` |

## マージリクエストの本文

課題ランナーが書く受け入れ手順は、マージリクエストの本文に置く。課題ランナーは、課題コメントに受け入れ手順を書かない。

本文の並びは、課題の URL、作業の一覧、印 `sdd-cur: 受け入れ手順`、受け入れ手順の順である。印の行は、本文にある受け入れ手順の最初の非空行である。

課題の URL は印より前である。作業の一覧も印より前である。課題の URL と作業の一覧と印のあいだに、空行も見出しも説明の行も入れない。印の行より後ろには課題の URL を含めない。現在の手順は、本文の印の行より後ろである。

課題ランナーが、マージリクエストを知らせる課題コメントは、マージリクエストの URL だけである。題や説明は付けない。このコメントには印を書かない。

確認と回答の課題コメントは、変えない。課題コメントの印と、最後の受け入れ手順コメントを取る規則は、変えない。

## 着手の課題コメント

実装、修正、軽微な修正の着手は、課題のコメントに書く。要件、設計、コミットメッセージ、マージリクエストの会話には書かない。

コメントの最初の非空行が `sdd-cur: 着手` と一文字も違わないとき、着手である。印の行の前後に空白があれば、着手ではない。

印の直後の行は、クローン識別子である。識別子は、空でなく、空白を含まない一行である。

確認、回答、受け入れ手順の印と、その判定は、変えない。マージリクエストを知らせる課題コメントは、「マージリクエストの本文」の節のままである。

## 要件と設計の形式

新形式の印は、次の行である。例は、囲みコードブロックの中に一つだけ置く。囲みの外に、その行は書かない。

```
<!-- sdd-cur:form -->
```

印が無いファイルを、`validate` は検査しない。スキップだけでは失敗にしない。

印がある要件の必須の節は「受け入れ条件」だけである。それ以外は任意である。

印がある設計の必須の節は「受け入れ条件」「範囲外」「決定」「テスト」である。

印がある設計には、任意の節 `## データモデル`、`## インターフェース`、`## 図` を書いてよい。節が無いときは `validate` は失敗しない。節があるときは、本文が空でないことを検査する。
`## 図` があるときは、各本文に Mermaid の囲みコードブロックを一つ以上持つことを検査する。

受け入れ条件の項目は、`- <番号>. 条件: <条件> 主体: <主体> 結果: <結果>` の一行である。番号は、そのファイルの中で重複しない。

印がある設計の「テスト」節の、行頭が `- ` である項目は、その設計の受け入れ条件の番号を `[<番号>]` で参照する。参照されない受け入れ条件があると、検査は失敗する。

- 印がある設計の作業の一覧の見出しは `## 作業の一覧` である
- 作業の項目は、行頭が `- ` であり、`- <番号>. ` に続く本文を持つ
- 作業が満たす受け入れ条件の番号は、本文の `[<番号>]` である
- 形を満たす受け入れ条件の番号のうち、どの作業の `[<番号>]` にも無いものは、`受け入れ条件が作業の一覧に入っていません: <番号>` で失敗する

反映済みの開始行が無いときは、その形では失敗しない。開始行があるときの形は、既存の「反映済みの回答」と同じであり、`readReflectedIds` が拒否しないことである。

曖昧な語は、次の十八語である。一つの囲みコードブロックの非空行が、`ambiguousWords` と一文字も違わず、過不足が無く、同じ順である。

```
適切に
必要に応じて
適宜
可能な限り
十分に
なるべく
できるだけ
高速に
使いやすく
柔軟に
基本的に
原則として
一般的に
望ましくは
できれば
TBD
TODO
FIXME
```

シナリオの一行は、行全体が `- シナリオ: 条件: <条件> 主体: <主体> 結果: <結果>` である。
`<条件>` と `<主体>` と `<結果>` は、それぞれ空白以外の文字を含む。
追加と変更の項目の本文には、その一行が一つ以上ある。
シナリオは見出しにしない。
印がある設計で、追加または変更の項目にその一行が無いと、`validate` は失敗する。
既存の要求は、変更されるときにだけシナリオを足し、一括では書き換えない。
削除の項目にはシナリオを要しない。

本文は、見出しの次の行から、行が `## ` で始まる次の行の直前までであり、空白と改行だけなら空である。出現する各節の本文をそれぞれ検査する。
本文が空のときの違反は `節の本文が空です: <節名>` であり、節名はデータモデル、インターフェース、図である。
Mermaid の囲みは、行全体がバッククォート三つの直後に `mermaid` を続けたものと一致する開始行で開き、行全体がバッククォート三つと一致する行で閉じたブロックを一つと数える。行頭の空白は無い。中身が空でも数える。
囲みが無いときの違反は `図に Mermaid の囲みがありません` である。
